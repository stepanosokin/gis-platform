## Как устроена платформа

### Какие контейнеры входят в Compose-проект

Compose-проект объединяет контейнеры одного развёртывания и его внутреннюю сеть. CLI выбирает состав по платформенному YAML. В таблице указаны имена сервисов. Docker добавляет к имени контейнера имя проекта и номер, например `gis-platform-caddy-1`.

| Сервис | Когда появляется | За что отвечает |
| --- | --- | --- |
| `caddy` | В каждом запущенном развёртывании. | Принимает внешние HTTP/HTTPS-запросы и направляет их к нужному сервису. |
| `pygeoapi` | Если настроен встроенный экземпляр pygeoapi. | Читает источники и выдаёт объекты через OGC API — Features. |
| Например, `provider-pygeoapi` | Для подключённых экземпляров из отдельных образов. Martin запускается, когда на него ссылается публикация. | Обслуживает данные через настроенный протокол. Здесь может работать pygeoapi, Martin или pydggsapi. |
| `access` | Если в YAML задан `auth`. | Обслуживает учётные записи и проверяет права на публикации. При настроенном `auth.cli` принимает локальные команды оператора. |
| `postgres` | Вместе с `access`. | Хранит учётные записи, сеансы, токены и разрешения в томе `accounts`. |
| `mailpit` | При `auth.mode: development`. | Принимает тестовые письма, например письмо подтверждения регистрации. |
| `metadata` | В конфигурациях, для которых CLI добавляет отдельный сервис метаданных. | Отдаёт публичные каталоги и описания API. |

В первом примере с GeoJSON работают `caddy` и `pygeoapi`. Посмотреть фактический состав своего проекта можно по [метке Compose](#найти-развёртывание-и-проверить-состояние).

### Какие конфиги определяют систему

| Файл или каталог | Что задаёт |
| --- | --- |
| `platform.yaml` | Что должно работать. Содержит внешний адрес, источники, экземпляры, публикации и настройки доступа. Его правит владелец развёртывания. |
| `integration.yaml` | Как добавить отдельный экземпляр из образа командой `provider add`. CLI переносит эти параметры в `platform.yaml`. |
| [compose.yaml](compose.yaml) и его дополнения | Из каких образов запускать сервисы, какие порты открыть и какие файлы и тома подключить. CLI выбирает дополнения, например для HTTPS и регистрации. |
| `GIS_STATE_DIR/plans/<id>/` | Снимок настроек конкретного плана. CLI готовит `Caddyfile`, конфиги провайдеров и доступа, OpenAPI и дополнительные файлы Compose. Сервисы используют файлы подтверждённой версии. |
| Окружение запуска | `COMPOSE_PROJECT_NAME` выбирает проект, `GIS_STATE_DIR` задаёт каталог состояния, `GIS_PUBLIC_BIND` управляет привязкой портов шлюза. |

Изменение `platform.yaml` вступает в силу после проверки плана и `config apply`. [Как читать YAML и файлы Compose](#подготовка-окружения-и-yaml)

### Как проходит запрос к публикации

Разберём запрос QGIS к коллекции `places`.

1. QGIS отправляет запрос по внешнему адресу, например `http://localhost:8080/features/collections/places/items?f=json`. Его принимает **Caddy**, единственная точка входа для запросов к публикациям.
2. Шлюз определяет по URL ID публикации `places`. Публикация связывает конкретный источник, экземпляр сервис-провайдера, протокол и режим доступа. Одни и те же данные можно опубликовать несколько раз, например через Features и тайлы или с разными правилами доступа.
3. Для защищённой публикации шлюз запрашивает решение у **компонента доступа**. Этот компонент использует PostgreSQL платформы для учётных записей, сеансов, токенов и персональных разрешений. Публичная публикация доступна без входа.
4. Для разрешённого запроса шлюз обращается через внутреннюю сеть Compose к **экземпляру сервис-провайдера**. В нашем примере pygeoapi читает файл GeoJSON и возвращает объекты. Другие экземпляры, например Martin или pydggsapi, могут читать свои форматы и отвечать по другим протоколам.
5. Клиент получает ответ через Caddy. По внешнему адресу также доступны каталоги, схемы и описания API. Видимость защищённых публикаций зависит от прав клиента.

**Источник** определяет, где лежат данные. **Адаптер** платформы знает, как настроить конкретный сервис-провайдер. **Экземпляр** — отдельное настроенное подключение с собственным ID. **Публикация** определяет, как клиент получает данные и кто имеет к ним доступ. [Глоссарий проекта](GLOSSARY.md)

Платформа работает с двумя разными БД. PostgreSQL платформы хранит учётные записи и права. Внешний PostGIS может быть источником пространственных данных. За его схему, данные и резервное копирование отвечает владелец этой БД.

## Подготовка окружения и YAML

### Что установить

- Git для получения исходного кода либо подготовленную копию нужной версии проекта.
- Node.js версии 24 или новее с npm. `npm ci` устанавливает зависимости по `package-lock.json`, `npm run build` компилирует TypeScript из `src/` в JavaScript в `dist/`, а `node dist/cli.js` запускает CLI администратора на хосте.
- Docker с работающим движком и Compose 2.24.4 или новее. Эта версия поддерживает переопределение монтирований в `compose.empty.yaml`. Для DGGS требуется запуск контейнеров `linux/amd64`.
- `curl` для проверки через шлюз. Для серверного развёртывания с TLS и регистрацией понадобятся сертификаты и ключи, SMTP-реле и `openssl` для создания секретов. Для штатных резервных копий нужен restic.

В Windows включите интеграцию Docker Desktop с пользовательским дистрибутивом WSL 2. В PowerShell команда `wsl --list --verbose` показывает дистрибутивы и версию WSL. Откройте выбранный дистрибутив и разместите рабочую копию в его файловой системе, например `~/gis-platform`. Установите Node.js и запускайте npm и команды из руководства в Bash этого же дистрибутива.

Проверку выполните в каталоге репозитория. На сервере далее используется `/opt/gis-platform`. Для локальной пробы подставьте каталог своей рабочей копии.

```sh
node --version
npm --version
docker info --format '{{.ServerVersion}}'
docker compose version
curl --version
```

### Какие файлы где лежат

| Где | Что хранится |
| --- | --- |
| `/opt/gis-platform` | Код выбранной версии, файлы Compose, примеры и собранный `dist/cli.js`. |
| `/srv/gis/platform.yaml` | Редактируемая конфигурация развёртывания. |
| `/srv/gis/data` и `/srv/gis/secrets` | Указанные в YAML файлы данных, сертификаты, ключи и файлы паролей. |
| `GIS_STATE_DIR`, например `/srv/gis/state` | Служебное состояние CLI, планы, подтверждённые версии, нативные конфиги, OpenAPI и архивы TLS. По умолчанию это `.gis-platform/` под корнем установки. |
| Именованные тома Compose | `accounts` хранит PostgreSQL платформы. `caddy_data` и `caddy_config` хранят данные Caddy. Отдельные экземпляры могут использовать свои тома. |

`COMPOSE_PROJECT_NAME` определяет группу контейнеров, сеть и имена томов. Сохраняйте то же имя проекта и тот же каталог состояния при обычных операциях. Для эксперимента задавайте отличающиеся имя, каталог состояния и порты. Сохраняйте конфигурацию, данные и секреты вне каталога кода, чтобы можно было заменить версию приложения по прежнему пути.

### Как Compose читает несколько файлов

Одна команда с несколькими `-f` строит **одну конфигурацию проекта**. Compose читает файлы в порядке перечисления. Основной файл описывает базовые сервисы, следующие добавляют или переопределяют настройки. Например, `compose.auth.yaml` добавляет PostgreSQL платформы и компонент доступа. Пути внутри файлов Compose обычно считаются от каталога первого файла. Пути внутри `platform.yaml` считаются от каталога самого `platform.yaml`.

| Файл | Когда используется |
| --- | --- |
| `compose.yaml` | Базовые настройки Caddy и встроенного pygeoapi. |
| `compose.empty.yaml` | Встроенный GeoJSON не используется. Убирает стандартное монтирование GeoJSON. |
| `compose.tls.yaml` | Внешний HTTPS и HTTP-порт для перенаправления. |
| `compose.auth.yaml` | В конфигурации задан `auth`. |
| `compose.mailpit.yaml` | `auth.mode: development`. |
| `compose.admin.json`, `compose.smtp.json` и `compose.providers.json` | Дополнения CLI для административного API, SMTP и экземпляров. Они создаются в каталоге плана, когда нужны. |

Например, команда ниже показывает имена сервисов в модели с регистрацией и тестовой почтой. Контейнеры она не запускает.

```sh
docker compose -p gis-guide-demo -f compose.yaml -f compose.auth.yaml -f compose.mailpit.yaml config --services
```

При `config apply` CLI сам выбирает файлы, готовит дополнения и передаёт Compose нужные порты, каталоги и секреты. Для обычного применения достаточно полного YAML. Как определить настройки уже работающего проекта, описано в [повседневной эксплуатации](#повседневная-эксплуатация).

### Файлы конфигурации YAML

В справке запись `<platform.yaml>` или `<integration.yaml>` означает путь к файлу. Например, можно передать `/srv/gis/platform.yaml` или `examples/provider-features.yaml`. Угловые скобки служат обозначением места аргумента и в команду не входят. В примерах `"$platform"` — значение переменной Bash с путём к вашему полному YAML.

**`platform.yaml`** описывает полное желаемое состояние развёртывания. `config validate` и `config plan` принимают этот файл. Если убрать действующую публикацию из полного YAML, `config plan` покажет её в списке удалений.

| Раздел | Содержимое |
| --- | --- |
| `schema_version` | Версия формата. Сейчас `1`. |
| `server` | Внешние имя хоста, порт и TLS. |
| `sources` | Файлы или объекты PostGIS по ID. |
| `providers` | Настройки экземпляров сервис-провайдеров по ID. |
| `publications` | Источник, экземпляр, протокол, доступ и метаданные по ID публикации. |
| `auth` | Необязательные настройки учётных записей, почты и административного API. |
| `cors` | Необязательный список веб-адресов приложений, которые обращаются к API с другого сайта. |

Первые пять разделов обязательны. Чтобы начать с пустого каталога публикаций, оставьте хотя бы один допустимый источник и задайте `publications: {}`. Для работающего проекта сначала просмотрите, какие публикации и разрешения такой план удалит. [Полный пример GeoJSON](examples/features.yaml)

**`integration.yaml`** содержит настройки одного экземпляра для команды `provider add`. На верхнем уровне идут `type` и `api`. Блок `api` задаёт `protocol`, `scheme`, `port`, `base_path`, `public_root`, `links` и `readiness`. Адаптер может поддерживать `postgis`, `environment` или `volumes`. Образ команда принимает отдельным аргументом, сама получает digest и после успеха записывает экземпляр под `providers.<id>` в полном YAML. Оставьте поля `image` и `digest` вне файла интеграции. Относительные пути в настройках экземпляра, в том числе `postgis.password_file`, считаются от платформенного YAML. [Пример интеграции pygeoapi](examples/provider-features.yaml)

В [JSON Schema](src/platform.schema.json) найдите раздел в `properties`. `description` объясняет назначение поля, `required` перечисляет обязательные поля, `enum` задаёт доступные значения. В `sources`, `providers` и `publications` блок `additionalProperties` описывает одну запись по ID. В `sources` выберите нужный `type` внутри `oneOf`. Для файла интеграции смотрите `properties.providers.additionalProperties`. Например, `server.port` — внешний порт Caddy, а `providers.<id>.api.port` — внутренний порт экземпляра в Compose.

Чтобы проверить файл интеграции без запуска контейнеров, добавьте его содержимое и `image` под `providers.<id>` во временной копии полного YAML в том же каталоге. Запустите `config validate` для этой копии. CLI проверит поля, ссылки между разделами и совместимость источника, адаптера и протокола. `provider add` применяет изменение к развёртыванию.

## Первое развёртывание

### Локальная проба с GeoJSON

1. Из корня репозитория соберите CLI и скопируйте пример в отдельный каталог. В примере источник `sample-places` указывает на `places.geojson` рядом с YAML. Экземпляр `file-features` обслуживает публичную публикацию `places`.

```sh
npm ci
npm run build
demo_root="$PWD/test_results/gis-guide-demo"
mkdir -p "$demo_root"
cp -n examples/features.yaml "$demo_root/platform.yaml"
cp -n examples/places.geojson "$demo_root/places.geojson"
export COMPOSE_PROJECT_NAME=gis-guide-demo
export GIS_STATE_DIR="$demo_root/state"
export GIS_PUBLIC_BIND=127.0.0.1
platform="$demo_root/platform.yaml"
public_url=http://localhost:8080
```

2. Убедитесь, что порт 8080 свободен. Если он занят, измените `server.port` в `$platform` и укажите тот же порт в `public_url`. Проверьте YAML и создайте план.

```sh
node dist/cli.js config validate "$platform"
node dist/cli.js config plan "$platform"
```

3. `validate` проверяет настройки. `plan` показывает изменения относительно действующей версии и возвращает ID плана. Для новой пробы ожидается добавление `places`, удаляемых публикаций нет. Проверьте внешний адрес и вставьте в следующую команду ID из вывода. `apply` проверяет источники и конфиги, запускает сервисы, проверяет маршруты и подтверждает новую версию.

```sh
read -r -p 'ID плана: ' plan_id
node dist/cli.js config apply "$plan_id"
node dist/cli.js status
node dist/cli.js doctor --publication places
curl -fsS "$public_url/features/collections?f=json"
curl -fsS "$public_url/features/collections/places/items?f=json&limit=1"
```

4. Ожидайте статус `ready` и ответ с коллекцией `places` и её объектами. Измените локальную копию YAML, например заголовок публикации, и повторите `validate → plan → apply`. Адрес коллекции определяется ID публикации, поэтому изменение заголовка сохраняет URL.

### Развёртывание на сервере

1. Получите каталог `/srv/gis` с правом записи для владельца развёртывания. Поместите согласованную версию кода в `/opt/gis-platform`. Ниже подготовка новой установки на примере GeoJSON. Для существующей установки оставьте действующий YAML и данные на месте.

```sh
cd /opt/gis-platform
git rev-parse HEAD
npm ci
npm run build
install -d -m 750 /srv/gis/data
install -d -m 700 /srv/gis/secrets /srv/gis/state
cp -n examples/features.yaml /srv/gis/platform.yaml
cp -n examples/places.geojson /srv/gis/data/places.geojson
```

В `/srv/gis/platform.yaml` замените `sources.sample-places.path` на `data/places.geojson`. Подставьте рабочий источник, когда будете готовы. Относительный путь считается от `/srv/gis`, где лежит YAML.

2. Задайте внешний адрес и TLS. Для штатного HTTPS на 443 уберите `server.port: 8080` из скопированного примера. Если используете другой порт, добавьте его к `public_url` в командах проверки. При публикации с регистрацией подготовьте SMTP и секреты по [инструкции управления доступом](#учётные-записи-и-доступ). Проверьте доступ к реестрам образов, SMTP и внешнему PostGIS из сети Docker, если они используются.
3. До применения проверьте DNS, порт и межсетевой экран. Если клиенты обращаются к Caddy напрямую, выполните `unset GIS_PUBLIC_BIND` и ограничьте внешний доступ правилами межсетевого экрана. Для проверки только с хоста или работы через прокси на том же хосте задайте `GIS_PUBLIC_BIND=127.0.0.1`. Используйте выбранную привязку уже при первом применении. CLI проверяет Caddy через `127.0.0.1`, поэтому одного внешнего интерфейса для проверки недостаточно.

```sh
cd /opt/gis-platform
export COMPOSE_PROJECT_NAME=gis-platform
export GIS_STATE_DIR=/srv/gis/state
platform=/srv/gis/platform.yaml
public_url=https://gis.example.org
node dist/cli.js config validate "$platform"
node dist/cli.js config plan "$platform"
read -r -p 'ID плана: ' plan_id
node dist/cli.js config apply "$plan_id"
node dist/cli.js status --json
node dist/cli.js doctor --json
```

4. Проверьте внешний URL из плана через Caddy с серверной и клиентской сети. Для защищённых публикаций проверьте ответы анонимного и разрешённого клиента. Ожидайте `ready` в `doctor` и данные публикации в ответе на запрос.

```sh
curl -fsS "$public_url/features/collections/places/items?f=json&limit=1"
```

### Внешний HTTP и HTTPS

`server.host` должен совпадать с именем, по которому клиенты открывают платформу. Настройте DNS на хост шлюза или на внешний прокси, который направляет трафик к Caddy. Платформа обслуживает запросы от корня адреса. При отсутствующем `server.port` Caddy использует HTTP на 80 либо HTTPS на 443. При HTTPS с порта 80 выполняется перенаправление. При занятости 80 для локального HTTPS установите `GIS_HTTP_REDIRECT_PORT` в свободный порт.

```yaml
server:
  host: gis.example.org
  tls:
    cert_file: secrets/tls/fullchain.pem
    key_file: secrets/tls/server-key.pem
    ca_file: secrets/tls/it-root.pem
```

`cert_file` содержит PEM-сертификат сервера и промежуточные сертификаты. `key_file` содержит соответствующий закрытый ключ. Укажите `ca_file`, если CLI должен доверять частному УЦ. Если доверенный корень уже известен Node.js, поле можно опустить. При необходимости добавьте корень доверия Node.js через `NODE_EXTRA_CA_CERTS` и передайте корень curl через `--cacert`. HSTS выключен.

Для замены сертификата подготовьте комплект и создайте новый план. CLI проверяет цепочку, ключ, имя хоста и срок действия, затем сохраняет принятую копию в `GIS_STATE_DIR/tls/`. `doctor --json` показывает состояние и `data.tls.expiresAt`. У старой версии без архива комплект должен оставаться доступен по прежним путям для отката. Для возврата на HTTP уберите `server.tls`, проверьте изменение внешнего адреса и примените новый план. При смене схемы или адреса пользователи входят заново.

Для проверки ещё не открытого наружу HTTPS замените значения в примере именем и портом из YAML. `--resolve` направляет запрос на loopback и сохраняет правильное имя хоста в TLS.

```sh
curl -fsS --resolve 'gis.example.org:443:127.0.0.1' \
  --cacert /srv/gis/secrets/tls/it-root.pem \
  'https://gis.example.org/features/collections?f=json'
```

## Повседневная эксплуатация

### Найти развёртывание и проверить состояние

Начните с имени проекта. Команды ниже обращаются к тому движку Docker, который выбран в текущем Docker context. Проверьте имя контекста, если работаете с несколькими хостами.

```sh
docker context show
docker compose ls --all
export COMPOSE_PROJECT_NAME=gis-platform
docker ps -a \
  --filter "label=com.docker.compose.project=$COMPOSE_PROJECT_NAME" \
  --filter 'label=com.docker.compose.oneoff=False' \
  --format 'table {{.ID}}\t{{.Names}}\t{{.Status}}\t{{.Ports}}'
```

`docker compose ls --all` помогает найти проект. Колонка `CONFIG FILES` может включать файлы нескольких ревизий. Для работающего Caddy точный каталог смонтированного конфига можно посмотреть в поле `Mounts`. Подставьте имя контейнера из предыдущей команды.

```sh
docker inspect --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}' gis-platform-caddy-1
node dist/cli.js status --json
node dist/cli.js doctor --json
```

Монтирование `/etc/caddy/gis` обычно указывает на `GIS_STATE_DIR/plans/<id>`. Для CLI задайте каталог состояния выше `plans/` и имя нужного проекта. Для диагностики от владельца развёртывания оставьте `GIS_ADMIN_PORT` незаданным. Для команд с сертификатом оператора задайте его в отдельной сессии терминала.

### Остановить, запустить или перезапустить

Эти команды работают с **уже созданными контейнерами** и сохраняют именованные тома. Подставляйте имена или ID из списка текущего проекта. В примерах используются типичные имена контейнеров.

| Действие | Порядок |
| --- | --- |
| Остановить стек | Сначала остановите Caddy командой `docker stop gis-platform-caddy-1`. Затем остановите компонент доступа, экземпляры и служебные сервисы. PostgreSQL платформы остановите последним, если он используется. |
| Запустить остановленный стек | Запустите PostgreSQL командой `docker start gis-platform-postgres-1`, если он используется. Дождитесь `healthy` в `docker ps`. Запустите остальные сервисы по их именам, затем Caddy. |
| Перезапустить один сервис | Выполните `docker restart <имя-контейнера>`. Перезапуск компонента доступа или шлюза кратковременно прерывает связанные запросы. |
| Перезапустить весь стек | Остановите его и запустите в указанном порядке. |

После запуска проверьте `doctor --json` и готовность публикации через Caddy. `docker logs --tail 100 <имя-контейнера>` показывает последние строки журнала. Добавьте `--follow` для наблюдения и завершите просмотр клавишами Ctrl+C.

Если используете `docker compose start`, `stop` или `restart`, передайте то же имя проекта и точный набор файлов и значений окружения действующей конфигурации. Через команды Docker по имени контейнера этот набор восстанавливать не требуется. Списки `CONFIG FILES` служат для диагностики.

Для применения YAML используйте CLI. Команды `start` и `restart` используют существующие файлы, монтирования и образы. `docker compose down -v` удаляет тома и может уничтожить учётные записи и права. Для штатной остановки используйте `stop`.

Если контейнеры уже удалены, проверьте наличие томов, `GIS_STATE_DIR`, исходных данных и секретов. Подготовьте новый план из действующего полного YAML и проверьте результат применения. Если CLI возвращает `NO_CHANGE` при отсутствующих контейнерах, используйте порядок повторного развёртывания из [обновления версии](#обновить-версию-платформы). При потере состояния или тома учётных записей переходите к [восстановлению из копии](#резервное-копирование-и-восстановление).

## Добавление и обновление источников

Выберите способ выдачи и подготовьте источник до планирования. Ключ в `sources` — ID источника. На него будут ссылаться записи публикаций. Файлы указывают абсолютным путём или относительно платформенного YAML. Файловые источники монтируются в контейнеры для чтения.

| `sources.<id>.type` | Что подготовить | Поддерживаемая выдача |
| --- | --- | --- |
| `geojson` | GeoJSON `FeatureCollection` с хотя бы одним объектом и уникальными строковыми ID. | Features через pygeoapi |
| `geopackage`, `shapefile` | Векторный файл, имя слоя `layer` и поле ID `id_field`. | Features через pygeoapi |
| `geoparquet` | Один векторный файл Parquet с метаданными GeoParquet и полем `id_field`. | Features через pygeoapi |
| `postgis` | Таблица или представление, поле ID и поле геометрии. Подключение задаётся на экземпляре. | Features, MVT, OGC API — Tiles |
| `geotiff`, `cog` | Геопривязанный растр `.tif` или `.tiff` и код его системы координат. | Maps через pygeoapi |
| `mbtiles`, `pmtiles` | Локальный архив растровых тайлов или MVT в Web Mercator. Тип тайлов определяется по каталогу Martin. | Прямые веб-тайлы через Martin |
| `parquet` | Снимок H3 с одной строкой для каждой ячейки и числовыми показателями. | DGGS через pydggsapi |

1. Подготовьте данные и доступ к файлу или БД. Проверьте ID объектов и систему координат.
2. Добавьте строку или блок под `sources` в полном YAML. Для PostGIS укажите схему и отношение в источнике, а хост, БД, роль и файл пароля — в `providers.<id>.postgis`.
3. Укажите этот ID в `publications.<id>.source`. Добавьте или выберите подходящий экземпляр сервис-провайдера. Пример для каждого протокола есть в [главе о публикациях](#публикация-данных).
4. Выполните `config validate` и `config plan`. Проверьте план и примените его. Только запрос к публикации подтверждает, что клиент получил нужные данные.

### Файлы и системы координат Features

- Для GeoJSON используйте строковый `id` объекта. Платформа допускает один источник `geojson` на полный YAML.
- Для GeoPackage укажите точное имя слоя. Для Shapefile укажите имя слоя без расширения. Положите рядом файлы с тем же базовым именем и расширениями `.shx`, `.dbf`, `.prj` и `.cpg` при наличии.
- Для GeoPackage, Shapefile и GeoParquet укажите `id_field` с уникальными непустыми строками или целыми числами. Для GeoParquet подготовьте метаданные `geo`, первичную геометрию WKB и плоские рёбра. При отсутствии `crs` в метаданных GeoParquet используется CRS84.
- Встроенный pygeoapi для GeoParquet собирается с PyArrow 23.0.1. В дополнительном образе для GeoParquet нужен совместимый PyArrow, а для GeoPackage и Shapefile — Fiona.

Пример записей в разделе `sources`. Добавьте нужную запись к остальным источникам вашего YAML.

```yaml
sources:
  places-package: {type: geopackage, path: data/places.gpkg, layer: places, id_field: place_id}
  places-shape: {type: shapefile, path: data/places.shp, layer: places, id_field: place_id}
  places-parquet: {type: geoparquet, path: data/places.parquet, id_field: place_id}
```

`extent` — охват публикации в CRS84. Порядок координат — запад, юг, восток, север. Для Features шлюз описывает поддерживаемые CRS в поле `crs` коллекции. CRS84 по умолчанию использует порядок долгота, широта. Можно указать `crs` в конфигурации публикации, а в запросе передать URI из описания коллекции через `crs` для ответа и `bbox-crs` для окна отбора. Например, при EPSG:4326 порядок широта, долгота. Ответ содержит `Content-Crs`.

Для GeoJSON и PostGIS поддерживаются CRS84, EPSG:4326 и EPSG:3857. Для GeoPackage, Shapefile и GeoParquet можно указать поддерживаемые двухмерные CRS. Применение плана проверит преобразование координат. Для окна через антимеридиан PostGIS требует два запроса с каждой стороны 180°. Объедините результаты по ID объекта. Для GeoPackage, Shapefile и GeoParquet можно передать окно CRS84 с переходом от положительной долготы к отрицательной.

### Подготовить данные PostGIS

1. Попросите администратора БД подготовить таблицу или представление с непустым стабильным уникальным ID и типизированной колонкой геометрии с объявленным SRID. Для примера Features используйте SRID 4326. Для запросов `datetime` подготовьте колонку времени, предпочтительно `timestamptz`.
2. Выдайте выделенной роли чтения `USAGE` на схему и `SELECT` на источник. Проверьте, что хост и порт БД доступны из контейнера. Запишите пароль в UTF-8 одной строкой в файл, доступный владельцу развёртывания.
3. Заполните `schema`, `relation`, `id_field`, `geometry_field` и `max_lag_seconds`. Последнее поле описывает задержку подготовки данных в БД. Допустимая задержка публикации `freshness.max_delay_seconds` по умолчанию составляет 60 секунд. Значение источника должно укладываться в этот предел. Чтобы новые запросы видели изменения после COMMIT при нулевой задержке, укажите 0 в источнике и публикации.
4. Для файлов и PostGIS используйте разные экземпляры. Для разных подключений к PostGIS задайте отдельные экземпляры. Порт по умолчанию — 5432. Для смены пароля подготовьте новый файл, поменяйте `password_file` и примените план. Прежний пароль должен работать, пока нужен откат к нему.

### Обновить файловый источник

Подготовьте снимок или архив под новым именем и поменяйте `sources.<id>.path`. Сохраните прежний файл и связанные части набора по прежним путям, пока нужен откат. Выполните `validate → plan → apply`, затем проверьте новый ответ по прежнему URL. Сохранение ID публикации поддерживается для новой версии того же источника и протокола. Перенос на другое отношение или подключение PostGIS считается сменой источника для ID публикации.

## Управление сервис-провайдерами

| Адаптер | Когда использовать |
| --- | --- |
| `pygeoapi` | Features, Maps и внешнее API Tiles. Для Tiles нужен отдельный Martin для тайлов. |
| `martin` | Векторные тайлы из PostGIS, прямые тайлы из MBTiles/PMTiles и формирование тайлов для Tiles. |
| `pydggsapi` | Доступ к снимку H3 Parquet через DGGS. |

Запись `type: pygeoapi` без `image` использует встроенный экземпляр платформы для Features. Допустим один встроенный экземпляр. Для остальных укажите `image` и `api` либо используйте `provider add`. Выбирайте явный тег версии образа или digest. Для управляемого экземпляра `api.port` задаёт порт внутри контейнера, `base_path` — внутренний путь, а `readiness` — проверку готовности относительно внутреннего пути. Для pyDGGSAPI с вложенными адресами укажите `base_path: /`. Адаптер настроит внутренний путь по публичному префиксу.

### Добавить экземпляр

Для нового экземпляра в `providers` рекомендуется ID без префикса `provider-`, например `pygeoapi`, `martin` или `pydggsapi`. Для дополнительного экземпляра укажите назначение, например `pygeoapi-archive`. В публикации укажите ID экземпляра в поле `provider`. В публикации Tiles поле `tile_provider` указывает на экземпляр Martin, который формирует тайлы.

Для управляемого экземпляра GIS Platform добавляет `provider-` к короткому ID при формировании имени сервиса Compose. Для ID `pygeoapi` имя сервиса — `provider-pygeoapi`, а имя контейнера в проекте `gis-platform` — `gis-platform-provider-pygeoapi-1`. Если ID уже начинается с `provider-`, платформа обычно использует его целиком. Если в одном проекте есть два управляемых экземпляра с ID `pygeoapi` и `provider-pygeoapi`, второй получает имя сервиса `provider-provider-pygeoapi`. Чтобы обновить имена в действующем проекте, выполните `config plan` и `config apply` с текущим YAML.

В `api.protocols` перечислите протоколы экземпляра. Для каждого из них шлюз создаст корень `/<публичный-префикс>/<протокол>`. По умолчанию публичный префикс совпадает с ID в YAML. Например, ID `pygeoapi` с `api.protocols: [features]` даёт `/pygeoapi/features`. Чтобы задать другой префикс, укажите уникальное значение `api.public_prefix` одним сегментом без `/`.

В примере для ID `provider-pygeoapi` задан `api.public_prefix: pygeoapi`. Один контейнер обслуживает `/pygeoapi/features`, `/pygeoapi/maps` и `/pygeoapi/tiles`. Martin формирует тайлы для Tiles через `tile_provider` и может отдельно публиковать `/martin/mvt`. pyDGGSAPI обслуживает `/pydggsapi/dggs`. [Пример с несколькими протоколами](examples/provider-protocols.yaml)

Для OGC API у каждого корня свои `/collections`, `/openapi` и `/conformance`. Для прямых веб-тайлов вложенный корень Martin даёт `/catalog`, `/openapi` и `/conformance`, а TileJSON находится по адресу `/<префикс>/mvt/<ID>`. Шлюз показывает клиенту метаданные и дополнительные возможности доступных ему публикаций.

Можно дописать запись в `providers` полного YAML и применить её вместе с публикацией через `config plan` и `config apply`. Это удобнее, когда экземпляр и публикация добавляются одновременно.

Для отдельного добавления подготовьте [файл интеграции](examples/provider-features.yaml). Пример ниже использует собранный CLI и переменную `platform`, указывающую на полную конфигурацию. Сначала примените черновые изменения в полном YAML или подготовьте копию из действующей версии. Для нового экземпляра выберите свободный ID.

```sh
node dist/cli.js provider add pygeoapi-archive geopython/pygeoapi:0.24.0 \
  examples/provider-features.yaml "$platform"
```

Команда сама создаёт и применяет план, а затем записывает секцию `providers.pygeoapi-archive` с digest в полный YAML. В Compose появляется сервис `provider-pygeoapi-archive`. Martin запускается, когда на него ссылается публикация через `provider` либо `tile_provider`. У некоторых адаптеров доступны `environment` и `volumes`. Имена томов привязаны к ID экземпляра.

### Перейти с плоских URL на вложенные

1. Действующий `api.protocol` и `api.public_root` сохраняют плоские адреса. Чтобы перейти, замените оба поля на `api.protocols` и при необходимости задайте `api.public_prefix`. Для встроенного pygeoapi добавьте управляемый экземпляр с образом и переведите публикации на него через поле `provider`.
2. Сохраните ID, источник и протокол каждой публикации. Для Martin с PostGIS сохраните то же подключение, в том числе для `tile_provider`. Используйте относительные ссылки в файлах стилей MapLibre или обновите их на вложенный URL.
3. Выполните `validate → plan → apply`. Сверьте `previousUrl`, `newUrl` и `personalGrants` в `publications` плана. После применения обновите адреса в клиентах. Старые маршруты перенесённых публикаций возвращают 404. Публикации других экземпляров под прежним общим корнем остаются доступны по своим URL.
4. Если нужно вернуть прежние адреса, спланируйте и примените откат к предыдущей подтверждённой версии. Откат конфигурации сохраняет актуальные персональные разрешения.

### Обновить или удалить экземпляр

```sh
node dist/cli.js provider update pygeoapi-archive "$platform"
node dist/cli.js provider update pygeoapi-archive "$platform" geopython/pygeoapi:0.24.0
node dist/cli.js provider remove pygeoapi-archive "$platform"
```

Выберите одну нужную команду. `provider update` загружает образ из указанного аргумента или заново запрашивает текущую ссылку. CLI сохраняет подтверждённый digest в YAML и версии. При сбое проверки действующая версия возвращается с прежним образом. Для встроенного экземпляра образ определяется версией платформы.

`provider remove` покажет ID публикаций, если экземпляр ещё используется. Сначала перенесите или снимите эти публикации отдельным планом. После успешного удаления запись и контейнер исчезнут. Источники и данные именованных томов остаются на диске.

## Публикация данных

Во всех рецептах выполняйте команды из каталога приложения с параметрами своего проекта. `platform` указывает на ваш полный YAML, `public_url` — внешний адрес из плана, например `https://gis.example.org`. Если пример YAML содержит только один сценарий, возьмите из него нужные записи `sources`, `providers` и `publications` и добавьте их к действующим разделам. При копировании полного примера на другое место исправьте относительные пути.

Для каждого нового рецепта сначала проверьте входные данные, затем выполните общий цикл.

```sh
node dist/cli.js config validate "$platform"
node dist/cli.js config plan "$platform"
read -r -p 'ID проверенного плана: ' plan_id
node dist/cli.js config apply "$plan_id"
```

В плане проверьте добавляемые, меняемые и удаляемые публикации, внешний адрес и последствия для персональных разрешений. Подтвердите готовность по ID через `doctor --publication`, затем выполните соответствующий запрос через Caddy.

### Объекты через OGC API — Features

1. Для GeoJSON используйте [готовый пример](examples/features.yaml). Для GeoPackage, Shapefile или GeoParquet добавьте [файловый источник](#файлы-и-системы-координат-features) и укажите его ID в `publications.places.source`.
2. Выберите экземпляр pygeoapi для Features, укажите `protocol: features`, режим доступа и охват. Ключ `places` становится ID коллекции. Примените YAML.
3. Проверьте каталог, OpenAPI и чтение объектов. `limit` ограничивает число объектов, `bbox` задаёт окно в координатах CRS84.

```sh
curl -fsS "$public_url/features/collections?f=json"
curl -fsS "$public_url/features/openapi?f=json"
curl -fsS "$public_url/features/collections/places/items?f=json&limit=1"
curl -fsS "$public_url/features/collections/places/items?f=json&bbox=37,55,38,56"
```

| Источник Features | Пространственный фильтр | Временной фильтр | CQL2 |
| --- | --- | --- | --- |
| GeoJSON, GeoPackage, Shapefile | `bbox` | — | — |
| GeoParquet | `bbox` с точным пересечением геометрии | `datetime` при настроенном `time_field` | — |
| PostGIS | `bbox` | `datetime` при настроенном `time_field` | Text и JSON |

Для большого набора данных с фильтрацией подготовьте подходящее представление в PostGIS. Файловые варианты могут читать объекты слоя для проверки точного пересечения и подсчёта результатов.

### Динамическая публикация Features из PostGIS

1. [Подготовьте PostGIS](#подготовить-данные-postgis) и файл с паролем. Ниже дополнения к платформенному YAML. В этом примере pygeoapi встроен. Если встроенный экземпляр уже занят файловыми источниками, создайте управляемый экземпляр pygeoapi для Features с `image` и `api`.
2. Замените имена схемы, отношения, полей и сервера своими. Если источник не содержит поля времени, опустите `time_field`. Сохраните `extent` в соответствующем данным охвате.

```yaml
sources:
  observations:
    type: postgis
    schema: gis
    relation: published_observations
    id_field: id
    geometry_field: geom
    max_lag_seconds: 0
providers:
  live-features:
    type: pygeoapi
    postgis:
      host: postgis.example.org
      database: gis
      user: features_reader
      password_file: secrets/observations-password
publications:
  observations:
    source: observations
    provider: live-features
    protocol: features
    access: public
    title: Observations
    description: Observations published from PostGIS.
    extent: [37, 55, 40, 58]
    time_field: observed_at
    freshness:
      max_delay_seconds: 0
```

3. Примените полный YAML. Проверьте выдачу данных и, если нужно, временной фильтр. `datetime` принимает момент времени, интервал и открытые границы `..`.

```sh
curl -fsS "$public_url/features/collections/observations/items?f=json&limit=1"
curl -fsS --get "$public_url/features/collections/observations/items" \
  --data-urlencode 'f=json' \
  --data-urlencode 'datetime=2026-01-01T00:00:00Z/..'
```

Для CQL2 Text передайте `filter` и `filter-lang=cql2-text`. Для CQL2 JSON отправьте POST на `/features/collections/observations/items?f=json` с `Content-Type: application/json` и выражением в теле запроса. При переходе по ссылке на следующую страницу повторите POST с тем же выражением. Параметры перечислены в `/features/openapi?f=json`.

### Растровая публикация Maps

1. Подготовьте геопривязанный GeoTIFF или COG. В [примере YAML](examples/maps.yaml) укажите путь, `type: geotiff` либо `type: cog`, EPSG исходного растра и охват. Если `epsg` опущен, используется 4326. Охват должен иметь ненулевую ширину и высоту.
2. Используйте pygeoapi для `protocol: maps` под `/maps`. При применении CLI проверит формат, геопривязку, CRS и пробное получение PNG.
3. Запросите карту через Caddy. Меняйте `bbox`, `width` и `height` под свой участок.

```sh
curl -fsS "$public_url/maps/collections/terrain/map?bbox=36,54,40,58&width=800&height=600&f=png" -o terrain.png
curl -fsS "$public_url/maps/openapi?f=json"
```

Размеры задаются целыми числами от 1 до 2048 пикселей, по умолчанию 500 × 300. Без `bbox` провайдер использует мировой охват. Ошибочные параметры получают HTTP 400 с кодом `InvalidParameterValue`. Фактический охват и CRS возвращаются в `Content-Bbox` и `Content-Crs`. Режим доступа применяется и к метаданным, и к изображению.

### Векторные веб-тайлы MVT через Martin

1. Подготовьте [источник PostGIS](#подготовить-данные-postgis). В [примере YAML](examples/mvt.yaml) укажите подключение к БД на экземпляре Martin, данные источника и охват.
2. Укажите `protocol: mvt`. В `mvt_properties` перечислите дополнительные поля PostGIS для выдачи в тайлах. Поле `id_field` включается в тайлы. Используйте в комментариях к таблице только метаданные MVT. При проверке TileJSON шлюз отклоняет ссылки `data` и `grids`.
3. Примените план и запросите TileJSON. Ссылки указывают на тайлы XYZ в Web Mercator через Caddy.

```sh
curl -fsS "$public_url/mvt/observations"
```

В MapLibre укажите этот URL для векторного источника, а `observations` — как `source-layer`. При использовании другого веб-сайта добавьте его origin в `cors.allowed_origins`. Для защищённых публикаций передавайте Bearer-токен запросам этой публикации, её TileJSON, тайлам и ресурсам.

Для готовых векторных тайлов укажите источник `type: mbtiles` или `type: pmtiles` с путём к архиву и экземпляр Martin без подключения к PostGIS. Публикация использует `protocol: mvt`. В MapLibre укажите ID слоя из `vector_layers` в TileJSON как `source-layer`. Его задаёт архив.

#### Стиль и связанные ресурсы MapLibre

В записи публикации `mvt` задайте `maplibre.style_file` для JSON-стиля версии 8. В `resources` ключ — путь ресурса внутри публикации, значение — путь к файлу на диске.

```yaml
cors:
  allowed_origins: ['https://maps.example.org']
publications:
  observations:
    # Добавьте этот блок к остальным полям публикации.
    maplibre:
      style_file: observations-style.json
      resources:
        markers.json: markers.json
        markers.png: markers.png
        markers@2x.json: markers@2x.json
        markers@2x.png: markers@2x.png
        labels.geojson: labels.geojson
        fonts/MapSans/0-255.pbf: fonts/MapSans/0-255.pbf
```

В стиле используйте `"url": "./"` для TileJSON той же публикации, `"sprite": "./resources/markers"` для атласа, `"data": "./resources/labels.geojson"` для вспомогательного GeoJSON и `"glyphs": "./resources/fonts/{fontstack}/{range}.pbf"` для шрифтов. Укажите `"text-font": ["MapSans"]` в слое с подписями. Включайте JSON и PNG для каждого разрешения атласа, которое запрашивает клиент.

CLI сохраняет стиль и ресурсы в план и преобразует ссылки в URL шлюза. После изменений подготовьте новый план. При откате выдаются сохранённые файлы выбранной версии. Стиль в примере открывается по `/mvt/observations/style.json`.

```js
// token содержит токен пользователя, полученный вне кода приложения.
const publication = 'https://gis.example.org/mvt/observations';
const map = new maplibregl.Map({
  container: 'map',
  style: publication + '/style.json',
  transformRequest: (url) =>
    url === publication || url.startsWith(publication + '/')
      ? { url, headers: { Authorization: 'Bearer ' + token } }
      : { url },
});
```

### Готовые растровые веб-тайлы через Martin

1. Подготовьте MBTiles или PMTiles с готовыми тайлами Web Mercator. В [примере YAML](examples/raster-tiles.yaml) поменяйте пути и охват. Для архивов используйте экземпляр Martin без `postgis`.
2. В полном YAML `protocol: mvt` выбирает прямые маршруты Martin и для растрового архива. В клиенте тип источника и слоя будет `raster`. Примените план и проверьте `curl -fsS "$public_url/mvt/aerial"`. TileJSON должен содержать шаблон URL шлюза `/mvt/aerial/{z}/{x}/{y}`.
3. В MapLibre задайте `{type: 'raster', url: 'https://gis.example.org/mvt/aerial', tileSize: 256}` и подставьте реальный размер тайла архива. Проверьте, что клиент получил сами тайлы и отобразил слой.

### Векторные тайлы через OGC API — Tiles

1. В [примере YAML](examples/tiles.yaml) укажите свой источник PostGIS и подключение Martin. `provider` указывает на pygeoapi с корнем `/tiles`, а `tile_provider` — на отдельный экземпляр Martin, который строит тайлы.
2. Примените конфигурацию и откройте коллекцию. Перейдите по ссылкам к списку наборов, набору WebMercatorQuad и определению матрицы. В шаблоне URL тайла подставьте номер матрицы, строки и столбца.

```sh
curl -fsS "$public_url/tiles/collections/observations?f=json"
curl -fsS "$public_url/tiles/openapi?f=json"
```

3. Для MapLibre используйте ссылку TileJSON из описания набора и ID публикации как `source-layer`. Хотите ещё прямой URL `/mvt` для тех же данных — создайте отдельную публикацию MVT со своим ID и правами. При недоступном Martin или PostGIS запрос за тайлом может вернуть HTTP 503.

### Ячейки H3 из PostGIS

Ячейки H3 можно выдать обычными полигонами через Features или MVT. Подготовьте представление с границами и показателями и укажите его в [примере для двух протоколов](examples/h3-postgis.yaml). Стабильный `feature_id` идентифицирует строку наблюдения, `h3_id` — ячейку, которая может повторяться.

Если в БД хранится `cell` типа `h3index` и доступны расширения H3, DBA может адаптировать следующий запрос. Он разрезает границу ячейки по 180° и приводит все геометрии к `MultiPolygon` с SRID 4326.

```sql
CREATE VIEW h3_data.published_observations AS
SELECT observation_id::text AS feature_id,
       cell::text AS h3_id,
       h3_get_resolution(cell) AS resolution,
       observed_at,
       measurement,
       ST_Multi(h3_cell_to_boundary_geometry(cell))::geometry(MultiPolygon, 4326) AS geom
FROM h3_data.observations;

GRANT USAGE ON SCHEMA h3_data TO h3_reader;
GRANT SELECT ON h3_data.published_observations TO h3_reader;
```

Проверьте ID и геометрию. Примените план и откройте `/features/collections/h3-observations/items?f=json&limit=1` и `/mvt/h3-observation-tiles`. Features сохраняет границу объекта целиком. Martin режет геометрию по области тайла с буфером. Отсутствующее значение приходит как `null` в Features и опускается в MVT. Нулевое значение сохраняется в обоих.

### Ячейки H3 из Parquet через DGGS

1. Подготовьте Parquet с одной строкой на уникальный строковый ID H3 в нижнем регистре. Все ячейки имеют одно разрешение. Файл содержит ровно столбец `id_field` и перечисленные в `properties` столбцы показателей. Для целых значений используйте `BIGINT`, для вещественных — `DOUBLE`. Границы строятся из ID.
2. Укажите путь, разрешение и охват в [примере YAML](examples/h3-parquet.yaml). Используйте закреплённый pydggsapi 0.4.0 для `linux/amd64`, `protocol: dggs`, оба пути `/dggs` и `readiness: /conformance`. При инициализации DuckDB загружает расширение `httpfs`.
3. Примените конфигурацию. Проверьте каталог, затем получите зоны и показатели. Для запросов к зонам укажите `Accept: */*`. Выберите реальный ID ячейки из свойства `zoneId` в ответе GeoJSON.

```sh
curl -fsS "$public_url/dggs/collections"
zones="$public_url/dggs/collections/h3-measurements/dggs/h3/zones"
curl -fsS -H 'Accept: */*' \
  "$zones?bbox=12.28,45.41,12.36,45.47&zone-level=7&compact-zones=false&f=geojson&geometry=zone-region"
read -r -p 'ID ячейки H3: ' h3_id
curl -fsS -H 'Accept: */*' "$zones/$h3_id"
curl -fsS -H 'Accept: */*' "$zones/$h3_id/data?zone-depth=0"
```

Swagger доступен на `/dggs/docs`, OpenAPI — на `/dggs/openapi`. Ответ `/data` сохраняет ноль и `null`. Для отсутствующей строки возвращается HTTP 204. Точные целые гарантированы в диапазоне от −9007199254740991 до 9007199254740991, дальше pydggsapi может округлить `BIGINT`.

`limit` ограничивает число ячеек-кандидатов до их сопоставления со строками Parquet. По умолчанию это 1000. Для широкого охвата увеличьте лимит в допустимых пределах или делите `bbox` на небольшие окна и объединяйте результаты по `zoneId`. Для уровня 7 проверено окно `11.8,45.0,12.9,45.9` с `limit=10000`. [Проверки DGGS](tests/README.md#ячейки-h3-из-parquet)

Для просмотра в QGIS откройте URL запроса зон с `f=geojson` как векторный слой по HTTP. Слой содержит геометрию и ID ячеек. Показатели можно запросить отдельно по `/data`.

### Снять публикацию и вернуть её

1. Уберите запись публикации из полного YAML. Перед применением найдите её в `removed`, проверьте `routesToClose` и последствия `personalGrants: delete`. После успешного удаления URL возвращает 404. Источник может продолжать использоваться другими публикациями.
2. Для возврата добавьте прежнюю публикацию обратно либо подготовьте [откат конфигурации](#обновление-и-откат). Прежний ID зарезервирован за тем же источником и протоколом. Для других данных с другой идентичностью или другого протокола выберите новый ID.
3. В случае закрытой публикации после возврата выдайте нужные персональные разрешения заново. Откат YAML использует текущее состояние БД доступа. Например, откат после снятия закрытого слоя возвращает маршрут, но разрешение на него нужно восстановить отдельной командой.

## Учётные записи и доступ

| Роль | Для чего нужна |
| --- | --- |
| Владелец развёртывания | Имеет доступ к хосту, Docker, файлам и секретам. Применяет YAML, обслуживает контейнеры и делает резервные копии. |
| Администратор платформы | Активная учётная запись с подтверждённым email из `auth.administrator_emails`. Имеет доступ ко всем публикациям. |
| Оператор CLI | Локальная учётная запись с клиентским сертификатом. Получает отдельные права на диагностику, чтение пользователей или изменение доступа. |

### Включить регистрацию и почту

1. Создайте два независимых файла секретов для нового развёртывания. Пример ниже предполагает, что YAML расположен в `/srv/gis`. Сохраните существующие секреты при обновлениях.

```sh
install -d -m 700 /srv/gis/secrets
(
  umask 077
  set -C
  openssl rand -hex 32 > /srv/gis/secrets/auth-secret
  openssl rand -hex 32 > /srv/gis/secrets/postgres-password
)
```

2. Добавьте в YAML настройки. Для локальной пробы используйте `development` и Mailpit. При необходимости поменяйте порт 8025.

```yaml
auth:
  mode: development
  secret_file: secrets/auth-secret
  postgres_password_file: secrets/postgres-password
  mailpit_port: 8025
  administrator_emails: [administrator@example.org]
```

3. На рабочем сервере используйте `mode: production`. Удалите поле `mailpit_port`, добавьте SMTP-реле. Сохраните `username` и `password_file` вместе для реле с аутентификацией. Для реле без аутентификации опустите оба. Запишите пароль SMTP в отдельный закрытый файл. На порту 587 обычно используется STARTTLS. Для TLS при подключении задайте `secure: true`.

```yaml
auth:
  mode: production
  secret_file: secrets/auth-secret
  postgres_password_file: secrets/postgres-password
  administrator_emails: [administrator@example.org]
  smtp:
    host: relay.example.org
    port: 587
    from: GIS Platform <accounts@example.org>
    username: gis-platform
    password_file: secrets/smtp-password
```

4. Примените план. Откройте `/account/register` и создайте тестовую учётную запись. Подтвердите email из письма. Для Mailpit письма видны на `http://localhost:8025` на хосте. Проверьте вход на `/account/login` и доступ к `/account/profile`. Внешний URL определяет ссылки в письмах и адрес веб-сеанса.

### Настройка закрытых публикаций и локального CLI

| `access` | Кто получает данные |
| --- | --- |
| `public` | Любой клиент, в том числе без входа. |
| `registered` | Активная учётная запись с подтверждённым email. |
| `private` | Активная учётная запись с подтверждённым email и персональным разрешением. Администратор платформы имеет доступ по своей роли. |

Укажите режим в `publications.<id>.access` и примените план. Для `registered` и `private` требуется `auth`.

Для административных команд настройте локальный API с проверкой обоих сертификатов. Выделите отдельный УЦ. Выпустите серверный сертификат для `serverAuth` с `IP:127.0.0.1` в SAN. Для каждого оператора выпустите сертификат с `clientAuth` и `CN`, совпадающим с ключом в `operators`. Разместите серверные файлы относительно YAML. Защитите закрытые ключи правами ОС, храните ключ УЦ отдельно, а каждому оператору предоставьте его клиентский ключ.

Добавьте следующий блок **внутрь** настроенного `auth`.

```yaml
  cli:
    port: 8444
    ca_file: secrets/pki/cli-ca.pem
    cert_file: secrets/pki/cli-server.pem
    key_file: secrets/pki/cli-server-key.pem
    operators:
      operator: [diagnostics, users-read, access-write]
      monitor: [diagnostics]
```

После применения API слушает на `127.0.0.1:8444`. Для вызова от имени оператора укажите **клиентскую** пару и УЦ. Пути ниже замените выданными оператору.

```sh
export GIS_ADMIN_PORT=8444
export GIS_ADMIN_CA_FILE=/srv/gis/secrets/pki/cli-ca.pem
export GIS_ADMIN_CERT_FILE=/etc/gis-operator/operator.pem
export GIS_ADMIN_KEY_FILE=/etc/gis-operator/operator-key.pem
node dist/cli.js status --json
node dist/cli.js users list --json
```

`diagnostics` открывает `status` и `doctor`. `users-read` открывает `users list` и `tokens list`. `access-write` разрешает блокировку, разблокировку, выдачу и отзыв разрешений и отзыв токенов. Чтобы прекратить доступ оператора к CLI, уберите его из `operators` и примените план.

### Выдать и проверить доступ

Для примера замените `places-private` ID своей закрытой публикации и укажите email зарегистрированного пользователя.

```sh
node dist/cli.js users list --json
node dist/cli.js access grant places-private --email reader@example.org
node dist/cli.js users list --json
```

В `data.users` сверьте `email`, статус и список `publications`. Статус `active` означает, что пользователь может войти. При `unverified` подтвердите email. При `blocked` доступ от имени пользователя закрыт. `anonymous: true` обозначает доступ к публичной публикации без действующей идентификации.

Пользователь входит через веб-интерфейс и создаёт личный токен на `/account/tokens`. Секрет показывается один раз. Клиент передаёт его в `Authorization: Bearer <токен>`. Токен использует текущие права пользователя. Допущенное обращение продлевает срок токена на 90 дней. Смена или восстановление пароля отзывает прежние токены и сеансы. [Подключение QGIS с токеном](README.md#персональный-токен-для-qgis)

В следующем блоке выберите нужную операцию. `--user-id` можно использовать вместо `--email`. Указанные ID пользователя и токена получите из вывода соответствующих команд list.

```sh
node dist/cli.js access revoke places-private --email reader@example.org
node dist/cli.js users block --email reader@example.org
node dist/cli.js users unblock --email reader@example.org
node dist/cli.js tokens list --email reader@example.org --json
node dist/cli.js tokens revoke token-17 --email reader@example.org
```

Блокировка и отзывы действуют со следующего запроса. Проверьте отказ прежнему токену или доступ после разблокировки разрешённому пользователю. Для диагностики изменения найдите событие `access.change` в журнале компонента доступа.

## Обновление и откат

### Перед изменениями

1. Найдите текущий проект, проверьте `status --json`, `doctor --json` и внешний URL. Запишите `currentVersion`, коммит кода и расположение исходного YAML, чтобы знать, к какой версии возвращаться.
2. Сохраните копию `platform.yaml` и файлы, на которые ссылается действующая конфигурация. Для развёртывания с `auth` создайте копию `pre-update` и дождитесь подтверждения. Сохраните прежнее имя проекта, `GIS_STATE_DIR`, привязки интерфейсов, порты, файлы секретов и тома.
3. По возможности проверьте новую версию в отдельном проекте со свободными портами и копией данных. Для действующего сервера выделите время на переключение и проверку. Во время `apply` затронутые маршруты могут временно возвращать 503.

### Обновить конфигурацию или образ

- Для изменений YAML или снимка данных выполните `validate → plan → apply`. Проверьте текущую базовую версию плана, внешний адрес, списки изменённых и удаляемых публикаций и сохранение прав.
- Для обновления образа управляемого экземпляра используйте `provider update <id> <platform.yaml> [image]`. Ссылка на образ без изменений сохраняет закреплённый digest при обычном планировании. Команда `provider update` явно запрашивает и проверяет образ.
- Для замены TLS-сертификата следуйте [процедуре HTTPS](#внешний-http-и-https).

При изменении конфигурации CLI действует по шагам.

1. Сверяет базовую версию плана с действующей и проверяет, что исходные файлы и сертификаты соответствуют подготовленному плану. Одновременно применяется один план.
2. Проверяет изменённые источники и подготовленные конфиги. Нарушение на этапе проверки оставляет действующую версию в работе.
3. Закрывает затронутые маршруты на время переключения, передаёт новую конфигурацию Compose и проверяет готовность контейнеров и маршрутов.
4. Подтверждает версию и открывает маршруты. При сбое пытается восстановить прежнюю конфигурацию. Если восстановление не завершилось, затронутые маршруты остаются закрытыми.

### Обновить версию платформы

1. Подготовьте отдельную копию кода выбранной версии и проверьте требования этой версии. Из её каталога выполните `npm ci`, `npm run build` и `git rev-parse HEAD`. Оставьте прежнюю копию кода и сделанную перед обновлением резервную копию. Убедитесь, что исходные пути данных, секретов и редактируемого YAML по-прежнему доступны.
2. Укажите прежнее имя проекта и каталог состояния. Внесите необходимые изменения формата в рабочую копию YAML в том же каталоге. Запустите в новой версии CLI `config validate` и `config plan`. Проверьте план и примените его. Если CLI переключает версию, он подготавливает конфиги и запускает нужные сервисы из выбранной версии кода.
3. При `NO_CHANGE` CLI принял ту же конфигурацию без пересборки. Если изменился только CLI, используйте новый `dist/cli.js`. Чтобы запустить обновлённый стек через CLI, внесите уместное изменение в YAML, например уточните описание действующей публикации. Снова постройте план. Проверьте, что URL, права и списки удалений совпадают с ожидаемыми, и примените план из новой версии кода. Для совместимого обновления одного контейнера `access` можно использовать рецепт ниже. Для выпуска со специальным порядком развёртывания следуйте инструкции этого выпуска.
4. Проверьте `status`, `doctor`, публичные запросы, вход и закрытую публикацию с контрольным пользователем. Сохраните номер релиза, коммит и ID применённой конфигурации.

Пример пересборки только `access` на хосте, где PostgreSQL уже работает. Выполните в каталоге новой версии проекта. Подставьте ID **действующей** подтверждённой версии из `status --json`, а пути к секретам возьмите из применённого YAML. Дополнения `compose.smtp.json` и `compose.admin.json` берутся из этой же версии.

```sh
read -r -p 'Действующая версия config из status: ' current_version
export GIS_REVISION_DIR="$GIS_STATE_DIR/plans/$current_version"
export GIS_AUTH_SECRET_FILE=/srv/gis/secrets/auth-secret
export GIS_POSTGRES_PASSWORD_FILE=/srv/gis/secrets/postgres-password
access_files=(-f compose.yaml -f compose.auth.yaml)
if [ -f "$GIS_REVISION_DIR/compose.smtp.json" ]; then
  access_files+=(-f "$GIS_REVISION_DIR/compose.smtp.json")
fi
if [ -f "$GIS_REVISION_DIR/compose.admin.json" ]; then
  access_files+=(-f "$GIS_REVISION_DIR/compose.admin.json")
fi
docker compose -p "$COMPOSE_PROJECT_NAME" "${access_files[@]}" \
  up -d --no-deps --build --wait --wait-timeout 65 access
node dist/cli.js doctor --json
```

`--no-deps` ограничивает операцию сервисом `access`. Сохраняйте текущую БД и используйте этот рецепт только для совместимого обновления компонента доступа. Изменения Caddy, SMTP, TLS, провайдеров и миграции, которые требуют других действий, проводите по условиям соответствующего выпуска.

### Вернуть прежнюю конфигурацию

Скопируйте подходящий ID подтверждённой конфигурации, например `previousVersion` из `status --json`. Убедитесь, что связанные источники по прежним путям существуют и пригодны для чтения. Для PostGIS проверьте прежнее подключение, а для старых версий TLS — комплект по сохранённым путям.

```sh
node dist/cli.js status --json
read -r -p 'ID версии для отката: ' previous_version
node dist/cli.js config plan --rollback-to "$previous_version"
read -r -p 'ID проверенного плана отката: ' rollback_plan
node dist/cli.js config apply "$rollback_plan"
node dist/cli.js doctor --json
```

Список изменений в плане отката проверяется так же, как при обновлении. После отката синхронизируйте редактируемый YAML с подтверждённой версией. Подтверждённый снимок `platform.yaml` хранится в `$GIS_STATE_DIR/plans/<id>/`. Разрешайте его относительные пути от исходного положения YAML. Проверьте внешние маршруты и нужные разрешения.

Откат конфигурации использует текущую БД доступа и выбранную сохранённую конфигурацию. Для возврата версии кода используйте сохранённую копию релиза и отдельно учтите совместимость БД. Для восстановления учётных записей после потери БД используйте проверенный резервный снимок.

## Резервное копирование и восстановление

### Что входит в резервную копию

Копирование выполняет владелец развёртывания из каталога версии GIS Platform с настроенным `auth` и работающим PostgreSQL платформы. CLI создаёт согласованный дамп БД, включает историю подтверждённых конфигураций и архивы TLS, а также используемые файловые источники, секреты и конфиги действующей и предыдущей версий. Клиентские ключи операторов хранят их владельцы.

| Что сохранить дополнительно | Как |
| --- | --- |
| Редактируемый YAML, исходные стили и ресурсы, оригиналы TLS, файлы окружения и сведения о версии | Передайте реальные пути дополнительными аргументами `backup create`. Эти пути должны быть вне служебного каталога и не содержать его. Секреты restic храните отдельно от входов копирования. |
| Код релиза и возможность собрать его снова | Сохраните доступ к точной версии кода и запишите коммит. |
| Внешний PostGIS и пользовательские тома сторонних сервис-провайдеров | Настройте отдельные копии. В резервный комплект платформы входят ссылки на источник и подключение. |

### Настроить репозиторий и ежедневное копирование

1. Установите restic версии 0.20 или новее. Подготовьте отдельный репозиторий rest-server по HTTPS на другом хосте и доступ с учётной записью этого развёртывания. Храните пароль restic отдельно от резервируемых файлов и репозитория.
2. Подготовьте закрытый файл окружения, например `/etc/gis-operator/backup.env`. При необходимости укажите закрытые значения `RESTIC_REST_USERNAME` и `RESTIC_REST_PASSWORD` в этом файле. Используйте URL без встроенных учётных данных. Для частного УЦ укажите `RESTIC_CACERT`.

```sh
export COMPOSE_PROJECT_NAME=gis-platform
export GIS_STATE_DIR=/srv/gis/state
export RESTIC_REPOSITORY=rest:https://backup.example.org/gis-platform/
export RESTIC_PASSWORD_FILE=/etc/gis-operator/restic-password
# export RESTIC_CACERT=/etc/gis-operator/backup-ca.pem
# export GIS_BACKUP_RETENTION_DAYS=30
```

3. Инициализируйте **новый** репозиторий один раз. Затем вручную выполните первое копирование и проверьте результат.

```sh
cd /opt/gis-platform
. /etc/gis-operator/backup.env
restic init
node dist/cli.js backup create daily /srv/gis/platform.yaml --json
restic snapshots --tag "gis-platform-$COMPOSE_PROJECT_NAME"
restic check
```

К снимкам обоих видов добавляется тег `gis-platform-<имя-проекта>`. По умолчанию CLI оставляет снимки за 30 дней от последнего успешного снимка проекта. Полный ID успешной копии возвращается в `data.snapshotId`. Если запись прошла, а очистка истёкших снимков завершилась ошибкой, сначала проверьте `restic snapshots` по тегу и разберите ошибку очистки.

4. Настройте ежедневное задание для владельца развёртывания. Например, добавьте в его `crontab -e` строку ниже. Укажите время обслуживания и добавьте пути к установленным `node` и `restic` в окружение cron, если их нет в системном `PATH`. Настройте доставку ошибок и запись полного ID снимка.

```cron
15 2 * * * /bin/bash -c 'cd /opt/gis-platform && . /etc/gis-operator/backup.env && node dist/cli.js backup create daily /srv/gis/platform.yaml --json'
```

Перед обновлением дополнительно запускайте `backup create pre-update`. Ждите подтверждения. Дождитесь завершения `config apply`, если применение уже выполняется. Сохраняйте файлы и секреты неизменными до завершения снимка. После аварийной остановки проверьте рабочие каталоги `.gis-backup-work-*` в `GIS_STATE_DIR` и журнал задачи. Обращайтесь с рабочими дампами как с секретными файлами. [Подготовка репозитория restic](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)

```sh
node dist/cli.js backup create pre-update /srv/gis/platform.yaml --json
```

### Сверка доступа

Сначала выберите базовый снимок, из которого нужно восстановить конфигурацию и файлы. Затем установите, какие учётные записи, сеансы и разрешения действовали к моменту прекращения записи на исходной платформе. Старый дамп может вернуть отозванные права, разблокировать учётную запись или снова сделать действующим прежний токен.

- Если журнал и независимые записи подтверждают отсутствие изменений после базовой копии, при восстановлении подойдёт её дамп и флаг `--verified-no-changes`.
- Если изменения были, выберите более свежий снимок того же развёртывания и используйте `--verified-authority`. Он должен учитывать все изменения до прекращения записи. CLI проверяет идентификатор развёртывания, время дампа, настройки доступа и ключ. Если изменения вносились в правила публикаций, операторов или ключ, подберите совместимую базовую копию и подтвердите актуальность прав.
- Пока состояние доступа не подтверждено, держите защищённые маршруты закрытыми.

Если исходный сервер ещё доступен, объявите окно на переключение, прекратите операции с учётными записями и правами и остановите компонент доступа. Оставьте PostgreSQL работающим. Подставьте имя контейнера `access`, найденное по метке проекта.

```sh
docker stop gis-platform-access-1
node dist/cli.js backup create pre-update /srv/gis/platform.yaml --json
```

Запишите полный ID свежего снимка. Сверьте с журналом выдачу и отзыв разрешений, блокировки и разблокировки, отзыв токенов и завершение сеансов. При пробном восстановлении выбирайте снимки и подтверждайте состояние доступа по тестовым сценариям, чтобы не останавливать исходный сервер.

### Пробное восстановление и запуск

1. Подготовьте отдельную машину или изолированную виртуальную машину с соответствующей версией кода и собранным CLI. На ней должны быть свободны прежние порты и исходные абсолютные пути для восстанавливаемых файлов. В примере разместите код под `/opt/gis-platform-restore`, чтобы `/srv/gis` оставался свободен для данных из копии. Выполняйте команды из каталога кода. Подключите закрытый файл окружения restic и настройте контролируемый доступ к внешнему PostGIS и SMTP.
2. Извлеките базовый снимок и, при необходимости, снимок с актуальным дампом в разные новые каталоги. Подставьте полный ID из `restic snapshots`. Команда проверяет файлы и отмечает состояние шлюза закрытым.

```sh
umask 077
install -d -m 700 /srv/gis-restore
read -r -p 'Полный ID базового снимка: ' snapshot_id
node dist/cli.js backup extract "$snapshot_id" /srv/gis-restore/baseline --json
```

Если нужен отдельный снимок с актуальным дампом, извлеките его отдельно.

```sh
read -r -p 'Полный ID снимка с актуальными правами: ' authority_id
node dist/cli.js backup extract "$authority_id" /srv/gis-restore/authority --json
```

Из первого результата выпишите `data.directory` и `data.originalStateDirectory`, из выбранного снимка с дампом — `data.payload`. `data.payload` — абсолютный путь к служебному комплекту, передаваемому в `backup recover`.

3. Восстановите служебный каталог из `data.directory` по пути `data.originalStateDirectory`. Верните остальные файлы базового снимка на их исходные пути, включая данные и секреты. Сохраните режимы доступа и владельцев. Пример копирования ниже применим, если восстановленные данные под `baseline/srv/gis/` включают всё необходимое, а `/srv/gis` ещё отсутствует на выделенной машине. Код приложения можно держать в отдельном каталоге, чтобы не мешать восстановлению путей.

```sh
test ! -e /srv/gis && cp -a /srv/gis-restore/baseline/srv/gis /srv/gis
```

Продолжайте после успешного копирования. Если `/srv/gis` уже существует, проверьте его содержимое и восстановите файлы на исходные пути только в выделенном окружении.

4. Выберите новое имя проекта с префиксом `gis-restore-`. Оно должно быть свободно, без прежних контейнеров и томов. Укажите исходный абсолютный путь каталога состояния и loopback.

```sh
export COMPOSE_PROJECT_NAME=gis-restore-pilot
export GIS_STATE_DIR=/srv/gis/state
export GIS_PUBLIC_BIND=127.0.0.1
read -r -p 'Абсолютный путь data.payload: ' payload
```

Запустите **одну** команду `recover`. Для проверенного свежего дампа выполните:

```sh
node dist/cli.js backup recover "$payload" --verified-authority --json
```

Для базового дампа при подтверждённом отсутствии изменений выполните:

```sh
node dist/cli.js backup recover "$payload" --verified-no-changes --json
```

CLI поднимает PostgreSQL с новым томом, восстанавливает дамп, проверяет готовность сервисов и открывает маршруты через Caddy на loopback. Если проверка до начала восстановления показала, что имя проекта занято, выберите свободное. Для продолжения уже начатого восстановления сохраните имя проекта и промежуточные файлы, исправьте причину отказа и повторите команду.

5. Проверьте текущую и предыдущую версии, чтение публичной публикации и отказ без соответствующих прав. Проверьте разрешённые контрольные учётные записи и отказ заблокированной записи, отозванному разрешению, отозванному токену и завершённому сеансу. Для локальной проверки HTTPS используйте `curl --resolve` с публичным именем и доверенным УЦ, как в [разделе HTTPS](#внешний-http-и-https).

```sh
node dist/cli.js status --json
node dist/cli.js doctor --json
```

После пробной проверки остановите тестовый стек.

6. Для возврата рабочего сервиса повторите проверенный порядок на выделенной машине. Сначала проверьте доступ на loopback. Затем подключите внешний прокси либо поменяйте привязку Caddy и направьте DNS на восстановленный хост. Сохраните имя восстановленного проекта. Пример для штатного HTTPS использует ID из результата восстановления и архив TLS.

```sh
read -r -p 'ID подтверждённой версии после восстановления: ' current_version
export GIS_REVISION_DIR="$GIS_STATE_DIR/plans/$current_version"
export GIS_PUBLIC_PORT=443 GIS_CADDY_PORT=443 GIS_HTTP_REDIRECT_PORT=80
export GIS_TLS_CERT_FILE="$GIS_STATE_DIR/tls/$current_version/cert.pem"
export GIS_TLS_KEY_FILE="$GIS_STATE_DIR/tls/$current_version/key.pem"
GIS_PUBLIC_BIND= docker compose -p "$COMPOSE_PROJECT_NAME" \
  -f compose.yaml -f compose.tls.yaml up -d --no-deps caddy
```

Если внешний порт отличается, укажите порт из YAML. Для версии без архива TLS укажите восстановленные исходные пути. Для HTTP используйте только `compose.yaml`, задайте `GIS_CADDY_PORT=80` и внешний порт из YAML. После переключения сохраните выбранную привязку в окружении оператора для последующих применений. Проверьте внешний URL, TLS и правила доступа из клиентской сети.

Обновите ежедневное задание резервного копирования с новым именем проекта и точным путём к восстановленному YAML. Выполните контрольное копирование и сохраните ID нового снимка. Удалите рабочие копии дампов и извлечённых секретов по правилам вашей организации.

## Диагностика и действия при сбое

Начните с точного URL, кода ответа и названия проекта. Проверяйте по очереди шлюз, компонент доступа, экземпляр и источник.

```sh
docker info --format '{{.ServerVersion}}'
docker compose ls --all
node dist/cli.js status --json
node dist/cli.js doctor --json
node dist/cli.js doctor --publication places --json
curl -sS -D - -o /dev/null "$public_url/features/collections/places?f=json"
```

| Симптом | Что проверить |
| --- | --- |
| Docker недоступен | `docker context show`, запущенный движок и доступ текущей учётной записи. В Windows проверьте Docker Desktop и интеграцию с нужным дистрибутивом WSL. |
| Запрос не доходит до шлюза | Контейнер Caddy, адрес и порт из плана, привязку интерфейсов, DNS и межсетевой экран. В HTTPS проверьте имя хоста, цепочку и срок сертификата. |
| HTTP 401 или 403 | Состояние сеанса или токена, режим доступа, подтверждение email и персональное разрешение. Сверьте запись в `users list --json`. |
| HTTP 404 или коллекция пропала из каталога | Правильный корень протокола и ID, актуальную версию YAML, режим доступа и видимость для текущего клиента. Проверьте `config plan` на удаление. |
| HTTP 503 | `closedRoutes` в `status`, готовность экземпляра и источника в `doctor`, журналы Caddy и провайдера. Для PostGIS проверьте доступ к БД из контейнера и прежнюю схему. |
| CLI не видит действующую версию | Проверьте каталог запуска, `GIS_STATE_DIR` и `COMPOSE_PROJECT_NAME`. Для оператора CLI проверьте порт, УЦ и клиентскую пару. |
| `config validate` сообщает ошибку | Найдите указанный путь поля в YAML и в `description` схемы. Проверьте имена ID, сочетание протокола, источника и адаптера. Наличие файлов и готовность провайдера проверяются при подготовке и применении плана. |

`doctor` показывает `data.gateway` со значением `ready`, `closed` или `unavailable`. Для публикаций смотрите `data.publications`, поля `instance` и `source`. Если экземпляр недоступен, источник может иметь состояние `unknown`. Для PostGIS недоступность источника также отображается в доступном клиенту каталоге как `status: unavailable`. Шлюз ждёт заголовки от провайдера PostGIS до 15 секунд. После восстановления БД с прежней схемой новые запросы могут обслуживаться автоматически. После смены схемы обновите YAML и примените план.

Запишите `X-Request-Id` из ответа клиента. По нему можно связать HTTP-код в журнале Caddy и событие `publication.request` в журнале `access`. Изменения прав пишутся как `access.change`. Для просмотра на хосте используйте имена контейнеров нужного проекта.

```sh
docker logs --since 10m gis-platform-caddy-1
docker logs --since 10m gis-platform-access-1
```

### Если применение прервалось

1. Выполните `status --json`. `currentVersion` — действующая подтверждённая версия, `previousVersion` — предыдущая, `pendingPlanId` — незавершённый план, `closedRoutes` — закрытые маршруты. Сохраните вывод `config apply` и журналы.
2. Если CLI сообщил `APPLY_IN_PROGRESS`, дождитесь работающего процесса. При `PLAN_STALE` постройте новый план по текущей версии.
3. Если связь оборвалась, проверьте состояние и повторите `config apply` с тем же ID. CLI вернёт сохранённый результат завершённой операции либо продолжит обработку состояния. Если файл изменился после планирования, подготовьте новый план.
4. При `APPLY_FAILED` выясните причину по сообщению CLI и проверьте прежнюю публикацию. При `RECOVERY_INCOMPLETE` затронутые маршруты остаются закрытыми. Исправьте доступность источника, PostgreSQL или Compose и повторите применение по указанному ID. Состояние и PostgreSQL нужны для корректного восстановления.
5. Если после принудительного завершения остался `apply.lock`, сначала убедитесь на хосте, что процессы применения и Compose завершились. Только для оставшегося **пустого** каталога используйте `rmdir "$GIS_STATE_DIR/apply.lock"` и повторите `config apply`. Дальше CLI восстановит последнюю подтверждённую конфигурацию.

## Справочник команд

Все команды CLI запускаются через `node dist/cli.js` из каталога собранной версии. В таблице показана часть команды после имени скрипта. `<id>`, `<file>` и другие обозначения заменяйте реальными значениями. Квадратные скобки в синтаксисе обозначают необязательный аргумент. `--json` можно добавить к любой команде для машинного вывода.

### Конфигурация, экземпляры и диагностика

| Команда | Кто запускает и результат |
| --- | --- |
| `config validate <file>` | Владелец проверяет полный YAML и получает список ID публикаций. |
| `config plan <file>` | Владелец готовит план применения. Результат включает `data.planId`, `added`, `changed`, `removed`, адреса и затрагиваемые сервисы. |
| `config plan --rollback-to <version>` | Владелец готовит план возврата к указанной подтверждённой версии. |
| `config apply <plan-id>` | Владелец применяет проверенный план. Результат сообщает ID действующей версии. |
| `status` | Владелец или оператор с `diagnostics` получает версию и состояние применения. |
| `doctor [--publication <id>]` | Владелец или оператор с `diagnostics` проверяет шлюз и все публикации либо одну по ID. |
| `provider add <id> <image> <integration.yaml> <platform.yaml>` | Владелец добавляет экземпляр из образа, применяет план и записывает изменение в YAML. |
| `provider update <id> <platform.yaml> [image]` | Владелец обновляет закреплённый образ экземпляра и YAML. |
| `provider remove <id> <platform.yaml>` | Владелец удаляет экземпляр без ссылок из публикаций. |

### Администрирование доступа

Для команд с выбором пользователя передайте **один** селектор `--email <email>` либо `--user-id <id>`. Используйте ID из `users list` или `tokens list`. Оператору нужна указанная роль в `auth.cli.operators`.

| Команда | Роль | Результат |
| --- | --- | --- |
| `users list` | `users-read` | Список пользователей, статусов и доступных публикаций. |
| `users block (--email <email> или --user-id <id>)` | `access-write` | Блокировка учётной записи. |
| `users unblock (--email <email> или --user-id <id>)` | `access-write` | Снятие блокировки. |
| `access grant <publication-id> (--email <email> или --user-id <id>)` | `access-write` | Выдача персонального разрешения для закрытой публикации. |
| `access revoke <publication-id> (--email <email> или --user-id <id>)` | `access-write` | Отзыв персонального разрешения. |
| `tokens list (--email <email> или --user-id <id>)` | `users-read` | ID токенов, имена, даты и признак активности. |
| `tokens revoke <token-id> (--email <email> или --user-id <id>)` | `access-write` | Отзыв токена указанного пользователя. |

Персональный токен создаётся владельцем учётной записи в веб-интерфейсе. Административные команды используют сертификат оператора.

### Команды резервного копирования

| Команда | Результат |
| --- | --- |
| `backup create daily [path ...]` | Ежедневный снимок. Возвращает полный `data.snapshotId`. |
| `backup create pre-update [path ...]` | Снимок перед обновлением или перед переносом с замороженными изменениями доступа. |
| `backup extract <snapshot-id> <new-directory>` | Извлекает снимок с полным ID в новый каталог. Возвращает пути исходного и восстановленного состояния и комплекта дампа. |
| `backup recover <absolute-payload> --verified-authority` | В изолированном проекте завершает восстановление после сверки более свежего дампа доступа. |
| `backup recover <absolute-payload> --verified-no-changes` | Использует базовый дамп при подтверждённом отсутствии изменений доступа после копии. |

См. [процедуру восстановления](#резервное-копирование-и-восстановление) перед запуском `recover`.

### Команды хоста

| Команда | Когда использовать |
| --- | --- |
| `npm ci`, `npm run build` | Подготовить CLI из кода выбранной версии. |
| `docker info`, `docker context show`, `docker compose version` | Проверить движок, выбранный контекст и версию Compose. |
| `docker compose ls --all` | Найти действующий или остановленный Compose-проект. |
| `docker compose -f <base> -f <override> config --services` | Узнать имена сервисов из выбранного набора файлов. |
| `docker ps -a` с фильтром по проекту, `docker inspect <container>` | Найти контейнеры и проверить порты, состояние и монтирования. |
| `docker stop <container>`, `docker start <container>`, `docker restart <container>` | Управлять уже созданными контейнерами. |
| `docker logs --tail 100 <container>` | Посмотреть журнал конкретного сервиса. |
| `docker compose ... up -d --no-deps …` | Целевое пересоздание по процедуре обновления или открытия Caddy после восстановления. |
| `curl` | Проверить ответ публикации с хоста и из клиентской сети. |
| `restic init`, `restic snapshots`, `restic check` | Подготовить новый репозиторий, найти копии и проверить хранилище. |

### Переменные окружения

| Переменная | Где используется |
| --- | --- |
| `COMPOSE_PROJECT_NAME` | Имя проекта Compose при применении, диагностике и копировании. |
| `GIS_STATE_DIR` | Каталог состояния для CLI. |
| `GIS_PUBLIC_BIND` | IP-адрес хоста для опубликованных портов Caddy. `127.0.0.1` ограничивает их loopback. Пустое значение позволяет Docker опубликовать порт на всех интерфейсах. |
| `GIS_HTTP_REDIRECT_PORT` | Порт хоста для HTTP-перенаправления при HTTPS. По умолчанию 80. |
| `GIS_ADMIN_PORT` | Порт локального административного API для клиента CLI. |
| `GIS_ADMIN_CA_FILE`, `GIS_ADMIN_CERT_FILE`, `GIS_ADMIN_KEY_FILE` | Доверенный УЦ и клиентский сертификат оператора с его ключом. |
| `NODE_EXTRA_CA_CERTS` | Дополнительный доверенный корень или цепочка для Node.js. |
| `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE` | HTTPS-репозиторий restic и отдельный файл его пароля. |
| `RESTIC_REST_USERNAME`, `RESTIC_REST_PASSWORD`, `RESTIC_CACERT` | Данные доступа к rest-server и доверенный УЦ для его HTTPS при необходимости. |
| `GIS_RESTIC_EXECUTABLE`, `GIS_BACKUP_RETENTION_DAYS` | Путь к restic и срок хранения копий в днях. |

CLI при работе с Compose сам подставляет `GIS_REVISION_DIR` и `GIS_PROVIDER_REVISION_DIR` для каталогов конфигурации, `GIS_SOURCE_FILE` для встроенного GeoJSON, `GIS_PUBLIC_PORT` и `GIS_CADDY_PORT` для портов, `GIS_TLS_CERT_FILE` и `GIS_TLS_KEY_FILE` для сертификата шлюза, `GIS_AUTH_SECRET_FILE` и `GIS_POSTGRES_PASSWORD_FILE` для секретов и `GIS_MAILPIT_PORT` для тестовой почты. При целевой ручной операции подставляйте только значения из действующего развёртывания, относящиеся к затрагиваемым сервисам.

### Машинный вывод

При `--json` в stdout приходит один объект с полями `status`, `code` и `data`. В скрипте проверяйте код процесса и поле `code`. Для `config plan` используйте `data.planId`. При повторном вызове `config apply` с уже завершённым планом сначала проверьте `currentVersion` в `status`. Результат повторного вызова описывает ранее выполненную попытку.

| Код процесса | Поле `code` | Значение |
| --- | --- | --- |
| `0` | `OK`, `NO_CHANGE` | Успех или изменение не требуется. |
| `1` | `FAILED` | Прочий сбой. |
| `2` | `INVALID_INPUT`, `INVALID_CONFIG` | Ошибка аргументов или конфига. |
| `3` | `NOT_FOUND` | Указанный объект, версия или план отсутствует. |
| `4` | `FORBIDDEN` | У вызывающей учётной записи нет нужных прав. |
| `5` | `PLAN_STALE`, `APPLY_IN_PROGRESS` | План устарел или выполняется другое применение. |
| `6` | `APPLY_FAILED` | Применение не удалось. Проверьте активность прежней версии. |
| `7` | `RECOVERY_INCOMPLETE` | Для восстановления затронутых маршрутов требуется устранить сбой. |

CLI выводит состояние и пути с учётом прав. Значения секретов и токенов остаются в предусмотренных для них файлах и интерфейсах.
