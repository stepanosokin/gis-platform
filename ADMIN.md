# CLI администратора GIS Platform

## Текущая реализация

CLI поддерживает проверку и применение YAML, откат к сохранённой версии и просмотр состояния через `status` для публикаций GeoJSON, GeoPackage, Shapefile, GeoParquet и внешнего PostGIS через OGC API — Features во всех трёх режимах доступа. Для управления доступом доступны `users list`, `users block`, `users unblock`, `access grant`, `access revoke`, `tokens list` и `tokens revoke`. Команды выполняются из корня репозитория. [Локальный запуск](README.md#локальная-публикация-geojson) · [Регистрация и доступ](README.md#регистрация-и-доступ)

```sh
npm ci
npm run build
node dist/cli.js config validate examples/features.yaml
node dist/cli.js config plan examples/features.yaml
```

Проверьте изменения публикации, URL и список сервисов в плане. Передайте ID из первой строки вывода в `node dist/cli.js config apply <plan-id>`. После применения коллекция из примера доступна по адресу `http://localhost:8080/features/collections/places`.

Добавьте `--json` к любой из трёх команд для машинного вывода. В ответе `config plan --json` ID плана находится в `data.planId`.

### Экземпляры сервис-провайдеров

Соберите CLI командой `npm run build`. Для пробы используйте свою копию `examples/features.yaml` в том же каталоге, что и `places.geojson`. Добавьте экземпляр из образа pygeoapi с указанием версии.

```sh
node dist/cli.js provider add second-features geopython/pygeoapi:0.24.0 examples/provider-features.yaml examples/local.yaml
```

Команда применяет конфигурацию, запускает контейнер `provider-second-features` в проекте платформы и записывает экземпляр в общий YAML. Порт из `api.port` доступен внутри Compose. Запросы пользователей идут через Caddy.

В [примере интеграции](examples/provider-features.yaml) задан адаптер pygeoapi для OGC API — Features. `api` описывает внутреннюю схему HTTP, порт, базовый путь, публичный корень, канонические ссылки и путь проверки готовности относительно внутреннего базового пути. Адаптер использует поля публикации `source`, `protocol`, `title`, `description` и `extent` для формирования нативной конфигурации. Можно добавить переменные окружения в `environment` и именованные тома в `volumes`. Имена томов привязаны к ID экземпляра. Для уже существующего YAML запись `type: pygeoapi` по-прежнему обозначает встроенный экземпляр платформы.

Чтобы перенести публикацию `places`, измените её поле `provider` на `second-features`. Запустите `config plan` и `config apply`. ID и права сохранятся. При общем корне `/features` URL останется прежним. Если изменить `public_root` экземпляра, план покажет старый и новый URL. Экземпляры с общим корнем обслуживают свои коллекции, а Caddy выдаёт общий каталог и OpenAPI по действующим правам.

```sh
node dist/cli.js provider update second-features examples/local.yaml
node dist/cli.js provider update second-features examples/local.yaml geopython/pygeoapi:0.24.0
node dist/cli.js provider remove second-features examples/local.yaml
```

`provider update` загружает указанный образ или снова запрашивает текущий тег. YAML и подтверждённая версия сохраняют digest, поэтому повторный запуск и откат используют тот же образ. При сбое проверок действующая версия возвращается вместе с прежним образом. Если нужен новый тег, передайте его команде `provider update`. Тома остаются на месте при обновлении и удалении.

Если платформа уже работает, примените черновые изменения через `config plan` и `config apply` перед управлением экземплярами. Так команда выполнит только запрошенное изменение.

Чтобы снова запустить остановленный проект, создайте свежий план из общего YAML и примените его с прежними `COMPOSE_PROJECT_NAME` и `GIS_STATE_DIR`. Ранее выполненный ID плана возвращает сохранённый результат.

`provider remove` перечисляет публикации, которые ещё ссылаются на экземпляр. Перенесите или удалите их через `config plan` и `config apply`, затем повторите команду. После успешного удаления контейнер и запись в YAML исчезнут. Папки источников и данные именованных томов сохранятся.

### Файлы и системы координат Features

Путь к каждому файлу может быть абсолютным или относительным к общему YAML. Для GeoPackage выберите слой через `layer`. Для Shapefile укажите имя слоя без `.shp`. Рядом должны лежать файлы с тем же именем и расширениями `.shx`, `.dbf`, `.prj` и, при наличии, `.cpg`. Провайдер берёт систему координат из метаданных слоя и использует `id_field` как ID объекта. Значения этого поля должны быть непустыми и уникальными строками или целыми числами. Подготовьте файлы до планирования и храните их по указанным путям, пока они нужны для работы или отката.

```yaml
schema_version: 1
server: {host: localhost, port: 8080}
sources:
  places-package: {type: geopackage, path: data/places.gpkg, layer: places, id_field: place_id}
  places-shape: {type: shapefile, path: data/places.shp, layer: places, id_field: place_id}
  places-parquet: {type: geoparquet, path: data/places.parquet, id_field: place_id}
providers:
  file-features: {type: pygeoapi}
publications:
  places:
    source: places-package
    provider: file-features
    protocol: features
    access: public
    title: Places
    description: Places from the selected file.
    extent: [36, 54, 40, 58]
    crs: [EPSG:3857, EPSG:4326, ESRI:102026, EPSG:5041]
```

Создайте публикацию на каждый нужный источник. Можно также поменять `source` в примере перед первой публикацией. Выполните `config validate`, `config plan` и `config apply`. Снимок файлов применяйте новым планом. Для безопасной смены снимка храните его по новому пути и обновляйте YAML.

GeoParquet читается напрямую из одного `.parquet` с метаданными `geo`, первичной геометрией в WKB и плоскими рёбрами. Когда метаданные не содержат поля `crs`, используется CRS84. Для встроенного экземпляра Compose собирает образ pygeoapi 0.24.0 с PyArrow 23.0.1. Для дополнительного экземпляра из образа установите совместимый читатель PyArrow в его окружение pygeoapi. Дополнительным экземплярам для GeoPackage и Shapefile требуется Fiona.

| Источник | Пространственный отбор | Время | CQL2 |
| --- | --- | --- | --- |
| GeoPackage, Shapefile | Пересечение с bbox | — | — |
| GeoParquet WKB | Пересечение с bbox по геометрии, включая частичное пересечение | `datetime` с полем `time_field` типа timestamp | — |
| GeoJSON | Пересечение с bbox | — | — |
| PostGIS | Пересечение с bbox | `datetime` с полем `time_field` | Text и JSON |

Для файлового источника, которому нужны CQL2 или запросы по большому набору данных, подготовьте геометрию и ID в PostGIS. Прямые запросы к трём новым файловым форматам читают объекты слоя для проверки точного пересечения и подсчёта результатов. Возможности фильтров указаны в описании коллекции и OpenAPI.

`extent` и ответ без параметра `crs` используют CRS84. В каталоге `/features/collections?f=json` и в описании коллекции поле `crs` содержит URI поддерживаемых систем. Добавляйте двухмерные географические и проецированные CRS через `crs` в YAML. При применении плана провайдер проверяет наличие CRS и возможность преобразования для публикации. Для существующих провайдеров GeoJSON и PostGIS доступны CRS84, EPSG:4326 и EPSG:3857.

В запросе к `/features/collections/places/items` задайте URI из списка в `crs` для координат ответа и в `bbox-crs` для четырёх координат `bbox`. Для CRS84 порядок осей долгота, широта. Для EPSG:4326 порядок широта, долгота. Если область пересекает антимеридиан, для новых файловых форматов используйте CRS84 с переходом от положительной долготы к отрицательной или отправьте два запроса с упорядоченными границами. Ответ со списком или отдельным объектом сообщает систему координат в заголовке `Content-Crs`.

### Растровая публикация Maps

Подготовьте геопривязанный GeoTIFF или COG. В [примере YAML](examples/maps.yaml) укажите путь к файлу, код EPSG источника и охват публикации в CRS84. Код источника по умолчанию — 4326. Для COG используйте `type: cog`. Расширение файла — `.tif` или `.tiff`. Контейнер получает файл отдельным монтированием только для чтения. Платформа проверяет формат, геопривязку, CRS и пробное построение PNG при применении плана.

Добавьте настройки в существующий YAML или используйте пример для отдельного проекта. Запустите `config validate`, `config plan` и `config apply`. Экземпляр pygeoapi для `protocol: maps` отвечает через Caddy под `/maps`. Режим `access` задаётся для каждой публикации. Каталог, OpenAPI и запросы карт учитывают те же права, что и публикации Features. Для замены растра подготовьте файл по новому пути и примените новый план. Сохраните прежний файл для отката.

```sh
curl 'http://localhost:8080/maps/collections/terrain/map?bbox=36,54,40,58&width=800&height=600&f=png' -o terrain.png
```

`bbox` задаёт четыре упорядоченные координаты CRS84 в порядке запад, юг, восток, север. Если пропустить `bbox`, закреплённый провайдер использует мировой охват. `width` и `height` задают целые размеры от 1 до 2048 пикселей каждый. Проверены ответы 1 × 1 и 2048 × 2048 и прямоугольные изображения с разным охватом. По умолчанию размеры составляют 500 × 300 пикселей. Формат по умолчанию — PNG. Некорректные параметры получают HTTP 400 с JSON-кодом `InvalidParameterValue`. Ответ сообщает фактические границы в `Content-Bbox` и систему координат в `Content-Crs`.

На закреплённом образе pygeoapi 0.24.0 с MapServer 8.4.0 маршрут `/maps/conformance?f=json` объявляет класс Maps Part 1 `core`, классы Common Part 1 `core`, `landing-page`, `json`, `html`, `oas30` и класс Common Part 2 `collections`. Нативный OpenAPI объявляет параметры ширины и высоты без пределов и ошибочно указывает JSON для успешного ответа карты. OpenAPI шлюза описывает PNG, указанные пределы и параметры функционального профиля. Локальная приёмка покрывает запросы PNG по `bbox`, `width` и `height` в рамках [OGC API — Maps Part 1, 1.0.0](https://ogcapi.ogc.org/maps/).

### Динамическая публикация Features из PostGIS

DBA готовит таблицу или представление с уникальным непустым ID и колонкой геометрии PostGIS с SRID 4326. Учётной записи нужны `USAGE` для схемы и `SELECT` для подготовленного источника. Для временных фильтров добавьте колонку с типом `timestamp`, предпочтительно `timestamptz`.

Укажите адрес, имя БД, пользователя и файл пароля отдельно для каждого экземпляра pygeoapi, который обслуживает PostGIS. Адрес и порт PostgreSQL должны быть доступны **из контейнера** pygeoapi. По умолчанию используется порт 5432. Запишите пароль в UTF-8 одной строкой и вычисляйте путь `postgis.password_file` относительно общего YAML. Compose монтирует файл как секрет только в нужный контейнер.

Добавьте источник, подключение и публикацию в соответствующие разделы платформенного YAML. Используйте отдельные экземпляры pygeoapi для файлов и PostGIS. В примере используется встроенный экземпляр. Для экземпляра из образа задайте тот же блок `postgis` рядом с `image` и `api`.

```yaml
sources:
  observations:
    type: postgis
    schema: gis
    relation: published_observations
    id_field: id
    geometry_field: geom
    max_lag_seconds: 0
providers:
  live-features:
    type: pygeoapi
    postgis:
      host: postgis.example.org
      database: gis
      user: features_reader
      password_file: ./secrets/observations-password
publications:
  observations:
    source: observations
    provider: live-features
    protocol: features
    access: public
    title: Observations
    description: Observations published from PostGIS.
    extent: [37, 55, 40, 58]
    time_field: observed_at
    freshness:
      max_delay_seconds: 0
```

Запустите `config validate`, `config plan` и `config apply`. Новый запрос к прежнему URL читает подтверждённые данные источника. Ответы шлюза имеют `Cache-Control: no-store`. Предел `freshness.max_delay_seconds` по умолчанию равен 60 секундам. Гарантированная DBA задержка подготовки `max_lag_seconds` должна укладываться в предел каждой публикации. При пределе 0 укажите источник с нулевой задержкой подготовки.

Откройте `/features/openapi?f=json` для списка параметров каждой коллекции. Передавайте CQL2 Text в параметре `filter` с `filter-lang=cql2-text`. Для CQL2 JSON отправьте POST к `/features/collections/observations/items?f=json` с `Content-Type: application/json` и выражением в теле запроса. Для перехода между страницами отправляйте POST с тем же выражением по URL нужной страницы. При настроенном `time_field` параметр `datetime` принимает момент, закрытый интервал или интервал с открытой границей `..`.

Для смены пароля задайте в YAML новый путь `password_file` и примените свежий план. Для отката прежний файл должен содержать пароль, который всё ещё действует в PostgreSQL. Чтобы перенести публикацию на другой экземпляр с сохранением ID, настройте тот же адрес, порт и БД.

### Ячейки H3 из PostGIS

Подготовьте одно представление DBA и опубликуйте его через два экземпляра, pygeoapi для Features и Martin для MVT. Укажите подключение, пароль и охват в [примере YAML](examples/h3-postgis.yaml), затем выполните `config validate`, `config plan` и `config apply`. Пример открывает публичные маршруты `/features/collections/h3-observations` и `/mvt/h3-observation-tiles`.

Если таблица наблюдений хранит `cell` типа `h3index`, DBA может использовать такой запрос. `observation_id` — постоянный уникальный ключ наблюдения. Несколько строк одной ячейки имеют одинаковый `h3_id` и разные `feature_id`. При хранении готовых границ и уровня выберите эти колонки напрямую. Расширения H3 нужны в БД, где выполняются функции H3.

```sql
CREATE VIEW h3_data.published_observations AS
SELECT observation_id::text AS feature_id,
       cell::text AS h3_id,
       h3_get_resolution(cell) AS resolution,
       observed_at,
       measurement,
       ST_Multi(h3_cell_to_boundary_geometry(cell))::geometry(MultiPolygon, 4326) AS geom
FROM h3_data.observations;

GRANT USAGE ON SCHEMA h3_data TO h3_reader;
GRANT SELECT ON h3_data.published_observations TO h3_reader;
```

Проверьте непустые ID, валидность геометрии и её SRID перед публикацией. `h3_cell_to_boundary_geometry` разрезает границу ячейки по 180°, а `ST_Multi` даёт одинаковый тип геометрии для всех строк. Роли чтения достаточно доступа к представлению. [Функции h3_postgis](https://pgxn.org/dist/h3/4.5.0/docs/h3-pg-skill/SKILL.html)

На pygeoapi 0.24.0 проверены CRS84, EPSG:4326 и EPSG:3857, пространственный отбор, CQL2 Text/JSON и `datetime`. Features сохраняет всю границу выбранной ячейки. Martin 1.16.1 выдаёт XYZ в Web Mercator и обрезает геометрию по области тайла с буфером. Оба маршрута сохраняют готовые показатели и строковый `h3_id`. Для отсутствующего значения Features возвращает `null`, а MVT опускает свойство. Нулевое значение присутствует в обоих форматах. Ячейка без наблюдений отсутствует в выдаче.

### Ячейки H3 из Parquet через DGGS

Подготовьте версионируемый файл Parquet для чтения. В нём должна быть одна строка на уникальный строковый ID H3 в нижнем регистре. Все ячейки одной публикации используют заданное разрешение. Перечислите разрешённые столбцы показателей в `properties`. Снимок содержит только эти столбцы и поле `id_field`. Для целочисленных показателей используйте знаковый 64-битный `BIGINT`, для вещественных — `DOUBLE`. CLI проверяет типы и возможность прочитать поля штатным поставщиком Parquet. Границы вычисляются по H3 ID.

Укажите путь, разрешение, показатели и охват в [примере YAML](examples/h3-parquet.yaml). Выполните `config validate`, `config plan` и `config apply`. Compose запускает закреплённый образ pydggsapi 0.4.0 для `linux/amd64`. При инициализации встроенный DuckDB загружает расширение `httpfs`. Для обновления подготовьте новый файл и измените `sources.<id>.path` в YAML. После применения следующий запрос по прежнему URL читает новый файл. Храните прежний снимок, если нужен откат.

Каталог, OpenAPI и Swagger доступны на `/dggs/collections`, `/dggs/openapi` и `/dggs/docs`. Для публикации действуют режимы `public`, `registered` и `private`. Метаданные, геометрия и показатели используют права одной публикации. Порт сервис-провайдера доступен внутри Compose.

К пути `/dggs/collections/{id}/dggs/h3` добавьте один из суффиксов.

| Суффикс | Результат |
| --- | --- |
| `/zones/{h3Id}` | ID, разрешение и полигональная граница ячейки со строкой в снимке |
| `/zones?bbox=12.28,45.41,12.36,45.47&zone-level=7&compact-zones=false&f=geojson&geometry=zone-region` | GeoJSON с границами и H3 ID подходящих ячеек |
| `/zones/{h3Id}/data?zone-depth=0` | Показатели одной ячейки. Ноль и `null` сохраняются. Если строки нет, API возвращает HTTP 204. |

На уровне 7 подтверждены два окна bbox на плотном и разреженном снимках. Для `12.28,45.41,12.36,45.47` достаточно лимита по умолчанию. Для `11.8,45.0,12.9,45.9` полнота подтверждена с `limit=10000`. В каждом случае порядок координат — запад, юг, восток, север.

Чтобы GeoJSON не терял ячейки из-за усечения, общее число ячеек H3, пересекающих bbox на уровне публикации, должно укладываться в `limit`. По умолчанию он равен 1000. Движок ограничивает список кандидатов до пересечения со списком ячеек, для которых есть строки в снимке. Делите bbox на меньшие окна при выходе за проверенный диапазон. [Результаты локальной проверки](tests/README.md#ячейки-h3-из-parquet)

Точные показатели `BIGINT` поддерживаются в безопасном диапазоне целых JSON от `-9007199254740991` до `9007199254740991` включительно. pydggsapi 0.4.0 может округлить `BIGINT` за пределами этого диапазона. [Воспроизведение ограничения](tests/README.md#ячейки-h3-из-parquet)

Один запрос Features с `bbox`, пересекающим 180°, отложен до поддержки в движке. На pygeoapi 0.24.0 запрос `bbox=179.9,-0.1,-179.9,0.2` вернул HTTP 200 и пустую коллекцию, хотя ячейка `857eb573fffffff` пересекает эту область. PostgreSQL-провайдер строит один прямоугольник через `ST_MakeEnvelope`. Для такой области отправьте два запроса, по одному с каждой стороны 180°, и объедините результаты по `feature_id`. [Код pygeoapi 0.24.0](https://github.com/geopython/pygeoapi/blob/0.24.0/pygeoapi/provider/sql.py#L751-L763) · [Правило bbox в OGC API — Features](https://docs.ogc.org/is/17-069r4/17-069r4.html#_parameter_bbox)

### Векторные веб-тайлы MVT через Martin

Скопируйте [пример YAML](examples/mvt.yaml) и укажите внешний PostGIS, доступный из контейнера Martin. Подготовьте таблицу или представление с типизированной геометрией и SRID. Выдайте роли `USAGE` на схему и `SELECT` на подготовленный источник. Martin открывает соединения в режиме чтения. Укажите файл пароля UTF-8 рядом с YAML и примените конфигурацию через `config validate`, `config plan` и `config apply`.

Один источник можно указать в публикациях Features и MVT. Каждая публикация имеет собственный ID и экземпляр сервис-провайдера. Настройте отдельный экземпляр Martin для каждого независимого подключения. Compose запускает экземпляр, когда к нему привязана хотя бы одна публикация. Свойство `id_field` включается в тайлы, а `mvt_properties` перечисляет дополнительные поля публикации. Используйте ID публикации как `source-layer` в стиле MapLibre. Для комментариев к таблице или представлению, которые Martin переносит в TileJSON, используйте только метаданные MVT. Проверка перед переключением отклоняет ссылки `data` и `grids`.

TileJSON доступен по `/mvt/observations`. Ссылки в документе адресуют шлюз, а тайлы MVT 2.1 используют XYZ и WebMercatorQuad. Порт Martin доступен внутри Compose. Кеш результатов отключён. При `freshness.max_delay_seconds: 0` новый запрос по тому же URL после COMMIT видит изменения, в том числе данные в ранее пустом тайле. Задержка подготовки источника `max_lag_seconds` должна укладываться в допустимую задержку публикации, по умолчанию 60 секунд.

При применении изменённого экземпляра CLI проверяет подключение и TileJSON во временном контейнере до переключения шлюза. При изменении структуры представления сначала обновите соответствующие параметры YAML, например `mvt_properties` или `geometry_field`, затем примените новый план. При недоступном PostGIS запросы, которые требуют данные, получают HTTP 503. Неизменённый экземпляр Martin может повторять подключение, пока другие публикации уже обслуживают запросы.

Для доступа к MVT с другого сайта добавьте его origin, например `http://localhost:5173`, в `cors.allowed_origins`. Токен для защищённой публикации передавайте через `transformRequest` MapLibre с заголовком `Authorization: Bearer <токен>`. Добавляйте заголовок только для запросов к URL этой публикации, включая TileJSON и связанные тайлы.

#### Стиль и связанные ресурсы MapLibre

Для публикации прямых веб-тайлов добавьте `maplibre` в запись публикации. Пути к локальным файлам считаются от каталога YAML. Ключи `resources` задают адреса файлов внутри публикации.
Выберите ID публикации и имена ресурсов, допустимые в файловой системе Windows. Например, `con` и `nul` зарезервированы.

```yaml
cors:
  allowed_origins: ['https://maps.example.org']
publications:
  observations:
    # Остальные поля публикации из examples/mvt.yaml
    maplibre:
      style_file: observations-style.json
      resources:
        markers.json: markers.json
        markers.png: markers.png
        markers@2x.json: markers@2x.json
        markers@2x.png: markers@2x.png
        labels.geojson: labels.geojson
        fonts/MapSans/0-255.pbf: fonts/MapSans/0-255.pbf
```

Стиль версии 8 открывается по `/mvt/observations/style.json`. В исходном стиле укажите `"url": "./"` для TileJSON этой публикации, `"sprite": "./resources/markers"` для атласа, `"data": "./resources/labels.geojson"` для связанного источника GeoJSON и `"glyphs": "./resources/fonts/{fontstack}/{range}.pbf"` для глифов. Для этого шрифта используйте `"text-font": ["MapSans"]`. Платформа преобразует ссылки в абсолютные URL шлюза при планировании. Добавьте в YAML оба файла каждого используемого разрешения атласа. Используйте латинские буквы, цифры, дефисы и подчёркивания в именах ресурсов. Для атласа допустим суффикс `@2x`, а для каталогов глифов — пробелы и запятые в имени стека шрифтов.

```js
const publication = 'https://gis.example.org/mvt/observations';
const map = new maplibregl.Map({
  container: 'map',
  style: `${publication}/style.json`,
  transformRequest: (url) => url === publication || url.startsWith(`${publication}/`)
    ? { url, headers: { Authorization: `Bearer ${token}` } }
    : { url },
});
```

Origin платформы допускается по умолчанию. `cors.allowed_origins` добавляет явные origins сайтов с картами. Вход и управление учётной записью доступны на адресе платформы. Предварительный запрос `OPTIONS` получает пустой ответ, а каждый запрос стиля, тайла или ресурса проходит проверку актуальных прав. При отзыве права или токена шлюз закрывает доступ со следующего запроса.

Команда `config plan` сохраняет стиль и ресурсы в план. После изменения файлов создайте и примените новый план. При откате шлюз выдаёт файлы выбранной версии.

### Векторные тайлы через OGC API — Tiles

Скопируйте [пример YAML](examples/tiles.yaml), укажите источник PostGIS и его подключение в экземпляре Martin. Поле `provider` указывает отдельный экземпляр pygeoapi с корнем `/tiles`. Поле `tile_provider` указывает экземпляр Martin, который формирует MVT. pygeoapi получает тайлы по внутренней сети Compose через MVT-proxy. Для выдачи того же источника через прямой TileJSON настройте отдельную публикацию MVT со своим ID и правами.

После `config validate`, `config plan` и `config apply` откройте `/tiles/collections/observations?f=json`. По ссылкам из коллекции можно открыть список наборов, описание WebMercatorQuad и определение матрицы. Из описания возьмите шаблон тайла и подставьте номер матрицы, строки и столбца в этом порядке. `/tiles/openapi?f=json` показывает методы, доступные с текущими правами. Caddy проверяет доступ к коллекции, метаданным набора и каждому тайлу. Для Bearer-запросов с другого сайта настройте `cors.allowed_origins`.

Ссылка TileJSON в описании набора подходит для поля `url` векторного источника MapLibre GL JS. Для `source-layer` укажите ID публикации. При сбое Martin или его подключения к PostGIS запрос тайла получает HTTP 503.

### Готовые растровые веб-тайлы через Martin

Скопируйте [пример YAML](examples/raster-tiles.yaml) и укажите пути к локальным растровым архивам MBTiles или PMTiles. Относительные пути считаются от каталога YAML. Архивы должны содержать готовые тайлы Web Mercator. Задайте экземпляр Martin без `postgis` и явно укажите его в каждой публикации. Docker монтирует указанные файлы только для чтения. Для внешних БД используйте отдельные экземпляры Martin.

В YAML `protocol: mvt` выбирает маршруты веб-тайлов Martin. В MapLibre GL JS задайте источник `{type: 'raster', url: 'http://localhost:8080/mvt/aerial', tileSize: 256}` и слой с `type: 'raster'`. Подставьте размер тайла из вашего архива. По URL источника клиент получает TileJSON со ссылкой на тайлы шлюза `/mvt/aerial/{z}/{x}/{y}`. Для браузерного доступа с другого сайта и защищённых публикаций действуют те же настройки origin и токена, что для MVT. Ответы получают `Cache-Control: no-store`.

Чтобы подключить или заменить архив, выполните `config validate`, `config plan` и `config apply`. План фиксирует контрольную сумму файла. При применении Martin открывает архив и проверяет формат и TileJSON до переключения шлюза. Для замены укажите путь к новому файлу и сохраните ID публикации, чтобы сохранить URL и права. Оставьте прежний архив по исходному пути для отката версии конфигурации.

### Настройка закрытых публикаций и локального CLI

Установите `access: private` в записи закрытой публикации в YAML. Персональные разрешения хранятся в PostgreSQL по постоянным ID пользователя и публикации. Чтобы назначить роль администратора для доступа к данным, укажите адрес пользователя в `auth.administrator_emails`. Роль действует после применения конфига для активной учётной записи с подтверждённым email.

Для локальных команд дополните существующий блок `auth` следующими полями.

```yaml
  administrator_emails: [administrator@example.org]
  cli:
    port: 8444
    ca_file: pki/cli-ca.pem
    cert_file: pki/cli-server.pem
    key_file: pki/cli-server-key.pem
    operators:
      operator: [diagnostics, users-read, access-write]
      agent: [diagnostics]
```

- Используйте отдельный центр сертификации для CLI. Сертификат сервера должен содержать `IP:127.0.0.1` в SAN и быть пригоден для серверной аутентификации. Для каждой локальной учётной записи выпустите отдельный клиентский сертификат с `clientAuth` и `CN`, совпадающим с именем записи в `operators`.
- Защитите каждый закрытый ключ правами ОС. У пользователя или агента должен быть доступ к своему ключу. Ключ центра сертификации храните отдельно. Удаление учётной записи из `operators` вступает в силу после применения конфига.
- Для локальной учётной записи задайте `GIS_ADMIN_PORT`, `GIS_ADMIN_CA_FILE`, `GIS_ADMIN_CERT_FILE` и `GIS_ADMIN_KEY_FILE`. В PowerShell используйте `$env:GIS_ADMIN_PORT = '8444'` и тот же синтаксис для путей. Административный порт публикуется на `127.0.0.1`.
- `diagnostics` разрешает `status` и `doctor` для проверки компонента доступа, шлюза, экземпляров сервис-провайдеров и источников публикаций. `users-read` разрешает `users list` и `tokens list`. `access-write` разрешает блокировку, разблокировку, выдачу и отзыв разрешений, а также `tokens revoke`. Для применения YAML действуют права ОС на рабочий каталог и Docker. Доступ к Docker нужен владельцу развёртывания.

```sh
node dist/cli.js users list --json
node dist/cli.js access grant parks-features --email reader@example.org
node dist/cli.js users block --user-id user-8
node dist/cli.js users unblock --user-id user-8
node dist/cli.js access revoke parks-features --user-id user-8
node dist/cli.js tokens list --email reader@example.org --json
node dist/cli.js tokens revoke token-17 --email reader@example.org
```

В JSON команды `users list` массив `data.users` содержит `id`, `email`, `name`, `registeredAt`, `status` и доступные `publications`. Статусы — `active`, `unverified` и `blocked`. У публикации `anonymous: true` означает доступ без действующей идентификации.

`access grant` с результатом `OK` подтверждает запись разрешения. Для проверки готовности пользователя к подключению найдите в `users list --json` его запись со статусом `active` и нужным ID в `publications`. При статусе `unverified` пользователь сначала подтверждает email. В режиме разработки письмо доступно в Mailpit на порту, заданном в `auth.mailpit_port`.

`tokens list --json` возвращает `data.userId` и массив `data.tokens` с ID, именами, датами создания и истечения и признаком `enabled`. Чтобы отозвать токен, передайте его ID и укажите владельца через `--email` или `--user-id`. Отзыв действует со следующего запроса. Пользователь создаёт токен в своём веб-сеансе и получает секрет один раз. [Подключение QGIS с токеном](README.md#персональный-токен-для-qgis)

Событие успешного изменения записывается в PostgreSQL вместе с изменением. Владелец развёртывания может посмотреть события `access.change` командой `docker compose logs access` с параметрами своего проекта. Событие содержит имя из проверенного клиентского сертификата, команду и ID затронутых объектов.

Журнал `caddy` содержит итоговый HTTP-код, ID запроса из `X-Request-Id` и ID отдельной публикации, если он есть. События `publication.request` в журнале `access` содержат тот же ID запроса, код решения о допуске и ID публикации. Для подтверждённой идентификации событие содержит ID пользователя и, при Bearer-аутентификации, ID токена. Секреты и данные недействительного токена в журнал не записываются.

### Обновление локального alpha-стенда

Начните с `docker compose ls --all`. По имени проекта и путям в `ConfigFiles` и монтированиях определите конфигурацию, каталог состояния и исходные данные действующего стенда. У локального `gis-platform-alpha` конфигурация и состояние находятся под `test_results/gis-platform-alpha/`.

Запустите `config plan` и `config apply` с `COMPOSE_PROJECT_NAME=gis-platform-alpha` и прежним `GIS_STATE_DIR`. Проверьте в плане публичный URL и список удаляемых публикаций. После применения проверьте публичный URL через Caddy, затем `doctor` и `users list` через CLI, если административный порт включён. Сохраняйте исходные файлы и тома при обновлении. Для автоматических проверок используйте временные проекты, описанные в [руководстве по тестированию](tests/README.md).

## Согласованный контракт первой версии

Этот раздел описывает целевой интерфейс, включая запланированные команды отката, диагностики и управления доступом. Доступные сейчас команды и границы их применения приведены выше. [Решение о CLI администратора](https://github.com/stepanosokin/gis-platform/issues/9)

### Запуск и права

Оператор и локальный ИИ-агент используют одну точку входа CLI на Node.js. CLI написан на TypeScript и может переиспользовать код проверки и типы компонента доступа. Команды запускаются локально в окружении развёртывания.

```bash
node dist/cli.js status
node dist/cli.js status --json
```

Агент работает под отдельной локальной учётной записью. Права на проверки состояния, чтение данных пользователей и изменения выдаются отдельно. Агент может сам выполнять делегированные команды. Журнал изменений фиксирует учётную запись, от имени которой выполнена команда. Те же команды доступны оператору в рамках его прав. Персональные токены пользователей предназначены для доступа к публикациям. [Решение об учётных записях и правах](https://github.com/stepanosokin/gis-platform/issues/6#issuecomment-6949343306).

### Конфигурация и диагностика

| Команда | Что делает |
| --- | --- |
| `config validate <file>` | Читает YAML, проверяет JSON Schema, ссылки на источники и экземпляры сервис-провайдеров, допустимые параметры и однозначность маршрутов. Проверка файла оставляет действующую версию в работе. |
| `config plan <file>` | Сравнивает полный YAML с действующей версией и выдаёт ID плана. Показывает добавленные, изменённые и удаляемые публикации, изменения публичных URL, компоненты к перезапуску и последствия для персональных разрешений. |
| `config plan --rollback-to <version>` | Готовит такой же план для сохранённой версии конфига. Показывает действующую версию, целевую версию и изменения, которые внесёт откат. |
| `config apply <plan-id>` | Применяет полный конфиг из плана. Проверяет, что план подготовлен для текущей версии. Перед переключением проверяет изменённые источники и подготовленные конфиги. |
| `status` | Показывает действующую версию и состояние платформы. После неполного восстановления показывает последнюю подтверждённую версию и маршруты, оставленные закрытыми. |
| `doctor [--publication <id>]` | Запускает диагностику платформы или одной публикации по её постоянному ID. Показывает, какая проверка прошла или завершилась ошибкой. Проверки охватывают доступность источника, сервис-провайдера и маршрут через шлюз, где это применимо. |

Пример изменения. Значение `plan-42` в примере возвращает команда `config plan`.

```bash
node dist/cli.js config validate platform.yaml
node dist/cli.js config plan platform.yaml
node dist/cli.js config apply plan-42
node dist/cli.js status
node dist/cli.js doctor --publication roads-features
```

#### Что происходит при применении

1. Просмотрите план до запуска `config apply`. План привязан к проверенному содержимому и к версии, действовавшей при его подготовке.
2. За один раз выполняется одно применение. Если другое применение ещё идёт или уже изменило действующую версию, CLI сообщает о конфликте. Проверьте текущую версию через `status` и постройте новый план.
3. Если предварительные проверки не прошли, действующая версия остаётся в работе. Временно недоступный источник в неизменённом экземпляре не блокирует изменение другого экземпляра. При изменении конфигурации экземпляра PostGIS проверяется доступ к его источникам.
4. На время переключения закрываются затронутые маршруты, в том числе маршруты перезапускаемых компонентов. После проверок шлюз открывает маршруты с правилами доступа новой версии.
5. Если переключение не удалось, платформа восстанавливает предыдущую рабочую конфигурацию. Если затронутые маршруты невозможно восстановить, они остаются закрытыми. Проверьте `status` и `doctor`.

Если связь с CLI оборвалась после запуска, проверьте `status --json` и повторите `config apply` с тем же ID. Для завершённой операции CLI возвращает сохранённый результат и текущую версию. После исправления причины завершившегося сбоя постройте новый план. После неполного восстановления новый план сначала завершает восстановление. [Решение о конфигурации и шлюзе](https://github.com/stepanosokin/gis-platform/issues/8#issuecomment-6950488601).

В выводе `status --json` поле `currentVersion` содержит последнюю подтверждённую версию, `previousVersion` — предыдущую, `pendingPlanId` — ID текущей операции, а `closedRoutes` — адреса, закрытые при переключении или восстановлении. Caddy возвращает `503` для закрытых маршрутов, пока слушает внешний порт. Локальный и делегированный CLI читают одно состояние. В каталоге `GIS_STATE_DIR` хранятся `status/active.json`, YAML, нативные конфиги и OpenAPI подтверждённых версий. При первом применении после обновления CLI переносит прежний `active.json` в каталог `status/`.

`doctor --json` показывает состояние шлюза в `data.gateway` и результаты по публикациям в `data.publications`. Статус шлюза — `ready`, `closed` или `unavailable`. У записи публикации есть `publicationId`, `instance` и `source`. Если экземпляр недоступен, проверка источника получает `unknown`. Владелец развёртывания может запустить `doctor` с доступом к Docker и `GIS_STATE_DIR`, оставив `GIS_ADMIN_PORT` незаданным. Для делегированного доступа нужна роль `diagnostics` и настроенный локальный административный порт.

При сбое PostGIS запросы к данным и TileJSON затронутой публикации получают `503 ServiceUnavailable`. Шлюз ждёт заголовки ответа провайдера PostGIS до 15 секунд. В каталоге OGC API у доступной пользователю публикации PostGIS появляется `status: unavailable`. После возвращения БД с прежней схемой новые запросы обслуживаются автоматически. После изменения схемы проверьте и примените обновлённый YAML.

При холодном старте экземпляр pygeoapi с PostGIS проверяет сохранённый OpenAPI. Если у экземпляра задан отдельный `readiness`, шлюз проверяет этот маршрут при применении изменившегося экземпляра.

#### Удаление и восстановление публикации

1. Чтобы удалить публикацию, уберите её запись из полного YAML. Для удаления всех публикаций задайте `publications: {}`. В плане проверьте `removed`, `routesToClose` и `personalGrants: delete` для удаляемых записей.
2. После успешного применения URL публикации возвращает `404`, публикация исчезает из каталога и OpenAPI, а её персональные разрешения удаляются. Файл источника остаётся доступен для других публикаций. При сбое до подтверждения удаления платформа восстанавливает предыдущую версию и её разрешения. Если результат удаления в БД пока неизвестен, маршруты остаются закрытыми. Повторите `config apply` с тем же ID после восстановления БД.
3. Чтобы вернуть ту же публикацию, подготовьте откат к версии, где она есть, или добавьте её обратно в полный YAML с прежним ID. Просмотрите все изменения в плане отката. ID зарезервирован за прежним источником и протоколом. Для другого источника или протокола задайте новый ID. При изменении названия URL сохраняется.
4. Выдайте нужные персональные разрешения через CLI. Откат конфига не меняет состояние учётных записей, токенов и разрешений в БД доступа.

```bash
node dist/cli.js config plan --rollback-to rev-12
node dist/cli.js config apply plan-43
node dist/cli.js access grant roads-features --email reader@example.org
```

### Пользователи, токены и разрешения

Команды, которым нужен конкретный пользователь, принимают один из двух параметров. `--email <email>` принимает email-логин, `--user-id <id>` — постоянный ID учётной записи. Отображаемое имя может повторяться. Смена email через CLI недоступна.

| Команда | Что делает |
| --- | --- |
| `users list` | Показывает email-логин, отображаемое имя, дату регистрации, статус учётной записи и доступные публикации для каждого пользователя. |
| `users block --email <email>` | Блокирует учётную запись. Блокировка действует со следующего нового запроса. |
| `users unblock --email <email>` | Снимает блокировку. Для защищённых публикаций продолжают действовать требования подтверждения email и текущих разрешений. |
| `tokens list --email <email>` | Показывает токены пользователя с их ID и именами. Секретные значения не выводятся. |
| `tokens revoke <token-id> --email <email>` | Отзывает указанный токен этого пользователя. Отзыв действует со следующего нового запроса. |
| `access grant <publication-id> --email <email>` | Выдаёт персональное разрешение на закрытую публикацию. Чтобы им воспользоваться, пользователю нужна активная учётная запись с подтверждённым email. |
| `access revoke <publication-id> --email <email>` | Удаляет персональное разрешение на публикацию. Изменение действует со следующего нового запроса. |

Доступные публикации в `users list` включают публичные публикации для всех пользователей. У заблокированного пользователя или пользователя без подтверждённого email для публичных публикаций указано, что доступ анонимный. Защищённые публикации показываются только при действующем доступе от имени учётной записи. Например, у заблокированного пользователя в списке останутся публичные карты с пометкой «анонимно». [Решение об учётных записях и правах](https://github.com/stepanosokin/gis-platform/issues/6#issuecomment-6949343306).

В примере оператор получает список токенов, отзывает один токен и отдельно снимает персональное разрешение на публикацию.

```bash
node dist/cli.js tokens list --email reader@example.org
node dist/cli.js tokens revoke token-17 --email reader@example.org
node dist/cli.js access revoke parks-maps --user-id user-8
```

### Машинный вывод

Добавьте `--json`, когда результат читает скрипт или агент. Команда пишет в `stdout` один JSON-объект. Поле `status` принимает `ok` или `error`, поле `code` содержит стабильный код результата, поле `data` — данные команды. Автоматизация проверяет код процесса и поле `code`. По умолчанию CLI выводит текст для человека.

Например, план построен для `rev-12`, но уже действует `rev-13`. `config apply plan-42 --json` завершится с кодом процесса `5`.

```json
{
  "status": "error",
  "code": "PLAN_STALE",
  "data": {
    "planId": "plan-42",
    "baseVersion": "rev-12",
    "currentVersion": "rev-13"
  }
}
```

| Код процесса | Поле `code` | Значение |
| --- | --- | --- |
| `0` | `OK`, `NO_CHANGE` | Успех или операция ничего не изменила. |
| `1` | `FAILED` | Прочий сбой. |
| `2` | `INVALID_INPUT`, `INVALID_CONFIG` | Неверные параметры команды или невалидный конфиг. |
| `3` | `NOT_FOUND` | Объект не найден, например пользователь, публикация, версия или план. |
| `4` | `FORBIDDEN` | У вызывающей учётной записи нет прав на операцию. |
| `5` | `PLAN_STALE`, `APPLY_IN_PROGRESS` | План устарел или другое применение ещё выполняется. |
| `6` | `APPLY_FAILED` | Операция с конфигурацией не удалась. Прежняя конфигурация действует. |
| `7` | `RECOVERY_INCOMPLETE` | Восстановление завершилось не полностью. Затронутые маршруты остаются закрытыми. |

При повторе завершённого `config apply` CLI возвращает код сохранённого результата. Версия, которую пыталась применить операция, может отличаться от текущей.

В текстовый и машинный вывод попадают только разрешённые поля. План может указать, что изменилась ссылка на секрет, а диагностика — что секрет недоступен. Значения секретов, строки подключения с паролями и содержимое токенов не выводятся. Доступ к данным из `users list` проверяется и в текстовом, и в машинном режиме.
