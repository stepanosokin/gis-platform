# Тестирование

Правила размещения тестов и результатов, а также выбора уровня проверок см. в [AGENTS.md](../AGENTS.md).

```sh
npm ci
npm test
```

`npm test` запускает полный локальный набор. Проверка типов, тесты CLI и HTTP-проверки публичной публикации выполняются в Docker. Проверки учётных записей запускаются из локального Node.js через опубликованный порт Caddy. Для публичной публикации и учётных записей создаются отдельные временные проекты Compose со свободными портами. После прогона их контейнеры и тома удаляются.

| Что проверить | Команда |
| --- | --- |
| Типы без Docker | `npm run typecheck` |
| Публичный CLI | `npm test -- --cli` |
| Применение YAML и чтение объекта через Caddy | `npm test -- --smoke` |
| Версии, переключение и восстановление через CLI и Caddy | `npm test -- --versions` |
| Экземпляры сервис-провайдеров через CLI, Caddy и Compose | `npm test -- --providers` |
| Динамические публикации внешнего PostGIS через CLI и Caddy | `npm test -- --postgis` |
| Ячейки H3 из одного представления PostGIS через Features и Martin | `npm test -- --h3` |
| Ячейки H3 из Parquet через DGGS и шлюз | `npm test -- --dggs` |
| Файловые источники Features и CRS через CLI и Caddy | `npm test -- --features-files` |
| Растровые публикации Maps через CLI и Caddy | `npm test -- --maps` |
| Динамические тайлы MVT и TileJSON через Martin, CLI и Caddy | `npm test -- --mvt` |
| Растровые и векторные MBTiles и PMTiles через Martin, CLI и Caddy | `npm test -- --raster-tiles` |
| Профиль OGC API — Tiles, метаданные и доступ через CLI и Caddy | `npm test -- --tiles` |
| Все сценарии регистрации и доступа | `npm test -- --access` |
| Один сценарий регистрации и доступа | `npm test -- --access HTTPS` |
| TLS на штатных портах 80 и 443 | `npm test -- --tls-standard` |
| Публикация портов Caddy без локальных переопределений | `npm test -- --tls-layout` |
| Зашифрованная копия, изолированное восстановление и актуальный доступ | `npm test -- --backup` |
| Закрытые публикации и локальный CLI | `npm test -- --private` |
| Один сценарий закрытых публикаций | `npm test -- --private 'personal grants'` |

Последний аргумент после `--access`, `--private`, `--versions`, `--providers`, `--h3`, `--dggs`, `--features-files`, `--maps`, `--mvt`, `--raster-tiles` или `--tiles` задаёт фильтр Node.js по имени теста. Путь к результатам указан в строке `Results:`. Раннер сохраняет вывод каждой команды после её завершения.

При разборе нестабильного теста повторите сценарий отдельно. Разные временные проекты Compose используют общий `dist/` рабочей копии и общий тег тестового образа Docker. Отдельный прогон исключает пересборку этих файлов и образа другим прогоном.

Целевые команды из таблицы подходят для цикла red → green и проверки исправлений по ревью. Дождитесь завершения запущенного прогона перед изменением исходников. Compose может пересобрать образ компонента доступа во время восстановления. Итоговый `npm test` запускайте после последних правок, чтобы все группы тестов проверяли одно состояние рабочей копии.

## Локальная приёмка первой версии

Для [#33](https://github.com/stepanosokin/gis-platform/issues/33) выбран средний уровень. Полный прогон проверяет сценарии [стартовой спецификации](https://github.com/stepanosokin/gis-platform/issues/13) на временных проектах Docker Compose. HTTP-клиенты обращаются к внешнему Caddy, оператор использует публичный CLI, а браузер и открытый QGIS выполняют связанные запросы со своими настройками доступа.

1. Подготовьте restic, Chrome с актуальной стабильной MapLibre GL JS, открытый QGIS 3.44 LTR и Python 3. Для полного прогона установите `GIS_TEST_CHROME`, `GIS_TEST_MAPLIBRE_DIST`, `GIS_QGIS_MCP=1` и `GIS_TEST_PYTHON` с путём к исполняемому файлу Python. Укажите `GIS_RESTIC_EXECUTABLE`, если restic отсутствует в `PATH`.
2. Выполните `npm test`. Проверьте итог всех групп и отсутствие пропусков QGIS и MapLibre. В каталоге из строки `Results:` найдите журналы `test-*.log`, браузерные результаты и два отчёта Python `acceptance-maps-features.json` и `acceptance-dggs.json`. Отдельно запустите `npm test -- --tls-standard`, если свободны порты 80 и 443.
3. Запишите версии клиентов, Docker и сервис-провайдеров, digest образов или ID локально собранных образов, версии `better-auth` и `@better-auth/api-key` из lockfile, режимы доступа, поддержанные сценарии, число публикаций и объектов. Для Maps запишите размеры исходных растров и подтверждённых PNG. Для DGGS запишите разрешение H3, bbox, лимит и число возвращённых ячеек на обоих наборах.

С заданным `GIS_TEST_PYTHON` тесты Maps и DGGS после проверок содержимого запускают замер через внешний HTTP или доверенный HTTPS. Четыре клиента в течение примерно восьми секунд каждый обходят запросы своего профиля. До нагрузки выполняется один прогрев на запрос. Время включает получение полного ответа, включая сетевое соединение. Отчёт содержит число ответов, p50, p95, максимум и размеры тел. Неверный HTTP-статус, число объектов или размер PNG прерывают замер. Для отдельной проверки самого измерительного клиента выполните `node --test tests/acceptance.test.mjs`.

В отчёты входят выборки `docker stats` с CPU, памятью и накопленным блочным вводом-выводом по контейнерам временного проекта. Размер их записываемых слоёв берётся из `docker inspect --size` после нагрузки. Отдельно запишите размеры тестовых файлов и свободное место на хосте. Записываемый слой не включает именованные тома и смонтированные файлы. Сохраняйте протокол и материалы прогона в `test_results/`.

Перед пилотом оператор проверяет доступ экземпляров к внешним источникам с фактическими правами на чтение, DNS до шлюза с клиентской сети, сертификат и цепочку доверия, а также доставку писем подтверждения и восстановления через SMTP-реле. Он проверяет запись и чтение копии на отдельном хосте и восстановление в отдельном стеке. Замеры повторяются на данных и при одновременной нагрузке пилота с наблюдением за задержкой, ошибками, CPU, памятью, диском и ростом томов. Численные цели для production согласуются по этим данным.

## Внешний HTTP и HTTPS

Для [#31](https://github.com/stepanosokin/gis-platform/issues/31) выбран полный уровень. `npm test -- --access 'TLS rejects|HTTPS serves'` использует временный Compose-проект и свободные порты loopback. Тесты создают доверенный корень, промежуточный сертификат и сертификаты сервера. Проверки покрывают отказ при неверной настройке, текущую версию и первый запуск, перенаправление, ссылки и OpenAPI, письма Mailpit, cookie, диагностику срока, замену сертификата, откат и возврат на HTTP. Результаты сохраняются в `test-access.log`.

`npm test -- --tls-standard` проверяет тот же переход с `server.host: localhost` без `server.port`. Для него должны быть свободны локальные TCP-порты 80 и 443. Caddy публикует оба порта только на loopback. В полном прогоне используются свободные порты, поэтому два постоянных порта можно проверять отдельной командой.

`npm test -- --tls-layout` проверяет конфигурацию Compose с внешними портами 80 и 443 без ограничения loopback. Команда не запускает контейнеры и входит в полный прогон.

Откат конфига проверяется по тем же URL и остаётся на восстановленной актуальной БД. Результаты — в `test-backup.log`.

## Динамические публикации PostGIS

Для #21 выбран полный уровень. Тесты CLI проверяют бюджет свежести и обязательное подключение экземпляра. Сценарий `--postgis` запускает временный проект Compose с внешним PostGIS и двумя учётными записями только для чтения. Он проверяет обновления по тому же URL после COMMIT, допуск к CQL2 JSON, фильтры и OpenAPI, независимые подключения, недоступность источника и отказ применения неверного подключения. Используется локальный образ `postgis/postgis:18-3.6`. Результат сохранён в `test-postgis.log`.

При ошибке `APPLY_FAILED` ищите нативный YAML экземпляра и `compose.providers.json` в `postgis-state/plans/<plan-id>/`. Для дополнительного экземпляра нативный YAML лежит в каталоге `provider-<id>/`. Если есть файл `provider-directory`, он указывает версию нативных файлов, которую смонтировал Compose.

При сбое чтения PostGIS сравните запрос списка и запрос заведомо существующего объекта по ID. Оба должны вернуть `503 ServiceUnavailable`. После восстановления источника запрос отсутствующего ID должен вернуть `404`.

Для #28 выбран полный уровень. Прогон `--postgis` останавливает одну из двух независимых внешних БД, проверяет холодный старт по сохранённому OpenAPI, изоляцию отказа, статусы в каталогах с разными правами, восстановление по тому же URL, изменение схемы и диагностику через CLI. Прогон `--mvt` проверяет холодный старт и восстановление одной внешней БД, пока другие экземпляры Martin читают вторую БД и архив. Сценарии `--versions` и `--private` проверяют закрытие маршрутов при переключении и делегированный доступ к диагностике.

## Ячейки H3 из Parquet

Для [#30](https://github.com/stepanosokin/gis-platform/issues/30) выбран полный уровень. `npm test -- --dggs` создаёт снимки в `test_results/`, применяет YAML во временном Compose и запрашивает данные и геометрию через Caddy по HTTPS. Тест проверяет точные показатели `BIGINT` в безопасном диапазоне целых JSON, три режима доступа, ссылки, Swagger и OpenAPI, отклонение дублированного ID и неподдерживаемого `INTEGER`, замену снимка и откат через CLI. Запускайте сценарий целиком. Вложенные проверки используют один стек последовательно. Результат записывается в `test-dggs.log`.

Нативная проверка точности за пределами безопасного диапазона запускается отдельно в контейнере Linux amd64 с pydggsapi 0.4.0. Снимки Parquet подключаются только для чтения. Геометрия сверяется с WKB границ H3. Первый запуск DuckDB внутри контейнера загружает расширение `httpfs`.

Команды PowerShell из корня репозитория.

```powershell
$image = 'ghcr.io/landscapegeoinformatics/pydggsapi@sha256:2c2b1683a474243639d59849679e32a434ab5581a7e54ce02879213bf509ea63'
$script = (Resolve-Path tests/pydggsapi-acceptance.py).Path
$results = (New-Item -ItemType Directory -Force "test_results/issue-30-native-$([guid]::NewGuid())").FullName
docker run --rm --platform linux/amd64 --mount "type=bind,src=$script,dst=/probe.py,readonly" --mount "type=bind,src=$results,dst=/fixture" $image python /probe.py fixtures
if ($LASTEXITCODE -ne 0) { throw 'Не созданы снимки Parquet' }
docker run --rm --platform linux/amd64 --mount "type=bind,src=$script,dst=/probe.py,readonly" --mount "type=bind,src=$results,dst=/fixture,readonly" $image python /probe.py check
```

Запрос `GET /dggs-api/collections/sparse/dggs/h3/zones/871ea541affffff/data?zone-depth=0` с `Accept: */*` возвращает HTTP 200 и число `9007199254740992` в `values["sparse.tally"][0].data[0]`. Parquet содержит `BIGINT` со значением `9007199254740993`. В pydggsapi 0.4.0 целые показатели проходят через тип с плавающей точкой. Ожидаемый результат команды `check` на этом образе — код выхода 1 и ошибка утверждения с двумя указанными числами. Это согласованное ограничение профиля за пределами безопасного диапазона JSON. [Воспроизведение #30](https://github.com/stepanosokin/gis-platform/issues/30#issuecomment-7059798430) · [Преобразование показателей в pydggsapi 0.4.0](https://github.com/LandscapeGeoinformatics/pydggsapi/blob/v0.4.0/pydggsapi/models/ogc_dggs/data_retrieval.py)

Для H3 уровня 7 запросы `f=geojson&geometry=zone-region&zone-level=7&compact-zones=false` дали следующие результаты. Полнота подтверждена для указанных окон и лимитов.

| bbox в порядке запад, юг, восток, север | Лимит | Плотный снимок, получено / ожидалось | Разреженный снимок, получено / ожидалось |
| --- | --- | ---: | ---: |
| `12.28,45.41,12.36,45.47` | По умолчанию | 13 / 13 | 3 / 3 |
| `11.8,45.0,12.9,45.9` | По умолчанию | 1 000 / 1 732 | 36 / 63 |
| `11.8,45.0,12.9,45.9` | `10000` | 1 732 / 1 732 | 63 / 63 |

В GeoJSON лимит отсекает геометрии кандидатов до отбора строк снимка. Даже короткий список ячеек может быть неполным. Для более широкого окна согласованный профиль предусматривает деление bbox. [Формирование списка зон в pydggsapi 0.4.0](https://github.com/LandscapeGeoinformatics/pydggsapi/blob/v0.4.0/pydggsapi/models/ogc_dggs/zone_query.py)

На том же образе `INTEGER` со значением `16777217` дал `16777216` при чтении с глубиной 0. CLI отклоняет `INTEGER` и принимает целочисленные показатели в формате `BIGINT`.

При ручной диагностике проверьте готовность API по `/dggs-api/collections` и отправляйте `Accept: */*` в запросах к зонам. Без заголовка эти маршруты могут вернуть HTTP 406. При ошибке `Read-only file system` для TinyDB используйте временную копию JSON-конфигурации с правом записи. Снимки Parquet подключайте только для чтения.

## Файловые источники Features и CRS

Для #22 выбран полный уровень. Прогон создаёт GeoPackage, Shapefile в EPSG:3857 и GeoParquet с WKB в `test_results/`, применяет YAML во временном проекте Compose и обращается к Caddy по HTTP. Сценарии проверяют выбор слоя и ID, пагинацию, частичное пересечение bbox и пустой результат внутри отверстия полигона, временной отбор GeoParquet, сведения о фильтрах, отказ для отсутствующего sidecar и неизвестной CRS. Тесты проверяют координаты и порядок осей CRS84 и EPSG:4326, а также EPSG:3857, ESRI:102026, EPSG:5041 и дополнительно настроенной EPSG:32637.

Если первый HTTP-запрос после `config apply` завершается `ECONNRESET`, проверьте его на новом соединении. Compose может пересоздать Caddy, пока Node.js ещё хранит прежнее соединение в пуле `fetch`. При проверках, которые переключают версии стека во время прогона, добавляйте заголовок `Connection: close`, как в [сценариях файловых публикаций](features-files.test.mjs).

При проверке первого запроса после переключения по HTTPS используйте `node:https` с `agent: false`, как в [тесте DGGS](dggs.test.mjs). В Node 26 заголовок `Connection: close` в `fetch` не устранил сброс старого HTTP/2-соединения. Новый TLS-сеанс позволяет проверить результат первого запроса без повторов.

## QGIS Desktop

В открытом QGIS тест подключается анонимно через окно WFS / OGC API – Features, затем обновляет аутентификацию в том же окне. Два сценария проверяют cookie веб-сеанса и именованный Bearer-токен. Закрытая публикация должна появиться без перезапуска QGIS. Провайдер OGC API – Features должен прочитать три объекта.

Перед полным прогоном с QGIS проверьте две предпосылки.

1. Откройте QGIS на хосте и запустите сервер плагина. Вызовите `qgis_mcp` → `diagnose`, чтобы проверить связь с нужным процессом.
2. Разблокируйте менеджер аутентификации. Через `qgis_mcp` → `execute_code` можно проверить состояние двумя строками `from qgis.core import QgsApplication` и `print(QgsApplication.authManager().masterPasswordIsSet())`. Ожидается `True`. Если рабочий профиль недоступен, используйте отдельный профиль QGIS в `test_results/`, включите в нём плагин и задайте тестовый мастер-пароль.

Запускайте команды в той же ОС, что и QGIS. В Windows используйте PowerShell. `npm test` автоматически включает проверки QGIS, когда локальный порт плагина доступен. Доступность порта подтверждает связь с плагином. Состояние менеджера аутентификации проверяется отдельно. Для отдельного прогона используйте `npm test -- --qgis`. Для полного прогона задайте `GIS_QGIS_MCP=1`, чтобы потребовать QGIS, или `GIS_QGIS_MCP=0`, чтобы пропустить его.

Нужен `uvx` и локально закешированный пакет `qgis-mcp-server` для источника QGIS MCP. По умолчанию используется архив репозитория плагина, как в конфигурации Codex. При другом источнике задайте `GIS_QGIS_MCP_SOURCE` тем же значением, которое передаёте `uvx --from`. Для порта плагина, отличного от `9876`, задайте `QGIS_MCP_PORT`. Тест использует отдельный временный проект Compose. Он удаляет тестовое подключение и тестовую конфигурацию аутентификации. Результат сохраняется в `test-qgis.log`.

Если закрытый слой пропал из списка, сначала проверьте статус и разрешение пользователя через [CLI администратора](../ADMIN.md#настройка-закрытых-публикаций-и-локального-cli). Когда доступ есть, выполните проверки в открытом QGIS.

1. Проверьте связь с нужным процессом QGIS и готовность менеджера аутентификации по шагам выше.
2. Сравните ответ внешнего каталога `/features/collections?f=json` анонимно и с аутентификацией сохранённого подключения QGIS. Для диагностики достаточно кода HTTP и ID коллекций. Храните секрет токена или cookie в локальном процессе.
3. В том же окне подключения WFS / OGC API – Features повторите подключение после обновления авторизации. Сверьте ID в колонке **Имя**. Колонка **Заголовок** может показывать, например, `Example places (private)` для ID `places-private`. Затем проверьте чтение объектов через провайдер OGC API – Features.

## Диагностика Docker

Перед сквозным прогоном проверь доступ к движку командой `docker info --format '{{.ServerVersion}}'`. Если Docker Desktop остановлен, запусти его командой `docker desktop start` и дождись, пока `docker info` вернёт версию сервера. Для отдельного прогона из WSL проверь через `wsl --list --verbose`, что доступен пользовательский дистрибутив и в нём работает Docker. Результат запуска из PowerShell указывай как прогон с Docker Desktop.

Если в Windows отказано в доступе к каналу `dockerDesktopLinuxEngine` или запуск дочернего Node.js завершается `spawnSync ... EPERM`, проверь разрешения локального запуска. Эти ошибки могут возникнуть до старта стека и HTTP-запросов.

| Что искать в каталоге прогона | Публичная публикация и версии | Регистрация и доступ | Закрытые публикации и токены |
| --- | --- | --- | --- |
| Вывод `config apply` | `apply.log` | `apply-access.log` | `apply-private.log` |
| Вывод тестов | `test-http.log`, `test-versions.log` | `test-access.log` | `test-private.log` |
| Сгенерированные конфиги | `state/plans/<plan-id>/` | `access-state/plans/<plan-id>/` | `private-state/plans/<plan-id>/` |

При сбое применения начни с лога `config apply`. Откат может удалить контейнеры до сбора логов сервисов. Для повторной диагностики используй копию данных и сгенерированные конфиги в отдельном проекте Compose. Сохрани вывод `docker compose logs --no-color` в каталог прогона до удаления контейнеров.
