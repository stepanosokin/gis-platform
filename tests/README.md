# Тестирование

Правила размещения тестов и результатов, а также выбора уровня проверок см. в [AGENTS.md](../AGENTS.md).

```sh
npm ci
npm test
```

`npm test` запускает полный локальный набор. Проверка типов, тесты CLI и HTTP-проверки публичной публикации выполняются в Docker. Проверки учётных записей запускаются из локального Node.js через опубликованный порт Caddy. Для публичной публикации и учётных записей создаются отдельные временные проекты Compose со свободными портами. После прогона их контейнеры и тома удаляются.

| Что проверить | Команда |
| --- | --- |
| Типы без Docker | `npm run typecheck` |
| Публичный CLI | `npm test -- --cli` |
| Применение YAML и чтение объекта через Caddy | `npm test -- --smoke` |
| Все сценарии регистрации и доступа | `npm test -- --access` |
| Один сценарий регистрации и доступа | `npm test -- --access HTTPS` |
| Закрытые публикации и локальный CLI | `npm test -- --private` |
| Один сценарий закрытых публикаций | `npm test -- --private 'personal grants'` |
| Обнаружение закрытого слоя в открытом QGIS через QGIS MCP | `npm test -- --qgis` |

Последний аргумент после `--access` или `--private` задаёт фильтр Node.js по имени теста. Путь к результатам указан в строке `Results:`. Раннер сохраняет вывод каждой команды после её завершения.

## Публикация GeoJSON через Features

Согласованный уровень для задачи #14 — средний. Пять сценариев проверяют публичный CLI, семь проверяют выдачу через Caddy на реальном стеке Compose.

## Регистрация и доступ к сервису по регистрации

Для задачи #15 выбран полный уровень. Восемь сквозных сценариев проверяют регистрацию и подтверждение email, профиль, смену и восстановление пароля с отзывом сеансов, каталог и связанные URL, блокировку, сохранение учётных записей, отказы компонента доступа и cookie по HTTPS. Письма проверяются через Mailpit. Проверки доступа, каталога, OpenAPI и ссылок выполняются по внешнему адресу Caddy. В полном прогоне эти сценарии дополняют 12 существующих тестов. Тестовые секреты и сертификат хранятся в каталоге прогона под `test_results/`.

При согласовании проверок изменений шлюза учтите выявленные в #15 сценарии.

- Откройте ссылки из каталога и согласованные представления, например JSON-LD по ссылке и заголовку `Accept`. Сравните выдачу с действующим сеансом и в анонимном запросе.
- При остановке компонента доступа или его хранилища проверьте ответ на вход и запрос к защищённой публикации с cookie и без неё. Отдельно проверьте доступность публичных данных.
- Когда HTML сервис-провайдера и страницы учётной записи доступны по одному адресу платформы, проверьте Content Security Policy на публичных и защищённых HTML-страницах провайдера.

## Закрытые публикации и CLI управления доступом

Для #16 выбран полный уровень. Восемь сценариев проверяют выдачу и отзыв разрешений, блокировку, данные и метаданные через Caddy, ошибки `401`, `403` и `503`, а также делегирование под разными Linux-учётными записями и журнал изменений. Тесты используют отдельный временный проект Compose. Ищите `apply-private.log`, `test-private.log` и `private-state/plans/<plan-id>/`. Одноразовые ключи CLI хранятся в каталоге прогона под `test_results/`.

Для диагностики делегирования запустите `npm test -- --private 'separate local accounts'`. Ошибка `useradd: group operator exists` возникает при подготовке Linux-контейнера, до запуска CLI. При добавлении тестовых учётных записей используйте существующую группу `users`, как в [тестовом скрипте](cli-local-accounts.sh).

## QGIS Desktop

Согласован средний уровень. В открытом QGIS тест подключается анонимно через окно WFS / OGC API – Features, затем добавляет cookie в временную конфигурацию аутентификации и обновляет то же окно. Закрытая публикация должна появиться без перезапуска QGIS. Провайдер OGC API – Features должен прочитать три объекта.

Откройте QGIS на хосте, запустите сервер плагина QGIS MCP и разблокируйте менеджер аутентификации. Запускайте команды в той же ОС, что и QGIS. Для QGIS под Windows используйте PowerShell. `npm test` автоматически включает эту проверку, когда локальный порт плагина доступен. Команда `npm test -- --qgis` запускает её отдельно и требует работающего плагина. Для полного прогона можно явно потребовать QGIS через `GIS_QGIS_MCP=1` или пропустить его через `GIS_QGIS_MCP=0`.

Нужен `uvx` и локально закешированный пакет `qgis-mcp-server` для источника QGIS MCP. По умолчанию используется архив репозитория плагина, как в конфигурации Codex. При другом источнике задайте `GIS_QGIS_MCP_SOURCE` тем же значением, которое передаёте `uvx --from`. Для порта плагина, отличного от `9876`, задайте `QGIS_MCP_PORT`. Тест использует отдельный временный проект Compose. Он удаляет тестовое подключение и тестовую конфигурацию аутентификации. Результат сохраняется в `test-qgis.log`.

Если закрытый слой пропал из списка, сначала проверьте статус и разрешение пользователя через [CLI администратора](../ADMIN.md#настройка-закрытых-публикаций-и-локального-cli). Когда доступ есть, выполните проверки в открытом QGIS.

1. Вызовите `qgis_mcp` `diagnose` для проверки связи с нужным процессом QGIS.
2. Сравните ответ внешнего каталога `/features/collections?f=json` без сессии и с аутентификацией сохранённого подключения QGIS. Для диагностики достаточно кода HTTP и ID коллекций. Храните cookie в локальном процессе.
3. В том же окне подключения WFS / OGC API – Features повторите подключение после обновления авторизации. Сверьте ID в колонке **Имя**. Колонка **Заголовок** может показывать, например, `Example places (private)` для ID `places-private`. Затем проверьте чтение объектов через провайдер OGC API – Features.

## Диагностика Docker

Перед сквозным прогоном проверь доступ к движку командой `docker info --format '{{.ServerVersion}}'`. Для отдельного прогона из WSL проверь через `wsl --list --verbose`, что доступен пользовательский дистрибутив и в нём работает Docker. Результат запуска из PowerShell указывай как прогон с Docker Desktop.

Если в Windows отказано в доступе к каналу `dockerDesktopLinuxEngine` или запуск дочернего Node.js завершается `spawnSync ... EPERM`, проверь разрешения локального запуска. Эти ошибки могут возникнуть до старта стека и HTTP-запросов.

| Что искать в каталоге прогона | Публичная публикация | Регистрация и доступ |
| --- | --- | --- |
| Вывод `config apply` | `apply.log` | `apply-access.log` |
| Вывод HTTP-тестов | `test-http.log` | `test-access.log` |
| Сгенерированные конфиги | `state/plans/<plan-id>/` | `access-state/plans/<plan-id>/` |

При сбое применения начни с лога `config apply`. Откат может удалить контейнеры до сбора логов сервисов. Для повторной диагностики используй копию данных и сгенерированные конфиги в отдельном проекте Compose. Сохрани вывод `docker compose logs --no-color` в каталог прогона до удаления контейнеров.
