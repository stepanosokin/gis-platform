# Авторизация, регистрация и разграничение доступа

Исследование для задачи [Проверить авторизацию, регистрацию и разграничение доступа](https://github.com/stepanosokin/gis-platform/issues/4), ведущий разработчик — stepanosokin. Дата проверки: 2026-11-17. Метод: официальная документация, спецификации и исходные документы проектов. Приложение не запускалось, запросы к развёрнутым сервисам не проверялись. Ни один вариант архитектуры этим документом не утверждается.

## Что установлено

Встроенной защиты ядра недостаточно: **pygeoapi 0.24.0 прямо исключает встроенный контроль доступа**, а **Martin 1.16.1 не аутентифицирует запросы** и предлагает проверку через NGINX. Следовательно, требование использовать встроенную авторизацию там, где она есть, не устраняет внешнюю проверку перед обоими серверами. Документ Martin проверен по тегу релиза через GitHub API; текущий сайт документации уже показывает beta 2.0, поэтому он не использован для вывода о стабильной версии. [pygeoapi stable: Security](https://docs.pygeoapi.io/en/stable/security.html), [Martin 1.16.1: NGINX](https://github.com/maplibre/martin/blob/martin-v1.16.1/docs/content/run-with-nginx.md).

Это подтверждает отсутствие встроенного решения в выбранном ядре, но не доказывает безопасность конкретной будущей конфигурации. Для сторонних компонентов ниже проверены документированные возможности, а не совместимость зафиксированного набора Docker-образов. `latest`-страницы меняются; перед имплементацией нужны конкретные версии и повторная проверка настроек.

## Исходные требования проекта

Обязательны pygeoapi и Martin в Docker, единый шлюз для внешних запросов, логин/пароль и токены, простые страницы регистрации и управления токенами, подтверждение email. Администратор управляет правами через конфигурацию либо БД; выбор ещё открыт. Доступ назначается **сервису публикации**, поэтому две публикации одного набора данных могут иметь разные права. CLI должен показывать логин, email, дату регистрации и доступные сервисы. Учёт запросов и биллинг пока не реализуются.

Предлагаемая трактовка требований, требующая закрепления в спецификации:

| Режим сервиса публикации | Кто получает доступ |
| --- | --- |
| Публичный | Любой, включая анонимного пользователя |
| Для зарегистрированных | Активный зарегистрированный пользователь с подтверждённым email |
| Закрытый | Активный пользователь с подтверждённым email из списка допуска именно этого сервиса |

Удобный постоянный ключ допуска — внутренний идентификатор пользователя; логин и email могут измениться. Проверка прав использует идентификатор сервиса публикации, а не имя таблицы или файла. Например, публикации `roads-features` и `roads-tiles` одного набора данных оцениваются независимо. Это проектное предложение, не встроенная возможность pygeoapi/Martin.

## Различать механизмы

- **Аутентификация** устанавливает личность; **авторизация** решает, разрешён ли доступ к конкретному ресурсу. Одного успешного входа недостаточно для закрытой публикации. [pygeoapi: Security and access control](https://dive.pygeoapi.io/advanced/security-access-control/).
- **HTTP Basic** передаёт логин и пароль в Base64; это не шифрование. Защита канала требует TLS. Сам Basic не предоставляет регистрацию, подтверждение email или отзыв отдельного токена. [RFC 7617](https://datatracker.ietf.org/doc/html/rfc7617).
- **Bearer** означает доступ по владению токеном; не означает обязательно JWT или OAuth. Токен следует передавать в заголовке, не помещать в ссылки и журналы: RFC отдельно описывает утечки через URL. [RFC 6750](https://datatracker.ietf.org/doc/html/rfc6750).
- **API key** здесь — прикладной секрет для программного клиента; правила выдачи, срока, хранения и отзыва необходимо определить отдельно. OpenAPI описывает API key как отдельную схему безопасности; описание схемы само по себе не проверяет запросы. [OpenAPI 3.1: Security Scheme](https://spec.openapis.org/oas/v3.1.0.html#security-scheme-object).
- **OIDC** — протокол входа поверх OAuth 2.0. ID token сообщает приложению о входе; доступ к API должен использовать предназначенный этому API access token и отдельную проверку прав. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html).

Логин/пароль не требует Basic на каждом запросе. В варианте OIDC пользователь вводит пароль на странице поставщика идентификации, затем клиент получает токены. Для браузера следует рассмотреть Authorization Code с PKCE; password grant нельзя выбирать ради простого UI: актуальная рекомендация OAuth запрещает этот grant. [RFC 9700, разделы 2.1.1 и 2.4](https://datatracker.ietf.org/doc/html/rfc9700).

## Небольшой набор вариантов

Оценки сложности ниже — вывод исследования, а не измерение ресурсов или готовности к эксплуатации.

На дату проверки официальный Keycloak предлагает релиз 26.8.2; у allauth опубликован 65.22.1 от 2026-11-13. Django 5.2 LTS имеет extended support до апреля 2028; allauth указывает Django 4.2+ среди требований, но это не делает уже неподдерживаемую ветку Django 4.2 подходящим выбором. Наличие релиза не является обещанием SLA или сроков исправления уязвимостей. Для сравнения использована документация Django 5.2 и текущая документация allauth/Keycloak; точный состав зависимостей ещё не выбран. [Keycloak downloads](https://www.keycloak.org/downloads), [allauth release notes](https://docs.allauth.org/en/latest/release-notes/recent.html), [Django supported versions](https://www.djangoproject.com/download/), [allauth requirements](https://docs.allauth.org/en/latest/installation/requirements.html).

Рассмотренные основы открыты: Django — BSD, allauth — MIT, Keycloak — Apache 2.0. Лицензии конкретных добавляемых зависимостей проверяются при выборе состава. [Django](https://www.djangoproject.com/download/), [allauth LICENSE](https://github.com/pennersr/django-allauth/blob/main/LICENSE), [Keycloak LICENSE](https://github.com/keycloak/keycloak/blob/main/LICENSE.txt).

| Вариант | Что уже есть | Что остаётся разработать / подтвердить | Цена сложности |
| --- | --- | --- | --- |
| Только ядро и Basic на шлюзе | Защита отдельных маршрутов паролем | Регистрация, email, токены, CLI и модель прав остаются снаружи | Не закрывает требования как самостоятельный вариант |
| Шлюз + небольшое приложение Django + django-allauth | Учётные записи и пароли Django; готовые формы входа/регистрации/восстановления allauth; обязательное подтверждение email настраивается | Решение доступа для шлюза, права публикаций, UI и жизненный цикл персональных токенов, CLI | Меньше отдельных систем, больше прикладной ответственности |
| Шлюз + Keycloak + небольшой адаптер прав | OIDC, формы входа/саморегистрации, email verification, управление пользователями и сессиями | Привязка маршрутов к сервисам публикации, общий расчёт прав, CLI сводки; пользовательская страница токенов под выбранную модель | Больше настроек и отдельный IdP, меньше собственной логики учётных данных |

Основания для строки Django: встроенная система предоставляет пользователей, хеширование паролей и сессии; allauth предоставляет необходимые страницы. `ACCOUNT_EMAIL_VERIFICATION="mandatory"` блокирует вход до подтверждения и требует обязательного email в полях регистрации. Это необходимо явно включить: значение по умолчанию — `optional`. [Django: authentication](https://docs.djangoproject.com/en/5.2/topics/auth/default/), [allauth: views](https://docs.allauth.org/en/latest/account/views.html), [allauth: configuration](https://docs.allauth.org/en/latest/account/configuration.html).

Простейший DRF `TokenAuthentication` не следует считать готовым менеджером персональных токенов: документация указывает ограниченную реализацию и отсылает к отдельному пакету для нескольких токенов и срока действия. Его стандартный заголовок — `Authorization: Token …`; префикс Bearer требует настройки. Конкретный механизм токенов в варианте Django остаётся открытым. [DRF: authentication](https://www.django-rest-framework.org/api-guide/authentication/).

Основания для строки Keycloak: имеются саморегистрация, required action Verify Email и SMTP; Admin API предоставляет пользователей, роли и группы. Доступен официальный контейнер с настройкой внешней БД. Это не означает, что Keycloak автоматически ограничит маршруты Martin/pygeoapi. [Keycloak: Server Administration](https://www.keycloak.org/docs/latest/server_admin/), [Admin REST API](https://www.keycloak.org/docs-api/latest/rest-api/index.html), [контейнер](https://www.keycloak.org/server/containers).

Keycloak выдаёт access/refresh tokens, имеет introspection и revocation endpoints. Готовый OIDC-вход не равен UI персональных долгоживущих API-токенов: надо выбрать короткие access tokens с обновлением либо отдельные персональные токены. Передавать refresh token в геосервисы не требуется. [Keycloak: OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers).

`oauth2-proxy` можно использовать как адаптер OIDC для шлюза: документированы группы и проверка verified email. Его наличие не заменяет согласованное правило допуска к каждому сервису. Если небольшой адаптер уже реализует вход/проверку, дополнительный прокси не обязателен. [OAuth2 Proxy: configuration](https://oauth2-proxy.github.io/oauth2-proxy/configuration/overview/).

### Почему не считать расширения pygeoapi готовым решением

Официальная документация pygeoapi указывает `fastgeoapi`, `pygeoapi-auth-deployment` и `pygeoapi-auth` как сторонние проекты. Это ссылка на интеграции, а не перенос их функций в pygeoapi. [Security](https://docs.pygeoapi.io/en/stable/security.html).

- `pygeoapi-auth-deployment` показывает Docker, Authelia, NGINX/Caddy, файловых/LDAP-пользователей и групповые правила. В проверенном README нет доказательства полного требуемого цикла саморегистрации, обязательного подтверждения email и управления персональными токенами; это **не установленное отсутствие** возможностей всех зависимостей. Для проекта такой цикл пришлось бы дополнительно доказать. [README](https://github.com/cartologic/pygeoapi-auth-deployment).
- У `pygeoapi-auth` документированный CLI внедряет security-схемы в OpenAPI по конфигурации Authelia. Это инструмент описания API; считать его самостоятельным сервером аутентификации нельзя. [README](https://github.com/geopython/pygeoapi-auth).
- `fastgeoapi` заявляет OIDC/JWT, API keys и OPA поверх pygeoapi. Эти возможности относятся к дополнительной оболочке, не закрывают автоматически второй обязательный сервер Martin и пользовательский жизненный цикл. В рамках минимального выбора не добавлять одновременно fastgeoapi и отдельный policy engine без доказанной необходимости. Совместимость конкретного релиза не проверена. [README](https://github.com/geobeyond/fastgeoapi).

## Общая граница доступа для обоих вариантов

Предложение: шлюз определяет сервис публикации по нормализованному маршруту и спрашивает компонент доступа о пользователе, состоянии email и правах. В NGINX OSS для этого есть `auth_request`: 2xx разрешает запрос, 401/403 запрещают, прочие статусы считаются ошибкой. Модуль не включён в сборку по умолчанию; наличие необходимо проверить в выбранном образе. [NGINX auth_request](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html).

Шлюз не должен сводить решение к «токен корректно подписан». Требуются срок, issuer/audience для OIDC, активность учётной записи, подтверждение email и актуальные права сервиса. Состояние `email_verified` предусмотрено OIDC, но приложение должно использовать его осознанно. [OIDC Core, standard claims и validation](https://openid.net/specs/openid-connect-core-1_0.html).

Предлагаемые ограничения, которые следует закрепить в спецификации:

1. Публиковать наружу только шлюз. Не открывать порты Martin, pygeoapi, БД и внутренней проверки доступа. Docker при публикации порта делает его доступным вне хоста по умолчанию; одного наличия сети Compose недостаточно. [Docker: port publishing](https://docs.docker.com/engine/network/port-publishing/).
2. Не доверять присланным пользователем заголовкам identity/forwarded. Шлюз формирует доверенные значения сам; TLS terminating proxy обязан предотвращать подмену таких заголовков. [RFC 9700, раздел 4.13](https://datatracker.ietf.org/doc/html/rfc9700#section-4.13).
3. Проверять все эквивалентные пути: завершающий слеш, кодирование, прямой source ID, aliases, комбинации источников, HTML/JSON, GET/HEAD и дополнительные методы. Маршруты должны однозначно соответствовать публикации. Это вывод о необходимой полноте защиты, не готовая функция шлюза.
4. Ограничивать не только данные. Каталоги, collections, OpenAPI, TileJSON, стили, sprites/fonts и ссылки могут раскрывать закрытые публикации или обходной адрес. Нужен отдельный выбор: скрывать закрытые элементы либо показывать описание без доступа. Для публичного общего каталога одной проверки URL недостаточно — понадобится фильтрация ответа или раздельная генерация. Список ресурсов Martin следует сверить с выбранным тегом. [Martin 1.16.1 endpoints](https://github.com/maplibre/martin/blob/martin-v1.16.1/docs/content/using.md).
5. Проверять доступ до выдачи кешированного содержимого. Martin 1.16.1 прямо описывает такую последовательность с NGINX. Персонализированные каталоги/ответы нельзя объединять одним ключом кеша; правила NGINX зависят от заголовков и настроек `proxy_cache_*`. Для закрытых ответов начальный безопасный вариант — запрет кеширования клиентом и общим CDN; ускорение согласовать отдельно. [Martin 1.16.1 NGINX](https://github.com/maplibre/martin/blob/martin-v1.16.1/docs/content/run-with-nginx.md), [NGINX proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).

## Жизненный цикл и CLI

Проектное предложение для регистрации: создать неподтверждённую учётную запись; отправить письмо; до подтверждения разрешать публичные сервисы; после подтверждения открыть режим «для зарегистрированных»; закрытые сервисы выдаёт администратор. Смена email требует повторной проверки нового адреса. Нужны ограничение повторных писем и попыток входа, восстановление пароля, блокировка учётной записи и аудит изменения допуска. Готовые процессы allauth/Keycloak следует использовать, а не повторять обработку паролей в шлюзе. [allauth configuration](https://docs.allauth.org/en/latest/account/configuration.html), [Keycloak administration](https://www.keycloak.org/docs/latest/server_admin/).

Для токенов до реализации согласовать: число на пользователя, срок, scope по сервисам, создание/показ секрета один раз, хранение проверяемого хеша для непрозрачных токенов, отзыв, замену, поведение при блокировке и смене пароля. Это предлагаемая спецификация, а не свойства всех рассмотренных продуктов.

Особенно важен **предельный срок действия отзыва**. Локальная проверка подписи JWT не узнаёт автоматически о последующем изменении состояния на сервере. Для немедленного запрета нужен запрос состояния либо отдельная текущая проверка/список отзыва; короткий TTL только ограничивает задержку. Keycloak предоставляет introspection активного состояния и revocation, но вызов revocation сам по себе не изменяет результат чисто локальной проверки подписи. Последнее — вывод из различия этих механизмов, который надо подтвердить на интеграции. [Keycloak OIDC endpoints](https://www.keycloak.org/securing-apps/oidc-layers).

CLI сводки требует собственной сборки результата в обоих вариантах:

| Источник | Доступные данные | Недостающая часть |
| --- | --- | --- |
| Django | `username`, `email`, `date_joined`, `is_active`; расширяемые management commands | Состояние email из allauth и вычисление доступных публикаций через общий компонент прав |
| Keycloak | Admin API: `username`, `email`, `createdTimestamp`, `emailVerified`, `enabled`; `kcadm` умеет перечислять пользователей и effective roles | Постраничное получение всех пользователей, перевод timestamp, соединение с политикой публикаций |

Источники: [Django User API](https://docs.djangoproject.com/en/5.2/ref/contrib/auth/), [Django management commands](https://docs.djangoproject.com/en/5.2/howto/custom-management-commands/), [Keycloak UserRepresentation](https://www.keycloak.org/docs-api/latest/rest-api/index.html), [Keycloak Admin CLI](https://www.keycloak.org/docs/latest/server_admin/#the-admin-cli). «Available roles» в Keycloak означает роли, которые можно назначить, а не доступные пользователю сервисы; для задачи нужен расчёт эффективного допуска.

Администраторы — отдельный допуск к управлению; это не четвёртый пользовательский режим публикации. При файловых правилах нужны валидация и понятное применение изменений; при БД — операции выдачи/отзыва и аудит. Ни хранение конфигурации, ни БД здесь не выбраны.

Машинный клиент нельзя молча считать человеком с подтверждённым email. Для будущих service accounts нужны явный тип субъекта, ответственный владелец и отдельный список сервисов; по умолчанию не включать их в «все зарегистрированные». Keycloak поддерживает client credentials, но соответствие бизнес-правилам задаёт проект. [Keycloak: client credentials](https://www.keycloak.org/securing-apps/oidc-layers#client-credentials).

## Что решить до имплементации

1. Auth-приложение либо IdP; конкретный механизм пользовательских токенов и поддержка клиентов GIS.
2. Конфигурация либо БД для администраторских правил; нужен ли UI администратора сейчас.
3. Видимость закрытых публикаций в каталогах и описаниях; политика для некорректного токена на публичном сервисе.
4. Допустимая задержка отзыва, сроки access/refresh/API tokens и правила смены email/пароля.
5. Какие операции публикации разрешены: чтение, запуск процессов, получение результатов, административное изменение. Нельзя выводить право записи из права чтения.

Будущий учёт можно подготовить стабильными `subject_id`, `publication_service_id`, `credential_id` без секрета, `request_id`, методом, результатом проверки, HTTP-статусом, объёмом и длительностью. Это предложение границы событий; тарифы, платежи и агрегирование не входят в текущую работу. Для cache hit следует сохранять тот же идентификатор публикации и решение доступа.

Остаются непроверенными: доставка email, точное покрытие маршрутов/метаданных, изоляция Docker, кеши после отзыва, смена email, блокировка пользователя и работа выбранных GIS-клиентов с токенами. Это вопросы будущей проверки совместимости, а не уже проведённые тесты и не состав четырёх уровней тестирования. Их наборы необходимо отдельно согласовать по правилам проекта.
