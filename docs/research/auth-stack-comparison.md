# Основа компонента доступа: Django, Flask и JavaScript/TypeScript

Исследование для [«Выбрать схему учётных записей, токенов и прав доступа»](https://github.com/stepanosokin/gis-platform/issues/6). Дата: 17 ноября 2026 года. Проверка по официальной документации, без запуска приложений, интеграций и измерений. Выбор стека остаётся решением пользователя.

## Что сравниваем

Сопоставляем готовые комплекты: **Django + django-allauth**, **Flask + Flask-Security** (поддерживаемое продолжение Flask-Security-Too), **Node.js + Express или Fastify + Better Auth**. Размер минимального приложения с одним HTTP-маршрутом не показывает сложность всей системы учётных записей.

Уже согласовано: режим публикации находится в общем конфиге, персональные разрешения — в БД; недоступные публикации скрываются; блокировка пользователя, отзыв токена и удаление разрешения должны действовать со следующего нового запроса; администратор работает через CLI, отдельная веб-панель администратора пока не нужна. Регистрация, подтверждение email и получение токена входят в исходные требования.

На момент начала сравнения **именованные независимые персональные токены** — например, отдельные для QGIS и скрипта — были кандидатом модели. После сравнения пользователь выбрал отдельные токены с независимым отзывом. Число, сроки и дополнительные ограничения токенов ещё обсуждаются. Ниже базовый сценарий получения токена отделён от выбранного менеджера персональных токенов.

## Сравнение готовности

| Часть | Django + allauth | Flask + Flask-Security | Node.js + Better Auth |
| --- | --- | --- | --- |
| Регистрация, проверка email, восстановление пароля | Готовые механизмы и серверные страницы | Готовые механизмы и серверные шаблоны | Готовые API и клиентские вызовы; страницы приложения нужно собрать |
| Базовое получение токена | Есть штатные session-token и JWT access/refresh стратегии allauth headless | Есть штатный токен аутентификации | Есть сессионный Bearer-механизм; отдельно API Key plugin |
| Возможные именованные независимые персональные токены | Нужен отдельный механизм/пакет и пользовательская страница | Штатный общий auth token не подтверждает такой менеджер; нужна отдельная часть | API Key plugin уже предоставляет большую часть жизненного цикла; страница остаётся нашей |
| БД, миграции и структура приложения | ORM, миграции, команды и шаблоны интегрированы в Django | Выбираем и согласуем расширения БД, миграций и почты | Выбираем адаптер БД и способ миграций; пользовательские таблицы прав остаются нашей частью |
| CLI | Штатные management commands, сводка доступных публикаций — наша | Есть команды пользователей/ролей; сводка публикаций — наша | Нужен CLI приложения; CLI Better Auth обслуживает его схему, не GIS-права |
| Проверка прав публикаций и фильтрация каталогов | Прикладная часть | Прикладная часть | Прикладная часть |
| Отзыв со следующего запроса | Нужна актуальная проверка токена/пользователя/прав | Нужна актуальная проверка токена/пользователя/прав | Нужна актуальная проверка ключа/пользователя/прав; исключить устаревшие кеши |

Таблица — инженерная оценка по описанным ниже функциям. Оценок трудозатрат в днях, производительности, памяти или сравнительной безопасности нет.

## Django + allauth

У allauth есть настройка обязательного подтверждения email и готовые пользовательские сценарии. Это аргумент в пользу Django для быстрого получения обычных серверных страниц регистрации и входа. Django включает средства миграций БД. Наличие готовой Django Admin не является преимуществом для текущего объёма, поскольку пользователь выбрал CLI. [Настройки allauth](https://docs.allauth.org/en/latest/account/configuration.html), [страницы allauth](https://docs.allauth.org/en/latest/account/views.html), [миграции Django](https://docs.djangoproject.com/en/5.2/topics/migrations/).

Текущее allauth headless имеет **Session Tokens и JWT Tokens**. JWT-стратегия выдаёт access/refresh-пару; опция `HEADLESS_JWT_STATEFUL_VALIDATION_ENABLED` проверяет действительность исходной сессии и по умолчанию выключена. Поэтому прежнее утверждение, что для Django обязательно нужен полностью собственный механизм любых API-токенов, слишком широко. Но эти стратегии сами по себе не доказывают готовый пользовательский менеджер именованных независимых PAT с индивидуальным сроком и отзывом. [Session/JWT strategies](https://docs.allauth.org/en/latest/headless/token-strategies/jwt-tokens.html), [конфигурация headless](https://docs.allauth.org/en/latest/headless/configuration.html).

**Оценка:** Django удобен своей согласованной структурой БД, команд и серверных страниц. Он не является автоматически самым простым для каждого возможного варианта токенов. Если выберем базовые session/JWT-токены, объём отдельной разработки может быть меньше, чем при менеджере PAT.

## Flask + Flask-Security

Поддерживаемый проект Flask-Security-Too в 2024 году заменил архивный Flask-Security. Сейчас он находится в Pallets Community Ecosystem и публикуется под обоими именами; сам проект рекомендует зависимость `flask-security`. На дату просмотра stable-документация обозначена 5.9.2. Старые статьи о прекращении поддержки исходного Flask-Security нельзя автоматически переносить на этот проект. [PyPI проекта](https://pypi.org/project/Flask-Security/), [репозиторий](https://github.com/pallets-eco/flask-security).

Flask-Security предоставляет регистрацию, подтверждение email, восстановление пароля, сессии, базовые роли и команды управления пользователями. Поставляются шаблоны входа, регистрации, восстановления пароля и подтверждения адреса. Эти функции не требуется собирать вручную только из Flask-Login. [Функции](https://flask-security.readthedocs.io/en/stable/features.html), [шаблоны](https://flask-security.readthedocs.io/en/stable/customizing.html).

При этом приложение собирается из расширений. Quick Start отдельно предупреждает, что для включаемых функций могут потребоваться дополнительные пакеты почты, локализации и другие зависимости. Для модели пользователей приведены варианты SQLAlchemy и других хранилищ. [Quick Start](https://flask-security.readthedocs.io/en/stable/quickstart.html).

Штатный auth token выдаётся при аутентификации; настраиваются заголовок и срок. В типичном механизме `fs_uniquifier` или отдельный `fs_token_uniquifier` позволяют инвалидировать токены пользователя. Это не доказательство готового списка независимых именованных токенов с индивидуальным отзывом. Для такого требования нужен отдельный механизм. Штатный заголовок — `Authentication-Token`, поэтому единый контракт `Authorization: Bearer …` нужно согласовать и настроить. [Конфигурация](https://flask-security.readthedocs.io/en/stable/configuration.html), [API сброса доступа](https://flask-security.readthedocs.io/en/stable/api.html#flask_security.datastore.UserDatastore.reset_user_access).

**Оценка:** Flask остаётся полноценным кандидатом для небольшого приложения с обычными формами и базовым токеном. Его маленькое ядро не устраняет выбор и сопровождение расширений. Для возможного менеджера PAT преимущество простого каркаса может уменьшиться.

## JavaScript/TypeScript + Better Auth

Better Auth предоставляет email/password API; обязательная проверка email настраивается через `requireEmailVerification`, но отправку писем выполняет предоставленная приложением функция. Для сброса пароля также нужен отправитель писем. Логин по username добавляется плагином; базовый поток использует email. [Email/password](https://better-auth.com/docs/authentication/email-password), [отправка писем](https://better-auth.com/docs/concepts/email).

Есть официальные интеграции Express и Fastify. Они подключают готовый обработчик auth-маршрутов. Отдельный Next.js, NestJS или React не обязателен: простые страницы можно реализовать в выбранном приложении. Better Auth предоставляет API и клиентские вызовы; это не готовый полный набор наших пользовательских страниц. [Express](https://better-auth.com/docs/integrations/express), [Fastify](https://better-auth.com/docs/integrations/fastify), [Basic Usage](https://better-auth.com/docs/basic-usage).

Текущий API Key plugin устанавливается отдельным пакетом **`@better-auth/api-key`**. Есть user-owned ключи, имя, срок, создание, получение списка и удаление; пользовательское удаление проверяет владельца. Это заметно ближе к возможному менеджеру PAT, чем общий токен входа. Собственную криптографию для выпуска и проверки ключа писать не требуется. Страницы создания/списка/отзыва остаются нашей частью. [API Key](https://better-auth.com/docs/plugins/api-key).

У ключей включено хеширование, которое можно отключить настройкой `disableKeyHashing`; отключение документация не рекомендует. Секрет возвращается при создании, последующие операции не предоставляют его исходное значение. Штатный заголовок — `x-api-key`; при выборе Bearer нужно согласовать извлечение ключа из `Authorization` через `customAPIKeyGetter` либо адаптер шлюза. [API Key reference](https://better-auth.com/docs/plugins/api-key/reference).

**Bearer plugin и API Key plugin решают разные задачи.** Bearer plugin позволяет передавать токен сессии вместо cookie, получая его после входа. Он не превращает сессию в отдельный именованный долгоживущий ключ. Для разных моделей нужно выбрать соответствующий механизм, а не включать оба без необходимости. [Bearer plugin](https://better-auth.com/docs/plugins/bearer).

Better Auth имеет БД-адаптеры и средства генерации схемы. Прямое выполнение миграций CLI поддерживается встроенным Kysely-адаптером; с другими адаптерами схема генерируется для инструмента выбранного ORM. Официальная инструкция Express требует ESM и различает маршруты Express 4/5; примеры следует применять к зафиксированным версиям. [Database](https://better-auth.com/docs/concepts/database), [Express integration](https://better-auth.com/docs/integrations/express).

**Оценка:** для API-компонента и возможных независимых персональных ключей Better Auth — сильный кандидат на наименьший объём нашей серверной логики. За это платим сборкой пользовательских страниц и выбором интеграции/адаптера. Для простых шаблонных страниц Python-комплекты могут оказаться удобнее. Без реализации сравниваем состав работы, а не количество строк или часы.

## Отзыв доступа: общее требование

Во всех вариантах шлюз должен получать решение, учитывающее текущий токен, активность пользователя, подтверждение email и разрешение публикации. Проверка подписи или срока токена не заменяет проверку этих фактов.

Для Better Auth при таком контракте нельзя опираться на устаревшие данные `session.cookieCache`: кешированные данные могут оставаться действительными до обновления. Ключи API можно хранить только в БД; вторичное хранилище и его fallback добавляют ещё один путь согласования состояния. Проверять ключ достаточно один раз за запрос: повторная проверка плюс получение сессии могут дважды списать счётчик rate limit. Проверка ключа также не отменяет нашу актуальную проверку пользователя и разрешения публикации. [Session management](https://better-auth.com/docs/concepts/session-management), [API Key advanced](https://better-auth.com/docs/plugins/api-key/advanced).

В Django и Flask тоже нужно выбрать механизмы с актуальной проверкой состояния. Реальную реакцию следующего запроса после блокировки, отзыва токена и изменения разрешения предстоит проверить интеграционно. Ни один вариант этим исследованием не объявлен уже соответствующим данному контракту.

## Прочие JS/TS-варианты

Auth.js Credentials передаёт предоставленные учётные данные нашей функции проверки. Документация прямо оставляет сохранение пользователей, обработку паролей и восстановление доступа приложению. Поэтому для локальной саморегистрации с обязательным email и пользовательскими токенами Better Auth является более сопоставимым главным кандидатом. Это не запрет Auth.js и не оценка его качества. [Auth.js Credentials](https://authjs.dev/getting-started/authentication/credentials).

NestJS и Passport организуют приложение и подключение стратегий аутентификации, но выбор этих каркасов сам по себе не определяет полный набор страниц, проверку email и менеджер персональных ключей. Без потребности в структуре NestJS его добавление не является необходимым условием для Better Auth. [Официальная интеграция Better Auth с Express](https://better-auth.com/docs/integrations/express).

## Что следует из сравнения

Предыдущая рекомендация Django объясняется готовыми страницами и едиными средствами БД/команд. Этого недостаточно для утверждения, что Django проще остальных вариантов целиком.

- Если приоритет — серверные страницы и единая структура Python-приложения, Django + allauth обоснован.
- Если приоритет — небольшой Python-компонент с обычными формами, Flask + Flask-Security тоже обоснован; Flask-Login в одиночку был бы неполным сравнением.
- Если приоритет — JavaScript/TypeScript и потенциальный менеджер независимых персональных ключей, Better Auth заслуживает равного рассмотрения и может сократить нашу серверную логику.

Базовый эксплуатационный состав в каждом варианте: приложение, хранилище учётных записей/прав и доступ к отправке email. Отдельный Keycloak не требуется ни одному из этих трёх комплектов. Факт, что pygeoapi написан на Python, не обязывает компонент доступа использовать Python: компоненты взаимодействуют через HTTP.

После сравнения пользователь выбрал TypeScript + Express + Better Auth с плагином API Key. Итоговые параметры токенов и учётных записей фиксируются в решении [«Выбрать схему учётных записей, токенов и прав доступа»](https://github.com/stepanosokin/gis-platform/issues/6). Выбор языка CLI остаётся отдельным вопросом карты.

## Границы исследования

Данные получены из текущей документации; номера пакетов и настройки нужно зафиксировать и перепроверить при имплементации. В Better Auth особенно важно сверить отдельный пакет API Key с версией core; в Flask использовать поддерживаемый проект Pallets-Eco; в allauth учитывать наличие новых headless-стратегий вместо старых утверждений об отсутствии токенов.

## Дополнительная проверка: автоматическое продление персональных API-ключей

Этот раздел сопоставляет варианты продления. После обсуждения пользователь выбрал продление того же секрета после успешно проверенного и допущенного запроса с истечением через 90 дней неактивности; общее предельное время жизни активно используемого токена не задаётся. Каноническое решение хранится в [вопросе о схеме доступа](https://github.com/stepanosokin/gis-platform/issues/6).

| Вариант | Поведение | Относительная сложность |
| --- | --- | --- |
| Без срока истечения | Секрет работает до индивидуального/общего отзыва или блокировки | Минимальная дополнительная логика: у API Key допускается `expiresAt = null`; проверка пользователя и прав по-прежнему нужна |
| Тот же секрет, срок сдвигается при успешном использовании | Клиенту не нужно менять строку токена; неиспользуемый ключ истекает | Небольшая дополнительная серверная логика поверх API Key plugin; требуется корректное обновление срока и обработка конкурирующих запросов |
| Короткий access token и обновление с заменой токенов | Клиент получает новые токены через refresh-процесс | Больше частей: серверный жизненный цикл refresh и поддержка обновления каждым клиентом; статический API Header QGIS сам такую схему не реализует |

Оценка сложности относительная, без запуска и оценок в часах. Скользящий срок того же ключа означает, что активно используемый секрет может оставаться действительным долго; это не ротация секрета.

В просмотренной документации API Key plugin есть фиксированное `expiresIn`, отсутствие срока и изменение ключа, но **нет документированной настройки автоматического скользящего срока по использованию**. Обновление `expiresIn` через серверное API меняет `expiresAt` относительно текущего времени. `refillAmount` и `refillInterval` пополняют квоту запросов; они не продлевают срок токена. [API Key](https://better-auth.com/docs/plugins/api-key), [Reference](https://better-auth.com/docs/plugins/api-key/reference), [update-api-key.ts](https://github.com/better-auth/better-auth/blob/main/packages/api-key/src/routes/update-api-key.ts).

В `verify-api-key.ts` проверяется истечение `expiresAt`; обновляются сведения о запросах, квотах и rate limit, но автоматического сдвига `expiresAt` нет. Следовательно, вариант «тот же ключ действует N дней после успешного использования» нужно реализовать доверенным серверным действием приложения, например через `updateApiKey` или условное обновление в БД выбранного адаптера. [Проверка ключа](https://github.com/better-auth/better-auth/blob/main/packages/api-key/src/routes/verify-api-key.ts).

Продление выполняется только после полной успешной аутентификации и проверки доступа к публикации. Истёкший, отозванный или недействительный ключ не продлевается; анонимный доступ к публичной публикации также не считается использованием ключа. Обновление не должно восстанавливать удалённый ключ или перетирать отзыв/блокировку при гонке запросов. Эти свойства являются требованиями к нашей логике, а не автоматически подтверждёнными свойствами произвольного вызова обновления. Частоту записей при множестве тайловых запросов и точную семантику срока нужно согласовать при проектировании реализации.

Документация помечает изменение `expiresIn` как server-only. Просмотренный `main` отдельно разрешает вызовы через сессию владельца и доверенный серверный вызов с `userId`; детали допустимых HTTP-полей не полностью совпадают с описанием. Поэтому контракт автоматического продления следует строить через собственное доверенное серверное действие и перепроверить на зафиксированной версии пакета. Продление не требует выдавать GIS-клиенту право менять срок ключа. [Документация обновления](https://better-auth.com/docs/plugins/api-key), [исходник маршрута](https://github.com/better-auth/better-auth/blob/main/packages/api-key/src/routes/update-api-key.ts).

Bearer plugin использует токен сессии вместо cookie и наследует жизненный цикл сессии. Это отдельный вариант, а не готовое автопродление независимых API-ключей. Настройки срока и обновления сессии описаны в `session.expiresIn` и `session.updateAge`; подменять ими уже выбранный тип персональных ключей без нового решения нельзя. [Bearer plugin](https://better-auth.com/docs/plugins/bearer), [Session management](https://better-auth.com/docs/concepts/session-management).
