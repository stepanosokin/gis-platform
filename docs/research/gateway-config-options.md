# Конфиг и шлюз: проверенные границы

Дата: 17 ноября 2026 года. Контекст: [Выбрать единый конфиг и схему публикации через шлюз](https://github.com/stepanosokin/gis-platform/issues/8).

Это исследовательская справка: факты и варианты, рассмотренные при обсуждении. Принятое решение записано в [тикете обсуждения](https://github.com/stepanosokin/gis-platform/issues/8). Изучены официальная документация и исходники; контейнеры, внешние БД и интеграционные проверки не запускались. База движков — pygeoapi 0.24.0 и Martin 1.16.1. Возможности Martin 2.x не предполагаются. Точные образы и digest ещё требуется выбрать.

## Шлюз и транспорт

| Область | Подтверждённый факт | Следствие для обсуждения |
| --- | --- | --- |
| Caddy: предварительная проверка | `forward_auth` отправляет GET-копию запроса в компонент доступа, передаёт исходные метод и URI. При 2xx продолжает обработку, другой ответ возвращает клиенту. [Документация](https://caddyserver.com/docs/caddyfile/directives/forward_auth) | Express может возвращать для API 401/403 в согласованном формате. Редирект на HTML-вход не обязателен. Проверка должна охватывать тайлы, стили, связанные ресурсы и условные запросы. |
| Caddy: TLS | Automatic HTTPS получает и обновляет сертификаты, добавляет редирект HTTP → HTTPS при выполнении условий для имени, DNS, портов и хранилища. Явный адрес `http://…` отключает automatic HTTPS для сайта. Явные маршруты HTTP имеют значение и могут менять поведение. [Документация](https://caddyserver.com/docs/automatic-https) | Можно предложить TLS termination в Caddy и глобальный выбор HTTP/HTTPS. Конфиг должен исключать выдачу содержимого по HTTP при HTTPS, включая альтернативные порты. Не считать автоматическое получение сертификата гарантированным для произвольной среды. |
| Caddy: загрузка конфига | `/load` применяет конфигурацию; при неудаче возвращает прежнюю. Admin API по умолчанию слушает `localhost:2019`. [API](https://caddyserver.com/docs/api) | Это откат одного Caddy. Он не обеспечивает транзакцию вместе с pygeoapi, Martin и БД разрешений. Admin API нельзя публиковать наружу. |
| Caddy: передача ответа | Reverse proxy поддерживает streaming, настройку заголовков, перехват ответа и доверенные прокси. [Документация](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) | Большие ответы можно передавать без сборки всего тела в Express. Автоматическое переписывание URL внутри JSON/HTML/стилей этим не обеспечивается. Нужно отдельно выбрать, кто обрабатывает каталоги и ссылки. |
| nginx: альтернатива | `auth_request` разрешает 2xx; при 401/403 запрещает, прочие коды считает ошибкой. Модуль не включён в сборку по умолчанию. [Документация](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html) | Это пригодная альтернатива, но нужно выбрать образ с модулем и сопоставить ошибку компонента доступа с внешним API-контрактом. |

Варианты, рассмотренные при обсуждении; итоговый выбор записан в тикете:

- Caddy выполняет TLS и предварительную проверку через Express, затем передаёт данные движкам; Express обслуживает учётные записи и формирует/фильтрует каталог и описания. Это сохраняет путь больших ответов через reverse proxy, но требует точной классификации всех маршрутов.
- Caddy выполняет TLS, а все прикладные запросы проходят через Express, который проверяет доступ и проксирует движки. Контроль маршрутов сосредоточен в одном месте, но Express становится частью пути всех потоков; необходимы корректные streaming, cancellation, compression и conditional requests.

| OpenAPI | Файл из `PYGEOAPI_OPENAPI` должен существовать до запуска. Генерация по умолчанию завершается ошибкой для некорректной коллекции; генераторы API могут обращаться к провайдерам. Вариант `--no-fail-on-invalid-collection` существует. [openapi.py](https://github.com/geopython/pygeoapi/blob/0.24.0/pygeoapi/openapi.py), [itemtypes.py](https://github.com/geopython/pygeoapi/blob/0.24.0/pygeoapi/api/itemtypes.py) | Отключение строгого режима нельзя считать надёжной изоляцией одной коллекции: обработка ошибки находится и на уровне генератора API. Проверять готовность каждого источника отдельно; не публиковать молча неполное описание. |
| Ошибка источника во время запроса | Features создаёт провайдер для конкретной коллекции и обрабатывает `ProviderGenericError` при загрузке и запросе. Объект API содержит конфиг и общий менеджер, а не заранее созданный провайдер каждого набора. [itemtypes.py](https://github.com/geopython/pygeoapi/blob/0.24.0/pygeoapi/api/itemtypes.py), [API](https://github.com/geopython/pygeoapi/blob/0.24.0/pygeoapi/api/__init__.py) | Из этого не следует необходимость отдельного контейнера на каждую публикацию. Но также не доказана изоляция всех ошибок запуска и всех провайдеров. |
| Общий каталог | `describe_collections` перехватывает исключение генерации отдельного описания: в общем списке пропускает его, при прямом запросе возвращает ошибку. Описание тайлов/карт может загружать провайдер. [API](https://github.com/geopython/pygeoapi/blob/0.24.0/pygeoapi/api/__init__.py), [collection.py](https://github.com/geopython/pygeoapi/blob/0.24.0/pygeoapi/api/collection.py) | Каталог платформы лучше строить из принятого конфига и разрешений, с отдельным состоянием публикации. Штатный `visibility:hidden` не заменяет разграничение доступа. |
| SQL-метаданные | SQL provider получает модель таблицы и поля при создании; существуют кешируемые помощники для модели/движка. [sql.py](https://github.com/geopython/pygeoapi/blob/0.24.0/pygeoapi/provider/sql.py) | Кеш соединения/схемы не равен кешу ответов. Изменение схемы требует отдельной проверки, очистки зависимых метаданных либо перезапуска; обычный COMMIT данных не должен требовать этого. |

Базовая рекомендация для планирования: один общий конфиг генерирует штатные конфиги и OpenAPI; публикации имеют отдельные права и маршруты, но это не требует отдельного процесса на каждую. До переключения проверять конфиг и доступность изменённых источников. При общей сборке pygeoapi сохранять работавшие артефакты и не запускать обязательную общую регенерацию OpenAPI, которая из-за временно недоступной БД может лишить остальных публикаций запуска. Конкретная изоляция старта — ещё вопрос реализации и проверки, а не доказанная гарантия движка.

## Кеш и требование свежести

Ниже — предложения, а не новые требования к продукту.

- В первой версии без кеша ответов шлюза: отключить кеш результатов динамических источников в движках; выдавать динамические ответы с `Cache-Control:no-store`; учитывать задержку подготовленных источников DBA. Более строгая фактическая свежесть допустима при установленном максимуме 60 секунд. Обязанность источника укладываться в общий бюджет при этом остаётся.
- Для всех ответов публикаций и каталогов, включая публичные и статические публикации, TileJSON, стили, sprites, данные, ошибки и 304, предложить `Cache-Control:no-store`. Иначе ответ, закешированный в публичном режиме с `max-age`, может обслужить новый запрос после перевода публикации в закрытый режим без обращения к серверу. `private` само по себе этого также не предотвращает. Проверка доступа нужна до условного ответа. Отдельные неизменяемые файлы интерфейса можно кешировать, если они не раскрывают сведения публикаций и не меняют режим доступа. Это предложение для первой версии до отдельного решения о версиях URL и инвалидации; оно не доказывает поведение внутренних кешей клиентов и не отменяет уже полученные пользователем данные.
- Если кеш ответов будет добавлен позднее: сначала проверять актуальные права; сохранять исходный deadline, учитывающий бюджет источника; не начинать полный срок заново при выдаче или перекладывании записи. Ключ должен учитывать публикацию, ревизию, все параметры и формат. Запретить выдачу после deadline, включая `stale-if-error` и `stale-while-revalidate` за пределом бюджета.

Основание HTTP-семантики: [RFC 9111, response directives](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2). `no-cache` требует подтверждения перед повторным использованием, `no-store` запрещает хранение, `private` разрешает личный кеш, `must-revalidate` запрещает повторное использование просроченного ответа. RFC отдельно ограничивает своё действие: внутренний кеш приложения и уже показанная карта не становятся автоматически управляемыми этими заголовками. Нужна проверка обычных повторных запросов поддерживаемых клиентов; заголовок сам по себе не доказательство всей цепочки.

## Что остаётся проверить

- Выбор варианта Caddy/Express, внешний набор маршрутов, относительные и абсолютные ссылки во всех связанных документах. Маршрут публикации в шлюзе не равен отдельному контейнеру движка.
- Ошибки запуска с недоступной БД, восстановление, смена схемы, стабильность всех остальных публикаций и сообщений каталога.
- Полный путь PNG/MVT/TileJSON/OGC Tiles и auth-заголовков; если платформа отдаёт сам архив PMTiles — дополнительно Range/206/416. Чтение архива Martin и HTTP-раздача самого архива — разные сценарии.
- Потоки, прерывание клиентом, размер ответа, content encoding, cache headers, ETag/304, HEAD/OPTIONS, недоступность компонента доступа; клиентские QGIS/MapLibre/Python-сценарии.
- Откат ревизии общего конфига должен возвращать согласованный набор файлов/маршрутов и режимов доступа; не должен восстанавливать отозванные токены и удалённые персональные разрешения из отдельной БД.

Это области будущей проверки. Состав четырёх уровней тестирования этим отчётом не задаётся.

## Уточнение: ошибки и общий каталог OGC

В Features 1.0.1 RFC Problem Details не обязателен. Раздел 9.3 показывает пример JSON-исключения по [exception.yaml](https://schemas.opengis.net/ogcapi/features/part1/1.0/openapi/schemas/exception.yaml): обязательная строка `code`, необязательная строка `description`. Это пример схемы ответа, а не требование заменить любой ответ именно этой структурой. pygeoapi `get_exception` выдаёт `code`, `type`, `description`; дополнительное поле `type` допустимо этой схемой, но само по себе не превращает ответ в RFC Problem Details. Для шлюза разумно предложить `application/json` с `code` и `description`, без секретов и внутреннего SQL.

401 и 403 прямо предусмотрены таблицей HTTP-кодов Features; для 401 требуется `WWW-Authenticate`. Другие подходящие HTTP-коды разрешены, поэтому 503 для недоступной публикации допустим. Ошибки прикладного шлюза и схемы доступа нужно описать в OpenAPI вместе со схемами безопасности: `/req/oas30/exceptions-codes` и `/req/oas30/security`. Основание: [Features 1.0.1, разделы 7.5, 9.3–9.4](https://docs.ogc.org/is/17-069r4/17-069r4.html).

Один datasource в нескольких публикациях с разными ID не создаёт выявленного запрета стандарта. Но общий неизменённый каталог pygeoapi требует проверки: `/req/core/fc-op` требует `/items` для каждой feature collection из ответа `/collections`, а отсутствующий `itemType` трактуется как `feature`. В `collection.py` pygeoapi векторный tile resource получает `itemType:tile`, но также items-ссылки; для map-only/raster-only коллекции отсутствие `itemType` может ошибочно представить её как Features. Это наблюдение по исходникам, не воспроизведённая ошибка конформности.

Следовательно, общий внешний `/ogc` с разными resource IDs технически можно рассматривать, но нельзя обещать конформность прямым проксированием смешанного `/collections`. Требуется согласованная классификация коллекций, корректные ссылки и OpenAPI либо отдельные внешние API roots для протоколов. Отдельные roots не требуют отдельного контейнера каждой публикации; варианты общей инстанции с адаптером и отдельных инстанций на протокол остаются выбором реализации. Отдельный `/tiles/{id}` для Martin, запрет составных источников и скрытие штатного каталога — допустимое проектное предложение; фактические URL и клиентская работа не проверены.
