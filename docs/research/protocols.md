# Протоколы и файловые источники pygeoapi и Martin

Исследование для задачи [Проверить протоколы и файловые источники pygeoapi и Martin](https://github.com/stepanosokin/gis-platform/issues/2). Срез источников: **17 ноября 2026 года**. Это документальная проверка официальных спецификаций, документации и кода; контейнеры и клиентские сценарии не запускались. Состав первой версии здесь не выбирается: протоколы можно вводить поэтапно. Исходные данные в первой версии доступны только для чтения; редактирование Features рассматривается как последующее расширение. DGGS/H3 исследуется отдельно.

## Вывод

Связка покрывает большую часть требований, но не означает полную реализацию всех частей каждого стандарта. pygeoapi предоставляет OGC API и подключаемые провайдеры; Martin обслуживает и генерирует тайлы. Документация pygeoapi прямо предусматривает публикацию тайлов Martin через `MVT-proxy`. Это позволяет сохранить оба основных движка и дать одному набору данных интерфейс OGC API — Tiles и обычный TileJSON/XYZ. [pygeoapi Tiles](https://docs.pygeoapi.io/en/stable/publishing/ogcapi-tiles.html)

Главные пробелы: OGC API — Styles отсутствует в подтверждённом стабильном интерфейсе обоих движков; Coverages в pygeoapi имеет статус Implementing и следует ещё проекту стандарта; обычный GeoTIFF не становится автоматически пригодным для растровых тайлов Martin. Наличие файлов стилей, PNG или MVT само по себе не подтверждает реализацию соответствующего OGC API. [Матрица pygeoapi](https://docs.pygeoapi.io/en/stable/introduction.html), [Styles OGC](https://ogcapi.ogc.org/styles/), [Coverages OGC](https://ogcapi.ogc.org/coverages/), [Martin stable API](https://github.com/maplibre/martin/blob/martin-v1.16.1/docs/content/using.md)

### Что уже описано для Martin 2.x

Текущая документация описывает `/ogc`: Tiles core/MVT/geodata-tilesets, Common и Tile Matrix Set 2.0; при styles — draft Styles core/global-styles; при rendering — Maps core и ряд классов карт. Документация сообщает о запуске официальных OGC тестов в CI, но это не утверждение о сертификате stable 1.16.1. OpenAPI там 3.1, поэтому OGC-классы OpenAPI 3.0 не декларируются. У composite sources нет OGC counterparts; Maps ограничены Web Mercator и условиями растрового источника/стиля. [Текущий OGC API Martin](https://maplibre.org/martin/ogc-api/)

Это кандидат для повторной проверки после стабильного релиза, а не основание переводить проект на beta. В теге 1.16.1 соответствующий документ отсутствует; поэтому матрица выше опирается на опубликованный перечень API и features именно этого тега.

## Источник, провайдер, протокол и формат ответа

Эти понятия нужно фиксировать раздельно. Пример возможной цепочки: **PostGIS → Martin → MVT по XYZ/TileJSON → pygeoapi MVT-proxy → OGC API — Tiles с теми же MVT**. Другой путь: **GeoTIFF → Rasterio provider → OGC API — Coverages → числовые данные/подмножество**, либо **GeoTIFF → MapScript → OGC API — Maps → PNG**. Доступ к значениям растра и картинка карты решают разные задачи. [pygeoapi Tiles](https://docs.pygeoapi.io/en/stable/publishing/ogcapi-tiles.html), [Coverages](https://docs.pygeoapi.io/en/stable/publishing/ogcapi-coverages.html), [Maps](https://docs.pygeoapi.io/en/stable/publishing/ogcapi-maps.html)

**Важная граница COG в Martin 1.16.1:** документация тега помечает поддержку нестабильной; default binary/Docker её не содержит. Подтверждены local COG, RGB/RGBA 8-bit; grayscale и более высокая разрядность указаны как work in progress, EPSG:3857 — как неподдерживаемый. Это существенно уже текущей документации 2.x с remote COG. Не следует обещать произвольный DEM/GeoTIFF как рабочий raster source stable Martin. [COG stable](https://github.com/maplibre/martin/blob/martin-v1.16.1/docs/content/sources-cog-files.md), [правила optional features](https://github.com/maplibre/martin/blob/martin-v1.16.1/docs/content/installation.md)

## Провайдеры и Docker

Официальный pygeoapi image запускает Gunicorn на порту 80; конфигурация подключается volume mapping. Dockerfile тега 0.24.0 использует Ubuntu Noble и устанавливает GDAL, Rasterio, SpatiaLite, MapScript, Xarray/NetCDF/Zarr и PostgreSQL client libraries. Это наличие зависимостей сборки, а не проверка всех форматов конкретного образа. Пакетная установка `pip install pygeoapi` сама по себе не доказывает наличие всех провайдеров. [Docker docs](https://docs.pygeoapi.io/en/stable/docker.html), [Dockerfile 0.24.0](https://github.com/geopython/pygeoapi/blob/0.24.0/Dockerfile)

Для Martin подтверждён образ `ghcr.io/maplibre/martin:1.16.1`, порт 3000 и mounting конфигурации. При PostGIS нужен минимум 3.0, рекомендован 3.1+. `unstable-*` features исключены из стандартных binaries и Docker. Style rendering включён в default Linux build, но документация предупреждает об изменениях в patch-релизах, отсутствии concurrency и cache для rendered requests. [Установка stable](https://github.com/maplibre/martin/blob/martin-v1.16.1/docs/content/installation.md), [ограничения rendering](https://github.com/maplibre/martin/blob/martin-v1.16.1/docs/content/sources-styles/rendering.md)

Для coverage formats важен состав именно контейнерной GDAL-сборки: Rasterio предупреждает, что PyPI wheels не содержат многих optional drivers. Поэтому формат файла, provider и зависимости следует проверять вместе. [Rasterio installation](https://rasterio.readthedocs.io/en/stable/installation.html)

Process API требует отдельно определённых processor plugins. Default local job manager — TinyDB; для асинхронных заданий нужны writable job storage и output directory. Наличие этого API не является готовой распределённой очередью вычислений. [Процессы и managers](https://docs.pygeoapi.io/en/stable/publishing/ogcapi-processes.html)

Records использует ElasticsearchCatalogue, TinyDBCatalogue или CSWFacade. Это каталог подготовленных metadata records, а не автоматическое описание любого смонтированного каталога исходников. [Records providers](https://docs.pygeoapi.io/en/stable/publishing/ogcapi-records.html)

Рекомендация для сохранения условия read-only: монтировать источники только для чтения, использовать отдельного PostgreSQL пользователя с разрешениями чтения и держать writable process/job storage отдельно. `editable: true` не включать в первую версию. Будущее редактирование потребует провайдера с CRUD, внешнего доступа/авторизации и учёта draft Features Part 4; PostgreSQL provider помечен как поддерживающий transactions, файловые GeoJSON/OGR/SQLiteGPKG — нет. [Transactions](https://docs.pygeoapi.io/en/stable/transactions.html), [матрица feature providers](https://docs.pygeoapi.io/en/stable/publishing/ogcapi-features.html)

## Решения, которые ещё нужно принять

1. Какие из Features, Maps, Tiles, Processes, Coverages, Styles и Records входят в первый этап, а какие допускают последующую поставку? MVT следует учитывать отдельно как формат выдачи Tiles.
2. Что означает обязательная поддержка: конкретные классы conformance и операции либо полная совместимость с выбранными клиентами? Какие версии QGIS/GDAL/веб-клиента должны работать?
3. Для растров нужны значения/подмножества coverage, изображения карт, растровые тайлы или все три результата? Каковы реальные CRS, число каналов, bit depth и форматы файлов?
4. Какие файловые источники обязательны без предварительного преобразования? Допустима ли загрузка больших векторов в PostGIS или подготовка tile archives? Место хранения производных файлов согласовать отдельно; `data/` нельзя использовать для них автоматически.
5. Достаточно ли выдачи MapLibre styles, либо требуется OGC Styles discovery/metadata/CRUD и SLD? Это разные требования.
6. Для Processes какие алгоритмы, входы/выходы, максимальные длительность и размер, sync/async и сохранность jobs нужны? Где будут храниться результаты с учётом read-only исходников?
7. Для будущего редактирования Features какие источники становятся writable и как изменения инвалидируют тайлы/каталог? Этот вопрос не расширяет scope первой версии.

После этих ответов можно выбрать протоколы первого этапа и подготовить стартовую спецификацию. После подготовки стартовой спецификации состав проверок для каждого из четырёх уровней нужно отдельно согласовать с пользователем и записать в спецификации. В этом исследовании не определены составы уровней тестирования, не написаны application code или тестовые сценарии и не сделан выбор v1.
