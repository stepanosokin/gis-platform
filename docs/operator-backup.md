# Резервное копирование и восстановление

Команды на production выполняет администратор из каталога развёрнутой версии GIS Platform. Для копирования нужен работающий PostgreSQL платформы. Установите restic 0.20 или новее и подготовьте отдельный репозиторий rest-server по HTTPS на другом хосте. Ограничьте доступ к репозиторию учётной записью этого развёртывания. Для восстановления храните пароль restic отдельно от репозитория и резервируемых файлов.

В примерах файлы развёртывания расположены под `/srv/gis`, а служебный каталог — в `/srv/gis/state`. Код Compose и сведения о развёрнутом коммите храните отдельно. Перед выполнением замените пути, имя проекта и адрес репозитория своими значениями.

## Копирование

Поместите параметры в закрытый файл окружения оператора. Для TLS с внутренним УЦ укажите `RESTIC_CACERT`. Для аутентификации rest-server задайте `RESTIC_REST_USERNAME` и `RESTIC_REST_PASSWORD` в том же закрытом файле вне резервируемых путей. [Руководство restic по подготовке репозитория](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)

```sh
export COMPOSE_PROJECT_NAME=gis-platform
export GIS_STATE_DIR=/srv/gis/state
export RESTIC_REPOSITORY=rest:https://backup.example.org/gis-platform/
export RESTIC_PASSWORD_FILE=/etc/gis-operator/restic-password
# export RESTIC_CACERT=/etc/gis-operator/backup-ca.pem
# export GIS_BACKUP_RETENTION_DAYS=30
```

Один раз выполните `restic init` с этими параметрами и сохраните доступ к паролю для оператора восстановления. Защищённый снимок формируется на отдельном сервере. Параметр `GIS_BACKUP_RETENTION_DAYS` задаёт срок в днях. При значении по умолчанию хранятся снимки за 30 дней от последнего успешного снимка этого проекта. После каждой успешной записи restic удаляет более старые снимки и освобождает их место. [Политика хранения restic](https://restic.readthedocs.io/en/stable/060_forget.html)

```sh
node dist/cli.js backup create daily /srv/gis/platform.yaml --json
node dist/cli.js backup create pre-update /srv/gis/platform.yaml --json
```

Назначьте первую команду в cron или systemd timer раз в сутки из каталога проекта с закрытым файлом окружения. Включите уведомление об ошибке задачи и записывайте ID успешного снимка из `data.snapshotId`. Выполняйте вторую команду перед обновлением кода, образов, конфигурации или данных. Продолжайте обновление после успешной копии.

Копия содержит согласованный дамп PostgreSQL, служебное состояние и артефакты обеих подтверждённых версий. В неё входят файловые источники публикаций обеих версий, секреты доступа, SMTP и PostGIS, серверные файлы административного TLS и архивы внешнего TLS из `GIS_STATE_DIR/tls/`. Для старой версии без архива резервируются файлы TLS по исходным путям. Клиентские ключи операторов остаются у их владельцев. Данные Caddy для этого режима восстанавливаются из конфигурации и серверного комплекта TLS. Тома Caddy и PostgreSQL сохраняются между обычными обновлениями Compose.

Передайте дополнительными аргументами редактируемый YAML и другие файлы, которыми управляет оператор. Среди них могут быть оригиналы стилей MapLibre, используемое окружение Compose и файлы сторонних сервис-провайдеров. Дополнительные пути должны находиться вне служебного каталога и не включать его. Для внешнего PostGIS и содержимого именованных томов сторонних сервис-провайдеров нужен их собственный порядок резервного копирования. Сохраняйте файлы и секреты неизменными до завершения команды. Возобновите копирование после завершения и проверки `config apply`, если применение выполняется в то же время.

По завершении CLI удаляет одноразовый закрытый каталог с рабочим дампом. После аварийной остановки проверьте каталоги `.gis-backup-work-*` в `GIS_STATE_DIR`. Если снимок не был подтверждён, повторите копирование перед обновлением. Проверяйте репозиторий командой `restic check` и проводите пробное восстановление в отдельном стеке.

## Сверка доступа

Выберите снимок платформы, из которого требуется восстановить файлы и конфигурацию. Для учётных записей используйте более свежий снимок того же развёртывания, если после базовой копии были изменения. Его дамп должен содержать все изменения до момента, после которого исходная платформа прекратила принимать изменения учётных записей и доступа. Если независимые записи подтверждают отсутствие любых изменений учётных записей и доступа после базовой копии, используйте её дамп с `--verified-no-changes`.

Если исходная БД доступна, остановите операции администрирования и компонент доступа. Проверьте, что источник больше не принимает новых изменений. Следующие команды записывают снимок `pre-update` в настроенном проекте с запущенным PostgreSQL.

```sh
docker compose -p "$COMPOSE_PROJECT_NAME" -f compose.yaml -f compose.auth.yaml stop access
node dist/cli.js backup create pre-update /srv/gis/platform.yaml --json
```

Перед восстановлением подтвердите по эксплуатационному журналу, что в выбранном свежем дампе учтены выдача и отзыв персональных разрешений, блокировки и разблокировки, отзыв токенов и завершение сеансов. Новый снимок должен содержать актуальные настройки доступа и тот же ключ для проверки сеансов, что и восстанавливаемая версия. Если правила доступа или ключ менялись, выберите для восстановления комплект с проверенными актуальными настройками. Если события или состояние источника подтвердить невозможно, держите защищённые маршруты закрытыми.

После сверки более свежего снимка команду восстановления запускают с `--verified-authority`. CLI проверяет идентификатор развёртывания, порядок снимков и совпадение настроек доступа и ключа. По одной дате создания снимка CLI не может определить, были ли более поздние изменения в исходной БД.

## Пробное восстановление и запуск

Подготовьте отдельную машину или изолированную виртуальную машину с версией кода, соответствующей восстанавливаемой конфигурации. Настройте контролируемый доступ к внешним источникам и SMTP. Убедитесь, что занятые на исходном сервере порты свободны, а файлы можно восстановить по исходным абсолютным путям. Используйте новое имя Compose-проекта с префиксом `gis-restore-`.

Извлеките оба снимка в разные новые каталоги под закрытым родительским каталогом. Передайте полные ID снимков. Команда проверит извлечённые файлы и пометит в них шлюз закрытым.

```sh
umask 077
mkdir -m 700 /srv/gis-restore
node dist/cli.js backup extract "$snapshot_id" /srv/gis-restore/baseline --json
node dist/cli.js backup extract "$authority_id" /srv/gis-restore/authority --json
```

Значение `data.directory` первой команды указывает на извлечённый `GIS_STATE_DIR`. Восстановите исходные пути из этого снимка, включая весь служебный каталог и файлы, расположенные вне него. Сохраните режимы и владельцев файлов. В примере на выделенной машине путь `/srv/gis` свободен.

```sh
test ! -e /srv/gis && cp -a /srv/gis-restore/baseline/srv/gis /srv/gis
export GIS_STATE_DIR=/srv/gis/state
export COMPOSE_PROJECT_NAME=gis-restore-pilot
export GIS_PUBLIC_BIND=127.0.0.1
node dist/cli.js backup recover /srv/gis-restore/authority/srv/gis/state/.gis-backup-payload --verified-authority --json
node dist/cli.js doctor --json
```

Вместо пути `authority/…/.gis-backup-payload` используйте `data.payload` второй команды извлечения. Если сверка подтвердила отсутствие изменений и вы извлекли только базовую копию, передайте её `data.payload` с флагом `--verified-no-changes`. На чистом проекте CLI поднимает PostgreSQL и восстанавливает базовый дамп. При наличии подтверждённого свежего дампа CLI заменяет БД доступа его содержимым. Это сохраняет последние права, блокировки и отзывы вместе с учётными записями. Caddy открывает маршруты на loopback после восстановления БД и проверки готовности стека. При отказе команды проверьте причину и повторите её с тем же изолированным проектом и восстановленными файлами.

На loopback проверьте публичные данные и ответ закрытой публикации с контрольными учётными записями и токенами. Для отозванного разрешения, заблокированной учётной записи, отозванного токена и завершённого сеанса подтвердите отказ. Сверьте доступ действующей учётной записи. Затем проверьте действующую и предыдущую версии в `status --json`. Для пробного восстановления используйте отдельные сетевые настройки и завершите работу стека после проверки.

Для возврата production в работу повторите проверенный порядок на выделенной машине. После проверки доступа администратор подключает внешний балансировщик или меняет привязку портов Caddy и направляет DNS на восстановленный хост. Следующие команды меняют привязку при штатном HTTPS с портом 443.

```sh
export GIS_REVISION_DIR="$GIS_STATE_DIR/plans/$current_version"
export GIS_PUBLIC_PORT=443 GIS_CADDY_PORT=443 GIS_HTTP_REDIRECT_PORT=80
export GIS_TLS_CERT_FILE="$GIS_STATE_DIR/tls/$current_version/cert.pem"
export GIS_TLS_KEY_FILE="$GIS_STATE_DIR/tls/$current_version/key.pem"
GIS_PUBLIC_BIND= docker compose -p "$COMPOSE_PROJECT_NAME" -f compose.yaml -f compose.tls.yaml up -d --no-deps caddy
```

Подставьте `current_version` из результата восстановления. Для HTTPS на другом порту используйте порт из YAML. Для старой версии без архива укажите восстановленные исходные пути TLS. В HTTP используйте только `compose.yaml`, задайте `GIS_CADDY_PORT=80` и внешний порт из YAML. После переключения проверьте внешний адрес, TLS и доступ из клиентской сети. Удалите рабочие копии дампов и извлечённые секреты по порядку обращения с секретными данными вашей организации. Сохраните сам зашифрованный снимок в репозитории restic.
