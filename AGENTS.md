## Git

Выполнять `git commit` и `git push` по тикету после окончания разработки и ревью, когда все требуемые локальные тесты и проверки прошли.

Для ревью добавь в индекс файлы тикета и передай обеим проверкам `code-review` команду `git diff --cached <base>`, где `<base>` — коммит до начала работы. После исправлений обнови индекс. Перед коммитом проверь `git diff --cached --check` и убедись по `git diff --cached --name-only`, что в индексе только файлы задачи.

## Тестирование

Перед локальным прогоном см. [команды тестирования и диагностику Docker](tests/README.md).

- Все тесты и проверки запускать только локально. Не использовать GitHub Actions для тестирования.
- Тестовый код, сценарии запуска и переиспользуемые инструменты хранить в `tests/` и включать в Git.
- Результаты и материалы тестирования — отчёты, логи, скриншоты, покрытие, временные и сгенерированные тестовые данные — хранить в `test_results/`. Содержимое этой папки оставлять вне индекса и истории Git; папка целиком исключена через `.gitignore`.
- Инструменты тестирования должны создавать `test_results/` при необходимости и направлять туда результаты и временные данные прогонов.

### Уровни тестирования

Использовать четыре уровня:

1. Без тестов.
2. Минимальный.
3. Средний.
4. Полный.

После подготовки стартовой спецификации отдельно согласовать с пользователем состав проверок для каждого уровня и записать согласованные наборы в спецификации. До согласования не определять состав уровней самостоятельно.

Для каждой задачи согласуй с пользователем уровень тестирования до правок и запуска любых тестов или автоматических проверок. Это правило действует и для документации, конфигурации, аудита и ревью. Предложи все четыре уровня и кратко объясни рекомендуемый выбор. Дождись ответа и зафиксируй согласованный уровень в тикете или ответе. До ответа можно читать файлы и сверять конфигурацию.

Если пользователь уже указал уровень или состав проверок, попросил обойтись без них либо явно поручил выбрать объём, следуй этому указанию без повторного вопроса. Согласованный объём действует и для итогового прогона, включая `npm test`, линтеры и проверку типов.

## Данные проекта

В `data/` хранить только вручную добавляемые данные проекта. Временные данные и материалы тестирования размещать в `test_results/`, а не в `data/`.

Хранение производных наборов данных в `data/` предварительно отдельно согласовывать с пользователем.

## Постоянный локальный стенд

Для работы с `gis-platform-alpha` см. [порядок обновления alpha-стенда](ADMIN.md#обновление-локального-alpha-стенда).

После закрытия [#33](https://github.com/stepanosokin/gis-platform/issues/33) разверни первую стабильную версию в Docker Desktop как постоянный Compose-проект `gis-platform`. После каждого следующего завершённого тикета обновляй этот проект с сохранением томов и проверяй доступность через шлюз. Локальные тесты запускай в отдельных временных проектах Compose.

## Работа с удалёнными серверами

Агенту запрещено самостоятельно подключаться по SSH к удалённому серверу и выполнять на нём команды. Для действий на удалённом сервере агент готовит инструкции и команды, которые выполняет пользователь.

## Ясность формулировок

Для упрощения формулировок задач, отчётов, описаний и объяснений применять локальный навык `wait-what` (`~/.agents/skills/wait-what/SKILL.md`): давать необходимый контекст, писать простым техническим языком и сохранять согласованные термины проекта. Упрощение не должно снижать достоверность, точность или ясность.
